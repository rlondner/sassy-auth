Auth Flows

Two flows depending on whether the app is first-party or third-party

OAuth2 Authorization Code Flow
For third-party / external resource servers
1
Resource server redirects user to SassyAuth:
GET /api/auth/oauth/authorize?client_id=<appPublicId>&redirect_uri=...&state=...
↓
2
SassyAuth shows hosted login UI. User authenticates (password, social, magic link, OTP).
↓
3
SassyAuth validates user belongs to an org associated with the requesting app. Issues short-lived code, redirects back:
GET <redirect_uri>?code=...&state=...
↓
4
Resource server exchanges code for JWT:
POST /api/auth/oauth/token
Body: code, client_id, client_secret, redirect_uri
↓
5
SassyAuth resolves effective permissions (roles + direct grants), returns signed RS256 JWT with permissions, org, aud claims.
Resource server verifies JWT using SassyAuth's public key from GET /api/auth/jwks — no round-trip to SassyAuth needed per request.
Direct Login Flow
For first-party apps tightly coupled to SassyAuth
1
First-party app POSTs credentials directly:
POST /api/auth/direct/login
Body: { identifier, password, appId }
↓
2
SassyAuth authenticates via BetterAuth, validates user's org is associated with appId.
↓
3
SassyAuth resolves effective permissions, returns signed RS256 JWT directly in the response body — no redirect.
Also used for Platform Admin login to the SassyAuth Management UI — the management UI is itself a first-party app.
★
Passwordless variants work the same way — the identifier step triggers a magic link or 6-digit OTP sent to email/phone. The code is exchanged for the same JWT at step 3.

Supported Login Methods (both flows)

Password
Username, email, or phone + password
Magic Link
Email link, single-use, time-limited
Email / SMS OTP
6-digit code sent to email or phone
Social Providers
Google · Microsoft · Apple · GitHub
