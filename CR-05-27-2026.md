## Findings (consolidated by severity)

### 🔴 Critical — must fix before merge / push

1. **RBAC isolation broken across orgs** — `apps/auth-server/src/common/permissions/check-permission.ts` (existing) and all consumers in `users.service.ts` (`ce7bbc5`, `6b5dbb3`, `762e58b`, `17b7348`, `aefa396`).
   The pattern
   ```ts
   await checkPermission(callerBaId, 'platform.users.manage').catch(async () => {
     await checkPermission(callerBaId, 'org.users.manage');
   });
   ```
   grants `org.users.manage` holders **global** access to every org's users. `checkPermission` does not constrain by `orgId`. For a multi-tenant SaaS, this is a tenant-isolation bug: an org admin in org A can list/update/delete/role-assign users in org B by passing any `publicId`.
   **Fix:** extend `checkPermission` with an `orgScope` parameter, or layer an `assertSameOrg(callerSaUser, targetSaUser)` helper before every mutation/read in `UsersService.{getUser,updateUser,deleteUser,assignRole,removeRole,resendInvitation,listUsers(when filtered)}`. `platform.users.manage` is the only permission that should be cross-tenant.

2. **Secrets/PII in request URL logs** — `72cffe1` (`request-logging.middleware.ts`).
   The middleware logs `req.originalUrl` verbatim:
   ```ts
   const message = `${req.method} ${req.originalUrl} ${res.statusCode} ${duration}ms`;
   ```
   Both **invitation tokens** (`GET /api/invitations/:token`, `POST /api/invitations/:token/accept`) and the admin's `?token=...` accept-invite redirect appear in URLs. These 32-byte hex tokens are bearer credentials. Any log shipper, file transport, or SIEM forwarder will exfiltrate them. Same risk for any future `?code=`, `?state=`, `?password=` query params.
   **Fix:** redact the path segment for `/api/invitations/:token*` (replace token with `:token`); strip the query string entirely or allowlist non-sensitive query keys. Apply the same scrubbing before forwarding to Sentry (Sentry has `beforeSend` / `requestBodies` knobs).

3. **Admin Next.js middleware does not validate session token** — `1a9ca0e` (`apps/admin/middleware.ts`).
   ```ts
   const sessionToken = request.cookies.get('better-auth.session_token')?.value
   if (!sessionToken) { ... redirect to /login ... }
   ```
   Any non-empty string in the cookie passes the gate. Combined with the manual cookie copy from auth-server in `login/actions.ts` (which uses a brittle regex and **omits Max-Age/Expires/Secure attributes upstream sent**), this is brittle defense-in-depth. The actual session validation only happens when API calls fire, so any admin page that doesn't immediately fetch from auth-server will render shells to attackers.
   **Fix:** call `auth.api.getSession()` (BetterAuth Node API) from middleware via a thin `/api/auth/me`-style endpoint, or use a JWT introspection at the edge. At minimum, set the cookie's `expires` from the upstream `Set-Cookie` and adopt `__Secure-` prefix in production.

### 🟡 Warning — fix soon

4. **PII (email) emitted to logs and Sentry** — `a68f119`, `f0e2a48`.
   - `UsersService.createUser` logs `{ email: dto.email }` on creation (`users.service.ts:171`).
   - Admin layout: `Sentry.setUser({ email: session.user.email })` (`(admin)/layout.tsx:31`) and `signIn` action calls `Sentry.setUser({ email })`.
   For GDPR/SOC2, plaintext emails in error tracking and structured logs need a DPA-aware policy. Prefer `{ id: saUser.publicId }` and `setUser({ id })`. Email may still be needed for correlation — emit a hash (`sha256(email)`) instead.

5. **Inconsistent `publicId` scheme breaks Sqid convention** — `92ecc2c`, `aefa396`.
   `createUser` now uses `baUserId.slice(0, 12)` and `baUserId.slice(12, 24)` as `publicId` for both `SaUser` and `SaInvitation`. UUIDs contain `-` at positions 8/13/18/23, so those slices include dashes (e.g., `f47ac10b-58c`, `c-4372-a567-`). This:
   - Visually differs from existing Sqid-encoded IDs elsewhere in the codebase.
   - Could collide if `publicId` uniqueness is enforced and another UUID happens to share a prefix (low but non-zero risk over time).
   - `resendInvitation` uses the same UUID-slice pattern, so the invitation's `publicId` is no longer derived from the parent user.
   **Fix:** keep `sqids.encode()` for `publicId`, but seed from a **counter or hash**, not `Date.now() % 1_000_000` (the original pre-fix code was already collision-prone — two creations in the same ms collide). The safest is `sqids.encode(saUser.id)` after creation, or a `nanoid(12)` alphabet-restricted to your URL-safe set.

6. **Hardcoded transaction tx ignored in InvitationsService spec mock** — `10a6466`.
   The test's `$transaction.mockImplementation` passes `mockPrisma` as the `tx`, but the production code never re-reads `inv` inside the transaction. The invitation check (`inv.expiresAt`, `inv.usedAt`) is done OUTSIDE the tx, so a race between two concurrent `accept` calls for the same token both pass the gate and both create accounts — second one fails on unique constraint, but only after the first transaction has committed Account+SaUser changes. The unique constraint on `saInvitation.token` saves us from double-token-use, but the `Account.create` could leave half-state if the constraint is on `(userId, providerId)` rather than `(invitationToken)`.
   **Fix:** Re-fetch `inv` inside the transaction with `tx.saInvitation.findUnique(...)` and re-validate before the writes; or use an atomic conditional update on `saInvitation` (`update where usedAt: null` and check `count === 1`).

7. **Password policy is minimum-length only** — `8f9e144` (`AcceptInvitationDto`), `268e8d7` (`AcceptInviteForm`).
   `@MinLength(8)` is below NIST/OWASP enterprise norms for an admin-targeted product. No common-password check, no entropy floor.
   **Fix:** add `zxcvbn` (or `@zxcvbn-ts/core`) with a minimum score of 3 on the API side; surface a strength meter on `AcceptInviteForm`. Mirror the same validator on `/api/auth/sign-in/email` flow if signup is reachable.

8. **User enumeration via login error codes** — `1a9ca0e` (`login/actions.ts`).
   The Server Action distinguishes `401` (invalid credentials) from `403` (inactive). The auth-server already returns a generic `INVALID_CREDENTIALS` on bad email (good), but if it ever returns 403 for `status='pending'/'inactive'`, that confirms account existence. Either always return 401 from the auth-server for inactive accounts and surface a separate "check your invitation" link by other means, or accept this as a UX tradeoff and document it as residual risk.

9. **`X-Request-Id` is reflected from inbound header without validation** — `495a133`.
   `req.headers['x-request-id']` is accepted as-is and used as the requestId in logs and Sentry. An attacker can inject log-line forging characters, ANSI escapes, or extremely long strings (DoS by log volume).
   **Fix:** validate against `/^[A-Za-z0-9._-]{1,128}$/`; fall back to UUIDv4 otherwise. Also consider rejecting an inbound value entirely from untrusted origins (only honor it from internal services).

10. **Sentry source maps and DSN exposure** — `0e3d406`.
    `sentry.client.config.ts` ships `NEXT_PUBLIC_SENTRY_DSN` to the browser — that's expected, but make sure the project's "allowed domains" is set in Sentry to prevent DSN abuse. `withSentryConfig` uploads source maps if `SENTRY_AUTH_TOKEN` is set; confirm `widenClientFileUpload`/`hideSourceMaps` defaults are still applied (Sentry's Next.js wrapper hides them on the public path by default in v10, but verify in `.next/static`).

11. **`createUser` `username` collision** — `ce7bbc5`.
    `prisma.saUser.create({ data: { username: dto.username ?? null } })` — if `username` has a unique constraint, supplying a duplicate throws a generic `PrismaClientKnownRequestError`. The transaction will roll back, but the BetterAuth `user` row is created **then** the saUser — wait, after `92ecc2c` it IS wrapped in `$transaction`, good. Still, the controller surfaces a 500 instead of a 409.
    **Fix:** catch `P2002` and map to `ConflictException('username|email already in use')` in `UsersService.createUser`.

12. **`assignRole` lacks idempotency guard** — `762e58b`.
    `prisma.saUserRole.create({ data: { userId, roleId } })` — if the `(userId, roleId)` pair has a unique constraint and the role is already assigned, this throws. The test mocks success and never exercises the dup case.
    **Fix:** use `upsert` on the composite key, or catch `P2002` → return 204 (idempotent semantics for role assignment match REST conventions).

13. **Cookie set in `login/actions.ts` discards upstream attributes** — `1a9ca0e`.
    The regex extracts only `better-auth.session_token=VALUE` and replays it with hardcoded `{ httpOnly, secure: NODE_ENV==='production', sameSite:'lax', path:'/' }`. No `Max-Age`, no `Expires`, no `Domain`. The cookie becomes a **session cookie** — closing the browser logs the user out. If BetterAuth issues a 7-day token, the user has a 7-day server-side session but only a tab-lifetime client cookie.
    **Fix:** parse the full `Set-Cookie` (use `set-cookie-parser`) and propagate `expires`/`maxAge`. Avoid hand-rolled regex.

14. **`getRoles(selectedOrg.appId)` effect missing dependency** — `a3ebb15` (`UserCreateDrawer`).
    `React.useEffect(..., [form.orgId])` — `orgs` and `getRoles` are stable in practice, but ESLint `react-hooks/exhaustive-deps` will flag this. Low risk; add `orgs` to the array.

15. **`acceptInvitation` does not invalidate sibling sessions** — `10a6466`.
    After accepting an invite, the user is logged in next via `/login`. There's no step that revokes any older BetterAuth sessions tied to this `baUserId`. If a user was previously soft-deleted and recreated with the same email (collides on BetterAuth `User` table via the same `baUserId` is impossible since UUID; but if there's an email-based account lookup elsewhere, that could matter).
    **Fix:** out of scope today, but worth filing as an issue.
