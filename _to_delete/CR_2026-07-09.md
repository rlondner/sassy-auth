### PR #145 — `user-create-drawer` form wrapping (2 non-merge commits, +4/-4)

**Diff:**

```diff
-        ) : (
-          <>
+          <form onSubmit={(e) => { e.preventDefault(); handleSubmit() }}>
             …
-                <Button variant="secondary" onClick={() => onOpenChange(false)} disabled={submitting}>…</Button>
-                <Button onClick={handleSubmit} disabled={submitting}>
+                <Button type="button" variant="secondary" onClick={() => onOpenChange(false)} disabled={submitting}>…</Button>
+                <Button type="submit" disabled={submitting}>
             …
-          </>
+          </form>
```

**Findings:**

- 🟡 **Warning — double-submit race.** `handleSubmit()` (drawer body lines 98–126) has no early-return on `submitting`; it only guards the button via `disabled={submitting}`. Enter-key form submission does **not** honor `disabled` on the submit button across all browsers/hydration states — Chromium fires `submit` even when the submit button is disabled if the form has a single implicit-submission trigger. On a cold-start hydration window (the same window the sibling commit `371e809` widens the login timeout for), a fast double-Enter can dispatch two `createUserAction` calls, both allocating a new user and both landing an invite email. Add `if (submitting) return` at the top of `handleSubmit()`.
- 🟢 Correct semantic HTML; explicit `type="button"` on Cancel avoids implicit submit.
- 🟢 No client-side XSS surface, no server-trust changes.

**Recommendation:** Request changes — add re-entry guard.
