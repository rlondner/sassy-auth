## 🔴 bug-0001 — RBAC isolation broken across orgs

**Fixed:** true
**Severity:** Critical
**Files:** `apps/auth-server/src/common/permissions/check-permission.ts`, all callers in `apps/auth-server/src/users/users.service.ts`
**Commits:** `633dfe7`, `17b7348`, `6b5dbb3`, `762e58b`, `aefa396`, `ce7bbc5`

**Description.** `checkPermission(betterAuthUserId, required)` only checks whether the caller holds the named permission. It never compares the caller's `orgId` to the target resource's `orgId`. The standard guard pattern used everywhere in `UsersService`

```ts
await checkPermission(callerBaId, 'platform.users.manage').catch(async () => {
  await checkPermission(callerBaId, 'org.users.manage');
});
```

therefore lets any holder of `org.users.manage` in org A read, update, delete, or assign roles for users in org B by passing any `publicId`. `platform.users.manage` should be the only cross-tenant permission.

**Repro.** Create two orgs `A` and `B`, give user `alice` (in org A) the `org.users.manage` role, create user `bob` in org B. Call `GET /api/users/<bob's publicId>` as alice — returns bob's profile instead of 403.

**Fix sketch.** Add an `orgScope` parameter to `checkPermission`, or layer an `assertSameOrg(callerSaUser, targetSaUser)` helper before every mutation/read in `UsersService.{getUser, updateUser, deleteUser, assignRole, removeRole, resendInvitation, getUserRoles, getEffectivePermissions, listUsers}` when the caller only has `org.users.manage` (and not `platform.users.manage`).

**Tests needed.** Cross-org access test for each of the 9 affected methods.

## 🔴 bug-0002 — Invitation tokens leak via request URL logs

**Fixed:** true
**Severity:** Critical
**File:** `apps/auth-server/src/common/logger/request-logging.middleware.ts:19`
**Commit:** `72cffe1`

**Description.** The middleware emits

```ts
const message = `${req.method} ${req.originalUrl} ${res.statusCode} ${duration}ms`;
```

`req.originalUrl` includes the path AND the query string. Endpoints `GET /api/invitations/:token` and `POST /api/invitations/:token` embed a 32-byte hex token as a **path segment** that functions as a bearer credential — anyone with the token can claim the account. Logging it means every log shipper, file transport, Sentry transport, and SIEM forwarder receives a usable credential. Same risk for any future `?code=`, `?state=`, `?password=`, `?secret=` query params.

**Repro.** Tail logs while issuing `curl http://localhost:3000/api/invitations/<token>` — token appears verbatim in the structured log entry.

**Fix sketch.**
1. Sanitize known-sensitive path segments (replace token in `/api/invitations/...` with `:token`) before logging.
2. Strip the query string by default — only allowlist known-safe keys.
3. Apply the same scrubber to Sentry breadcrumbs / events (`beforeSend`, `requestBodies`).

**Tests needed.** Middleware spec: assert that a request to `/api/invitations/abc123def456...` logs `/api/invitations/:token`, not the literal token.

## 🔴 bug-0003 — Admin middleware accepts any non-empty cookie value

**Fixed:** true
**Severity:** Critical
**File:** `apps/admin/middleware.ts`
**Commit:** `1a9ca0e`

**Description.**

```ts
const sessionToken = request.cookies.get('better-auth.session_token')?.value
if (!sessionToken) { /* redirect to /login */ }
```

The middleware never validates the cookie against the auth server. Any non-empty string passes the edge gate — an attacker can set `document.cookie = 'better-auth.session_token=anything'` and load admin shells. Real session validation only happens later when API calls fire, so any admin page that renders without an immediate fetch (or shows even partial UI before the fetch resolves) becomes an information-disclosure surface for attackers.

**Repro.** In a fresh browser, run `document.cookie = 'better-auth.session_token=junk; path=/'` then navigate to `/users`. The middleware lets you through; the page renders the shell before `getSession()` fails.

**Fix sketch.** Hit the auth-server `/api/auth/get-session` endpoint from middleware with the cookie attached, or use a JWT introspection at the edge. If the response is unauthenticated, redirect to `/login`.

**Tests needed.** Middleware integration test with a junk cookie value.

## 🟡 bug-0004 — PII (plaintext email) emitted to logs and Sentry

**Fixed:** true
**Severity:** Warning
**Files:** `apps/auth-server/src/users/users.service.ts:178`, `apps/admin/app/(admin)/layout.tsx:32`, `apps/admin/app/login/actions.ts:54`
**Commits:** `a68f119`, `f0e2a48`

**Description.** `UsersService.createUser` logs `{ email: dto.email }` on user creation; admin layout calls `Sentry.setUser({ email: session.user.email })`; `signIn` action calls `Sentry.setUser({ email })`. For GDPR/SOC2 environments, plaintext emails in structured logs and error tracking need a DPA-aware policy.

**Fix sketch.** Use the opaque `publicId` (Sqid) instead of email. If correlation across systems is still needed, hash: `sha256(email).slice(0,16)`. Remove `email` from `Sentry.setUser`.

**Tests needed.** Spec asserting no `email` field in log payloads / `Sentry.setUser` calls.

## 🟡 bug-0005 — Inconsistent `publicId` scheme (UUID slice vs Sqid)

**Fixed:** true
**Severity:** Warning
**Files:** `apps/auth-server/src/users/users.service.ts:149,163,278`
**Commits:** `92ecc2c`, `aefa396`

**Description.** `createUser` and `resendInvitation` now use raw UUID slices (`baUserId.slice(0,12)`, `baUserId.slice(12,24)`, `crypto.randomUUID().slice(0,12)`) as `publicId`. UUIDs contain `-` at positions 8/13/18/23, so the resulting `publicId` strings look like `f47ac10b-58c` and `c-4372-a567-` — visually inconsistent with the existing Sqid convention used everywhere else, and the dash-containing values may also collide if `publicId` uniqueness is enforced and another UUID happens to share a prefix.

**Fix sketch.** Inject `SqidService` into `UsersService` and use `sqids.encode(createdSaUser.id)` after the row is created (two-step inside the transaction: create with placeholder, then update `publicId`). Same for invitations.

**Tests needed.** Spec assertion that `publicId` matches the Sqid alphabet.

## 🟡 bug-0006 — Invitation race window: `inv` not re-fetched inside `$transaction`

**Fixed:** true
**Severity:** Warning
**File:** `apps/auth-server/src/invitations/invitations.service.ts:37-76`
**Commit:** `10a6466`

**Description.** `acceptInvitation` checks `inv.expiresAt` and `inv.usedAt` **before** opening the transaction, then writes inside the transaction without re-reading. Two concurrent `POST /api/invitations/<same-token>` calls can both pass the gate and both begin transactions; the second one's `Account.create` succeeds (different generated `id`), and both `saInvitation.update({ usedAt })` calls "succeed" (idempotent write to the same row). The unique constraint on `Account(userId, providerId)` does eventually save the data, but only after duplicate `bcrypt.hash()` work and possibly conflicting `emailVerified` writes.

**Fix sketch.** Re-fetch `inv` inside `tx.saInvitation.findUnique(...)` and re-assert `usedAt === null && expiresAt > now`. Or use atomic conditional update: `tx.saInvitation.updateMany({ where: { token, usedAt: null }, data: { usedAt: now } })` and assert `count === 1`.

**Tests needed.** Concurrent-accept test with two parallel calls.

## 🟡 bug-0007 — Password policy is minimum-length only (8 chars)

**Fixed:** true
**Severity:** Warning
**Files:** `apps/auth-server/src/invitations/dto/accept-invitation.dto.ts:4`, `apps/admin/app/accept-invite/accept-invite-form.tsx:27,62`
**Commit:** `8f9e144`, `268e8d7`

**Description.** `@MinLength(8)` only — no entropy floor, no common-password check, no character-class requirement. Below NIST/OWASP enterprise norms for an admin-targeted product.

**Fix sketch.** Bump to `@MinLength(12)` immediately as a first pass. Long-term: add `@zxcvbn-ts/core` with `score >= 3` validator. Surface a strength meter on the form.

**Tests needed.** DTO validation tests for weak vs strong passwords.

## 🟡 bug-0008 — User enumeration via login error code distinction

**Fixed:** true
**Severity:** Warning (residual risk)
**File:** `apps/admin/app/login/actions.ts:34-36`
**Commit:** `1a9ca0e`

**Description.**

```ts
if (res.status === 401) return { error: 'invalidCredentials' }
if (res.status === 403) return { error: 'inactive' }
```

If the auth-server ever returns 403 for inactive accounts (it currently returns generic 401 for bad email, which is good), this code path will distinguish "account exists but disabled" from "account doesn't exist" — a user-enumeration oracle.

**Fix sketch.** Always render the same `invalidCredentials` message in the UI. Surface "your account is disabled" via email or a "contact admin" link, not via the login response.

**No code PR.** Filed as advisory in TODO.md; close after auth-server is audited to confirm it never returns 403 on this flow.

## 🟡 bug-0009 — `X-Request-Id` reflected from inbound header without validation

**Fixed:** true
**Severity:** Warning
**File:** `apps/auth-server/src/common/middleware/request-id.middleware.ts:16`
**Commit:** `495a133`

**Description.** `(req.headers['x-request-id'] as string) ?? uuidv4()` — accepts any inbound header value, including ANSI escape sequences, newlines (log forging), null bytes, or arbitrarily long strings (DoS via log volume).

**Fix sketch.** Validate `/^[A-Za-z0-9._-]{1,128}$/`; fall back to `uuidv4()` on mismatch. Optionally only honor inbound `X-Request-Id` from known internal origins (e.g., when `X-Forwarded-For` is from a trusted proxy).

**Tests needed.** Spec asserting that a malicious inbound value is replaced by a fresh UUID.
