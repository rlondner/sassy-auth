# bug-0256: `autoSignIn: false` added to `auth.config.ts` by three open PRs (#316, #328, #329) — an unstated, untested auth-server change smuggled under cosmetic "Palette" titles → guaranteed 3-way merge conflict

**Severity:** Medium (scope creep + duplicate work + missing test — recurring Jules pattern)
**Status:** Open
**Fixed:** false
**Introduced by:** PR **#328** (`jules-16680163062728024582-5c7c94b2`, Jules bot) and PR **#329**
(`palette/share-link-copy-feedback-16997803198602290621`, Jules bot), both opened in the
2026-08-16 → 2026-08-17 window. The same hunk also lives in the still-open PR **#316**
(`palette/accessible-table-tooltips-…`, open since 2026-08-13).

## Description

Both PRs in this review window add the **identical single line** to
`apps/auth-server/src/auth/auth.config.ts`:

```diff
   emailAndPassword: {
     enabled: true,
+    autoSignIn: false,
     resetPasswordTokenExpiresIn: 3600, // 1 hour
```

Neither PR's stated purpose touches authentication behavior:

- **PR #328** — "🎨 Palette: Add localized ARIA labels and tooltips to row action triggers"
- **PR #329** — "🎨 Palette: Standardize ShareLinkDialog copy feedback hook"

The same `autoSignIn: false` line is **also** present in the still-open **PR #316**. So **three
open PRs now add the exact same one-line hunk on the same line of the same file** → whichever
merges first, the other two conflict on that hunk.

`autoSignIn: false` is a **real behavioral change**: it disables BetterAuth's default of
establishing a session immediately after `sign-up`, forcing an explicit sign-in afterwards. That
may well be *desirable* (it closes an auto-session-on-registration surface), but it is:

1. **Unrelated to every carrier PR's stated scope** (tooltips / copy feedback).
2. **Not on `master`** — so it is a genuine pending change, not a no-op.
3. **Shipped with no test** asserting the new post-signup behavior in any of the three PRs.
4. **Interacting with `POST /api/register`** (self-serve signup) and the invite-accept flow, both
   of which rely on the session/JWT lifecycle — a silent flip here can change what those endpoints
   return without any of the three PR authors having reviewed it as an auth change.

This is the same anti-pattern already filed against this Jules lineage: cosmetic "Palette" PRs
bundling `apps/auth-server` edits — cf. [bug-0246](./bug-0246.md) (`SEED_RUNNING` gate bypass in
#303), [bug-0247](./bug-0247.md) (`SEEDING` bypass in #306), [bug-0251](./bug-0251.md) (#316
bundles `auth.config.ts` + seeds under a tooltip title). It is also the same
duplicate-generation problem as [bug-0254](./bug-0254.md) (#324 vs #316), now escalated to a
**three-way** collision on the auth config.

## Why this is a bug (and not just noise)

1. **Guaranteed merge conflict** between three of the repo's own open PRs on one auth-config line.
2. **An auth-behavior change with zero auth-focused review or test coverage**, hidden behind two
   UI titles and one already-blocked PR.
3. **Decision fork:** if `autoSignIn: false` is wanted, it should land once, on its own auth-server
   PR, with a test — not be re-emitted as a rider on every cosmetic PR Jules generates.

## Files

- `apps/auth-server/src/auth/auth.config.ts` — `emailAndPassword.autoSignIn: false` (same line in
  PR #316, #328, #329).

## Suggested fix

- **Extract the auth change to a single, purpose-named PR** (`fix/auth-disable-autosignin` or
  similar) off `master`, with a test asserting that `POST /api/auth/sign-up/email` does **not**
  return a session cookie and that a subsequent explicit sign-in is required.
- **Strip `autoSignIn: false` (and any other `apps/auth-server/**` edit) from #316, #328, #329.**
  Reduce each to its stated UI scope only.
- **Add the Jules guardrail** already recommended in bug-0246/0251: forbid `palette/*` /
  UI-titled PRs from modifying `apps/auth-server/**`.
