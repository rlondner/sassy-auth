# bug-0250: Seed scripts set `twoFactorPromptedAt: new Date()`, suppressing the 2FA enrollment prompt for every seeded user

**Severity:** Critical (security posture regression — 2FA enrollment silently skipped)
**Status:** Open
**Fixed:** false
**Introduced by:** PR #316 (`palette/accessible-table-tooltips-…`, Jules bot — "🎨 Palette: Standardized Table Copy and Row Action Accessible Tooltips") **and** PR #315 (`palette-ux-validation-rebasing-…`, "Separate Drawer validation checks…"). Both add the identical change; neither is on `master`.

## Description

Three seed scripts now stamp `twoFactorPromptedAt` with the current time at user-creation:

```ts
// apps/auth-server/src/seed/seed.ts  (seedPlatformAdmin)
// apps/auth-server/src/seed/demo-multitenant.ts  (ensureUser)
// apps/auth-server/src/seed/demo-resource-server.ts  (ensureUser)
data: {
  // …
  status: 'active',
  twoFactorPromptedAt: new Date(),   // <-- added by #316 / #315
},
```

The admin 2FA-enrollment nudge is gated by `shouldPromptTwoFactor`
(`apps/admin/lib/two-factor-prompt.ts`, canonical copy in
`apps/auth-server/src/auth/should-prompt-two-factor.ts`):

```ts
export function shouldPromptTwoFactor(params): boolean {
  if (params.twoFactorEnabled) return false;
  if (!params.promptedAt) return true;                 // prompt only when never prompted…
  const intervalMs = params.intervalDays * 24 * 60 * 60 * 1000;
  return params.now.getTime() - params.promptedAt.getTime() > intervalMs;  // …or interval elapsed
}
```

With `promptedAt` set to "now" at seed time, the gate returns `false` for every seeded user
until `TWO_FACTOR_TRUST_DAYS` (default **14**) have elapsed. The login flow
(`apps/admin/app/login/actions.ts:234`) therefore **never routes seeded users to
`/login/two-factor-prompt`** for two weeks after each seed.

## Why this is a bug

1. **Suppresses 2FA enrollment for exactly the accounts that most need it.** The seeded users
   are the **platform admins** and the demo tenant/resource-server users — the highest-privilege
   accounts in the system. Marking them "already prompted" means a freshly-seeded environment
   silently ships privileged accounts that are never nudged to enrol in 2FA. If seeds are used to
   bootstrap a real/staging deployment (as `.env.example` and the seed docs suggest), this is a
   direct weakening of the account-security posture the 2FA feature exists to provide.
2. **It masks regressions in the enrollment flow under test.** The 2FA prompt is suppressed for
   precisely the users the e2e/dev flows exercise, so a broken enrollment prompt would not
   surface during normal seeded testing — the opposite of what test data should do.
3. **Not recoverable by re-seeding.** In all three files the write sits in the create branch of
   an idempotent upsert (`ensureUser` / `seedPlatformAdmin`), so re-running the seed does **not**
   clear the timestamp. Once a dev/CI database is seeded, the suppression persists across
   re-seeds; you must manually null the column or drop the DB.
4. **No explanation, no opt-in, no test.** The change is a bare one-liner in each seed with no
   comment, no env flag, and no accompanying assertion of intended behavior.

## Files

- `apps/auth-server/src/seed/seed.ts` (≈ line 117, `seedPlatformAdmin`)
- `apps/auth-server/src/seed/demo-multitenant.ts` (≈ line 100, `ensureUser`)
- `apps/auth-server/src/seed/demo-resource-server.ts` (≈ line 160, `ensureUser`)
- Gate (unchanged, for reference): `apps/admin/lib/two-factor-prompt.ts`,
  `apps/auth-server/src/auth/should-prompt-two-factor.ts`, `apps/admin/app/login/actions.ts:234`

## Suggested fix

Prefer leaving the field `null` in seeds so seeded users hit the normal enrollment prompt:

```ts
// simplest: remove the line — the column defaults to null
status: 'active',
```

If some test genuinely needs to *skip* the prompt page, make it explicit and opt-in rather than
the default, and only outside production:

```ts
const suppress2fa =
  process.env.SEED_SUPPRESS_2FA_PROMPT === '1' && process.env.NODE_ENV !== 'production';
// …
...(suppress2fa ? { twoFactorPromptedAt: new Date() } : {}),
```

Whichever path is chosen, add a test asserting that a freshly-seeded platform admin with
`twoFactorEnabled=false` **is** routed to `/login/two-factor-prompt` on first login (i.e. the
gate still fires) unless the suppression flag is explicitly set.
