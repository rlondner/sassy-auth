### bug-0214 :yellow_circle: Warning — directLogin org/app mismatch returns 403 before scrypt — timing oracle

**Files:**
- `apps/auth-server/src/token/token.controller.ts:384-387`

**Description:** The bug-0209 timing guard added a dummy `verifyPassword` on user-not-found paths to equalize response times. However, when the user IS found but their org's `appId` doesn't match the requested app, a `ForbiddenException(USER_ORG_MISMATCH)` is thrown at line 386 BEFORE password verification. This creates a three-way timing oracle:
- User-not-found: dummy scrypt (~100ms) → 401 `INVALID_CREDENTIALS`
- User-found, wrong tenant: no scrypt (~0ms) → 403 `USER_ORG_MISMATCH`
- User-found, right tenant, wrong password: scrypt (~100ms) → 401 `INVALID_CREDENTIALS`

An attacker can (1) confirm a user exists by measuring response time, then (2) enumerate which tenant/app they belong to by trying different `appId` values.

**Impact:** Tenant-membership oracle. An attacker learns which app/org a given email belongs to — enables targeted attacks and reveals organizational structure.

**Fix:** Move the org/app mismatch check AFTER password verification. Collapse the error response into `INVALID_CREDENTIALS` (same as user-not-found) to eliminate both timing and error-code side channels:
```typescript
// 3. Validate password (before any org/app checks)
const account = await prisma.account.findFirst({ ... });
if (!account?.password) { /* dummy scrypt + throw INVALID_CREDENTIALS */ }
const valid = await verifyPassword({ hash: account.password, password: dto.password });
if (!valid) throw new UnauthorizedException(INVALID_CREDENTIALS);
// 4. THEN check org/app match
if (saUser.org.appId !== app.id) throw new UnauthorizedException(INVALID_CREDENTIALS);
```

**Fixed:** false

### bug-0215 :large_blue_circle: Minor — directLogin timing guard incomplete — OAuth-only account path skips dummy scrypt

**Files:**
- `apps/auth-server/src/token/token.controller.ts:396-403`

**Description:** When the user IS found by identifier but has no credential-provider BetterAuth account (`!account?.password`), the controller throws `INVALID_CREDENTIALS` immediately at line 403 WITHOUT running `verifyPassword`. This path is measurably faster (~0ms DB lookup only) than the happy path (~100ms scrypt). An attacker who already knows a valid identifier can time responses to distinguish "has a password-based account" from "OAuth-only account (Google/Microsoft/etc)."

**Impact:** Narrow information leakage — reveals whether a known user authenticates via password or social login. Useful for targeted phishing.

**Fix:** Run the dummy `verifyPassword` before the throw:
```typescript
if (!account?.password) {
  await verifyPassword({ hash: await getDummyPasswordHash(), password: dto.password });
  throw new UnauthorizedException(INVALID_CREDENTIALS);
}
```

**Fixed:** false

### bug-0216 :yellow_circle: Warning — Post-login OAuth `next` path is broken — bug-0149 redirect non-functional

**Files:**
- `apps/auth-server/src/token/token.controller.ts:181`
- `apps/admin/lib/safe-next.ts:10-28`

**Description:** The bug-0149 fix builds the `nextPath` as `${OAUTH_AUTHORIZE_ROUTE}?${query.toString()}`, which resolves to `oauth/authorize?client_id=...` (no leading `/`, no host prefix). The admin's `validateNextUrl()` requires same-origin paths to start with `/` or absolute URLs to match an allowed origin. Since `oauth/authorize?...` satisfies neither condition, `validateNextUrl` returns `null` and the user is redirected to `/users` after login instead of back to the OAuth authorize endpoint. The intended round-trip flow (authorize → login → authorize) is completely broken.

**Impact:** The bug-0149 browser-friendly UX improvement is non-functional. Unauthenticated users who hit the authorize endpoint are sent to the admin login but never return to complete the OAuth flow.

**Fix:** Build the full path including the API prefix:
```typescript
const nextPath = `/${NEST_GLOBAL_PREFIX}/${TOKEN_CONTROLLER_PATH}/${OAUTH_AUTHORIZE_ROUTE}?${query.toString()}`;
// → "/api/token/oauth/authorize?client_id=..."
```
This starts with `/` and will pass `validateNextUrl`'s same-origin path check.

**Fixed:** false

### bug-0217 :yellow_circle: Warning — Helmet CSP breaks Swagger UI in development

**Files:**
- `apps/auth-server/src/configure-nest-app.ts:25`
- `apps/auth-server/src/main.ts:92-129`

**Description:** `helmet()` is applied unconditionally in `configureNestApp()` (line 25), including its default Content-Security-Policy which blocks inline scripts and styles. Swagger UI (mounted at `/api/docs` when `NODE_ENV !== 'production'`, main.ts line 92) relies heavily on inline scripts and styles. The comment at lines 20-23 incorrectly states the strict CSP is "only in effect in prod" — it's applied in all environments. Since Swagger UI is only mounted in non-prod, the CSP conflict only manifests in development, which is exactly where developers need it.

**Impact:** Swagger UI at `/api/docs` is broken in development. API documentation and interactive testing are unusable.

**Fix:** Disable CSP in development:
```typescript
app.use(helmet({
  contentSecurityPolicy: process.env.NODE_ENV === 'production',
}));
```

**Fixed:** false

### bug-0218 :yellow_circle: Warning — `updateUser` status guard is one-hop — pending→inactive→active bypasses it

**Files:**
- `apps/auth-server/src/users/users.service.ts` (status transition guard from commit `f9403a2`)

**Description:** The bug-0152 fix guards the `pending → active` transition (requires a completed invitation). However, an admin can bypass this by calling `updateUser` twice: first `pending → inactive`, then `inactive → active`. The guard only checks the immediate transition, not the destination state's prerequisites. A user activated via this path has no BetterAuth credential — they can appear in the user list as "active" but cannot log in.

**Impact:** Data integrity — an admin (intentionally or accidentally) can activate a user who never accepted their invitation. The user has no password/credential and cannot authenticate, but shows as "active" in the admin UI.

**Fix:** Guard the destination, not just the transition edge. Block any transition to `active` unless the user was previously `active` (reactivation from `inactive`) or has a completed invitation:
```typescript
if (dto.status === 'active' && existing.status === 'pending') {
  throw new BadRequestException('Cannot activate a pending user without invitation acceptance');
}
```

**Fixed:** false

### bug-0219 :yellow_circle: Warning — `updateUser` missing self-modification guard

**Files:**
- `apps/auth-server/src/users/users.service.ts` (updateUser method)

**Description:** Sibling mutations (`deleteUser`, `setUserRoles`, `setUserDirectPermissions`) all check whether the caller is modifying their own account and block it. `updateUser` has no such guard. An admin can set `status: 'inactive'` on their own account, effectively deactivating themselves. While not a security vulnerability per se, it creates an operational incident — the admin is locked out and requires another admin (or direct DB access) to reactivate.

**Impact:** Self-lockout risk. An admin can accidentally or intentionally deactivate their own account.

**Fix:** Add the symmetric self-modification check when `dto.status` is set:
```typescript
if (dto.status && user.betterAuthUserId === callerBaId) {
  throw new ForbiddenException('Cannot modify your own account status');
}
```

**Fixed:** false

### bug-0220 :large_blue_circle: Minor — `SaOauthCode` table has no cleanup job — unbounded growth

**Files:**
- `packages/db/schema.prisma` (SaOauthCode model)
- `apps/auth-server/src/` (no cleanup scheduler)

**Description:** The bug-0039 fix moved OAuth authorization codes from an in-memory Map to the `SaOauthCode` database table. The schema includes an `expiresAt` column, but no scheduled job exists to purge expired codes. Successfully exchanged codes are deleted atomically during token exchange, but codes from abandoned OAuth flows (user starts authorize but never completes token exchange) remain in the table indefinitely.

**Impact:** Unbounded row growth in `SaOauthCode`. Under normal usage growth is slow (one row per abandoned OAuth flow), but it's unbounded over time.

**Fix:** Add a NestJS `@Cron` job that runs periodically (e.g., every 15 minutes) to delete expired codes:
```typescript
@Cron('*/15 * * * *')
async purgeExpiredOauthCodes() {
  await this.prisma.saOauthCode.deleteMany({
    where: { expiresAt: { lt: new Date() } },
  });
}
```

**Fixed:** false

### bug-0221 :large_blue_circle: Minor — `updateUserAction` swallows Next.js `NEXT_REDIRECT` sentinel

**Files:**
- `apps/admin/app/(admin)/users/actions.ts` (updateUserAction)

**Description:** Sibling server actions (`createUserAction`, `deleteUserAction`, etc.) in the admin app re-throw `NEXT_REDIRECT` errors from their try/catch blocks so that Next.js redirect-on-session-expiry works correctly. **Fix:** Re-throw `NEXT_REDIRECT` errors in the catch block, matching the sibling action pattern.

### bug-0223 :large_blue_circle: Minor — Session validation cache negative-caches 5xx auth-server responses

**Files:**
- `apps/admin/middleware.ts:88`

**Description:** The session validation cache stores `{ ok: false }` for any non-2xx HTTP response from the auth-server, including 500 Internal Server Error. Transport-level errors (fetch throws) are correctly NOT cached (lines 95-101), but a 5xx response is treated as a successful HTTP round-trip and hits the `!res.ok` branch, getting cached for the full 10-second TTL. During a momentary auth-server error (e.g., a brief database hiccup), all users whose sessions are checked in that window are redirected to `/login` for up to 10 seconds after the server recovers.

**Impact:** A 1-second auth-server 500 can cause 10 seconds of false-negative session rejections.

**Fix:** Exclude 5xx responses from the negative cache:
```typescript
if (res.ok) {
  sessionCache.set(token, { at: Date.now(), ok: Boolean(body?.user) });
} else if (res.status < 500) {
  sessionCache.set(token, { at: Date.now(), ok: false });
}
```

**Fixed:** false

### bug-0224 :large_blue_circle: Minor — Throttler `@Throttle` decorator values duplicate module-level config

**Files:**
- `apps/auth-server/src/app.module.ts:17-54` (module-level `auth` bucket)
- `apps/auth-server/src/token/token.controller.ts:289-294` (`@Throttle` decorator)
- `apps/auth-server/src/invitations/invitations.controller.ts:7-12` (`@Throttle` decorator)

**Description:** The `auth` rate-limit bucket is defined in `ThrottlerModule.forRoot()` with `{ limit: 10, ttl: 60_000 }`, and the same values are repeated verbatim in `@Throttle` decorators on `directLogin` and the invitations controller. Since `@Throttle` overrides the module-level config, changing the module-level `auth` bucket values would have no effect on these endpoints — the decorator values silently mask the change.

**Impact:** Configuration drift risk. A future change to the module-level rate limit will not propagate to the two most security-sensitive endpoints.

**Fix:** Remove the explicit values from `@Throttle` decorators so they inherit from the module config, or add inline comments referencing the module as the source of truth.

**Fixed:** false

### bug-0225 :yellow_circle: Warning — BetterAuth sign-in/sign-up routes bypass NestJS ThrottlerGuard

**Files:**
- `apps/auth-server/src/main.ts:73` (BetterAuth mounted as raw Express middleware)
- `apps/auth-server/src/app.module.ts:52` (ThrottlerGuard registered as APP_GUARD)

**Description:** BetterAuth is mounted on the underlying Express app via `expressApp.all('/api/auth/*', toNodeHandler(auth))` BEFORE NestJS initializes. The `ThrottlerGuard` registered as `APP_GUARD` in `app.module.ts` is a NestJS guard that only runs within the NestJS execution context. All BetterAuth-managed routes (`POST /api/auth/sign-in/email`, `POST /api/auth/sign-up/email`, magic-link sends, OTP sends) are handled and responded to before NestJS ever sees them. The bug-0080 fix only protects NestJS-handled endpoints (`directLogin`, invitations), giving a false sense of security that "auth endpoints are rate-limited."

**Impact:** The primary authentication endpoints — the most critical brute-force targets — have zero rate limiting. An attacker can brute-force BetterAuth sign-in at unlimited speed.

**Fix:** Add Express-level rate-limiting middleware (e.g., `express-rate-limit`) on the `/api/auth/*` routes before the BetterAuth handler, or enable BetterAuth's own `rateLimit` plugin in `auth.config.ts`.

**Fixed:** false
