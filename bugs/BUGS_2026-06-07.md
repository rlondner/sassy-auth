## :red_circle: bug-0074 -- Inactive/pending users can obtain JWTs via both OAuth and direct login

**Fixed:** false
**Severity:** Critical
**File:** `apps/auth-server/src/token/token.controller.ts` (lines 82-92, 180-276)

**Description.** Neither the OAuth authorize flow nor the direct login flow checks `saUser.status` before issuing a JWT. After finding the `saUser` record, the controller validates org/app match (line 90, 229) and password (line 248) but never verifies that `status === 'active'`. A user set to `inactive` via `updateUser` can still authenticate and receive a valid JWT. Similarly, a user with status `pending` (not yet accepted their invitation) could authenticate if they somehow obtained credentials.

The `UpdateUserDto` supports setting `status` to `inactive` (line 8 of `update-user.dto.ts`), but this status field has no runtime effect on authentication -- it's purely cosmetic.

**Fix sketch.** After resolving the `saUser` in both `oauthAuthorize` (after line 89) and `directLogin` (after line 226), add a guard:

```typescript
if (saUser.status !== 'active') {
  throw new ForbiddenException(TokenErrorCode.USER_NOT_FOUND);
}
```

**Tests needed.** E2E test: set a user to `inactive`, attempt direct login -- should return 403. Same for OAuth authorize flow.

## :yellow_circle: bug-0075 -- `listUsers` accepts but ignores `appPublicId` filter

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/src/users/users.service.ts` (lines 54, 75-78)

**Description.** The `listUsers` method signature accepts `filters: { orgPublicId?: string; appPublicId?: string }`, and the controller passes the `appId` query parameter into `appPublicId`. However, the `where` clause at line 76 only adds `orgPublicId` to the filter -- `appPublicId` is silently ignored. API callers who pass `?appId=xxx` get unfiltered results, which is misleading and could cause the admin UI to display users from unrelated apps.

**Fix sketch.** Either implement the filter by joining through `org.app`:

```typescript
if (filters.appPublicId) {
  where['org'] = { ...where['org'], app: { publicId: filters.appPublicId } };
}
```

Or remove `appPublicId` from the method signature and controller to avoid the false promise.

**Tests needed.** Integration test: `listUsers({ appPublicId: 'xxx' })` should only return users whose org belongs to that app.

## :yellow_circle: bug-0076 -- `listRoles` and `getRole` missing `targetOrgId`; org admins can list all roles cross-tenant

**Fixed:** false
**Severity:** Warning
**Files:**
- `apps/auth-server/src/roles/roles.service.ts` (lines 37, 79)
- `apps/auth-server/src/common/permissions/check-permission.ts`

**Description.** Both `listRoles` and `getRole` call `checkPermission(callerBaId, ['platform.permissions.manage', 'org.permissions.manage'])` without passing a `targetOrgId`. The `checkPermission` helper succeeds for any non-platform permission when no `targetOrgId` is supplied. This means a user with `org.permissions.manage` in Org A can list and view all roles across all apps and orgs in the platform.

Compare with `listUsers` (lines 60-68 of `users.service.ts`), which correctly passes `targetOrgId: -1` when no org filter is specified, forcing the cross-tenant case to require `platform.users.manage`. The roles and permissions services do not follow this pattern.

The same issue exists in `permissions.service.ts` for `listPermissions` and `getPermission`.

**Fix sketch.** Either pass `targetOrgId: -1` when no app filter is specified (forcing platform-level permission), or scope the query to the caller's org when they hold only `org.permissions.manage`.

**Tests needed.** Integration test: a user with `org.permissions.manage` in Org A should NOT be able to list roles for Org B's app.

## :yellow_circle: bug-0077 -- `assignRole` and `removeRole` skip app-scoping validation

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/src/users/users.service.ts` (lines 291-323, 325-343)

**Description.** The single-role `assignRole` (POST) and `removeRole` (DELETE) methods look up the role by `publicId` without validating that the role belongs to the same app as the user's org. In contrast, the bulk `setUserRoles` (PUT) method calls `resolveRoleIdsForApp(org.appId, roleIds)` which validates that every role ID belongs to the target app. This means a caller could assign a role from App A to a user in App B via the POST endpoint, creating cross-app role contamination.

**Fix sketch.** After looking up the role at line 300, validate app match:

```typescript
const user = await prisma.saUser.findUnique({
  where: { publicId: userPublicId },
  include: { org: true },
});
if (role.appId !== user.org.appId) {
  throw new BadRequestException('Role does not belong to this user\'s app');
}
```

**Tests needed.** Integration test: assigning a role from App A to a user in App B's org should return 400.

## :yellow_circle: bug-0078 -- `SaRole` lacks `@@unique([appId, name])` constraint; duplicate role names per app possible

**Fixed:** false
**Severity:** Warning
**File:** `packages/db/schema.prisma` (lines 141-151)

**Description.** The `SaRole` model has `@@index([appId])` but no `@@unique([appId, name])` compound constraint. The application code catches `P2002` unique violations on role creation (line 133 in `roles.service.ts`), but the only unique constraint is on `publicId`. Two roles with the same name in the same app can be created via concurrent requests. Compare with `SaOrg` which has `@@unique([appId, name])` at line 91.

**Fix sketch.** Add `@@unique([appId, name])` to the `SaRole` model. The existing `P2002` catch block will then enforce the constraint at the database level.

**Tests needed.** Migration test: concurrent creation of two roles with the same name in the same app should result in exactly one success.

## :yellow_circle: bug-0079 -- `SaPermission.name` globally unique; prevents same permission name across different apps

**Fixed:** false
**Severity:** Warning
**File:** `packages/db/schema.prisma` (line 132)

**Description.** `SaPermission` has `name String @unique`, making permission names globally unique across all apps. If App A creates a permission named `users.read`, App B cannot create one with the same name. The `resolvePermissionIdsForApp` function validates app-scoping at the application level, suggesting the intended model is per-app uniqueness. This constraint causes confusing 409 Conflict errors when apps need similar permission naming conventions (e.g., `read`, `write`, `manage`).

Compare with `SaOrg` which uses `@@unique([appId, name])` -- per-app uniqueness.

**Fix sketch.** Change line 132 from `name String @unique` to `name String`, and add `@@unique([appId, name])` after line 138. Requires a migration.

**Tests needed.** Integration test: creating a permission named `users.read` in two different apps should both succeed.

## :yellow_circle: bug-0080 -- No rate limiting on `/api/token/direct/login` and `/api/invitations/:token`

**Fixed:** false
**Severity:** Warning
**Files:**
- `apps/auth-server/src/token/token.controller.ts` (lines 153-277)
- `apps/auth-server/src/invitations/invitations.controller.ts` (lines 16-20)
- `apps/auth-server/src/app.module.ts`

**Description.** No rate limiting is configured anywhere in the auth server. The `/api/token/direct/login` endpoint accepts unlimited password attempts -- an attacker can brute-force credentials without throttling. Similarly, the invitation acceptance endpoint can be probed repeatedly. BetterAuth may provide its own rate limiting on `/api/auth/*` routes, but the custom token and invitation endpoints are outside that scope.

**Fix sketch.** Install `@nestjs/throttler` and configure globally or per-endpoint:

```typescript
import { ThrottlerModule, ThrottlerGuard } from '@nestjs/throttler';

@Module({
  imports: [
    ThrottlerModule.forRoot([{ ttl: 60000, limit: 10 }]),
  ],
  providers: [{ provide: APP_GUARD, useClass: ThrottlerGuard }],
})
```

Apply stricter limits (`@Throttle({ default: { ttl: 60000, limit: 5 } })`) to `directLogin` and invitation acceptance.

**Tests needed.** Integration test: 6th login attempt within 60 seconds should return 429.

## :yellow_circle: bug-0081 -- `UpdateUserDto` string fields lack length constraints

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/src/users/dto/update-user.dto.ts` (lines 1-9)

**Description.** The `UpdateUserDto` has `@IsString() @IsOptional()` on `firstName`, `lastName`, `phoneNumber`, and `username` but no `@MinLength` or `@MaxLength` constraints. An empty string `""` passes validation and would overwrite existing data with blanks. Extremely long strings (megabytes) could be submitted, causing database write overhead. The `CreateUserDto` has proper constraints (`@MinLength(1) @MaxLength(120)` on names), but the update DTO does not follow the same pattern.

**Fix sketch.** Add constraints to match `CreateUserDto`:

```typescript
@IsString() @IsOptional() @MinLength(1) @MaxLength(120) firstName?: string;
@IsString() @IsOptional() @MinLength(1) @MaxLength(120) lastName?: string;
@IsString() @IsOptional() @MinLength(1) @MaxLength(20) phoneNumber?: string;
@IsString() @IsOptional() @MinLength(1) @MaxLength(50) username?: string;
```

**Tests needed.** Unit test: `PATCH /api/users/:id` with `firstName: ""` should return 400. `firstName` with 200 chars should also return 400.

## :yellow_circle: bug-0082 -- `OauthTokenExchangeDto.client_secret` required but never verified

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/src/token/dto/oauth-token-exchange.dto.ts` (line 15); `apps/auth-server/src/token/token.controller.ts` (lines 116-135)

**Description.** The `OauthTokenExchangeDto` declares `client_secret` as a required non-empty string (line 15), but the `oauthToken` controller method never references `dto.client_secret`. The field is validated for presence by class-validator then silently discarded. Any value passes. This gives a false sense of security -- callers may believe they are providing a secret that authenticates the client, but only the authorization code is checked.

**Fix sketch.** Either:
1. Add actual verification: store a hashed `clientSecret` on `SaApp` and compare during token exchange.

**Tests needed.** Integration test: token exchange with wrong `client_secret` should fail (if option 1), or the field should be removed from the DTO (option 2).

## :yellow_circle: bug-0083 -- PrismaClient singleton has no reconnection strategy on connection loss

**Fixed:** false
**Severity:** Warning
**File:** `packages/db/index.ts` (lines 1-14)

**Description.** The PrismaClient singleton is created once and cached globally. If the PostgreSQL connection drops (maintenance window, network blip, connection pool exhaustion), the cached client remains in a broken state. Subsequent requests fail with connection errors until the process restarts. In production, this can cause extended outages if the process manager does not automatically restart on database errors.

In development (`NODE_ENV !== 'production'`), the client is stored on `globalThis` for HMR reuse, but there is no reconnection or health-check logic in either mode.

**Fix sketch.** Add a Prisma middleware or event handler to detect connection errors and trigger reconnection:

```typescript
prisma.$on('error', (e) => {
  if (e.message.includes('connection')) {
    prisma.$disconnect().then(() => prisma.$connect());
  }
});
```

Or configure `connection_limit` and `connect_timeout` in the `DATABASE_URL` query string for automatic pool management.

**Tests needed.** Manual test: stop PostgreSQL, make a request, restart PostgreSQL, make another request -- the second should succeed without process restart.

## :large_blue_circle: bug-0084 -- `apiFetch` sends `Content-Type: application/json` on GET/DELETE with no body

**Fixed:** false
**Severity:** Minor
**File:** `apps/admin/lib/api.ts` (lines 8-20)

**Description.** The `apiFetch` helper unconditionally sets `Content-Type: application/json` on every request, including GETs and DELETEs that have no body. While most servers ignore this, it is technically incorrect per HTTP semantics and can cause unexpected behavior with some proxies or CDNs that reject bodyless requests with a Content-Type header.

**Fix sketch.** Only set `Content-Type` when a body is present:

```typescript
headers: {
  ...(init.body && { 'Content-Type': 'application/json' }),
  Cookie: cookieStore.toString(),
  ...init.headers,
},
```

**Tests needed.** Unit test: `apiFetch('/api/users', { method: 'GET' })` should not set Content-Type header.

## :large_blue_circle: bug-0085 -- User `publicId` generated via UUID truncation instead of Sqid

**Fixed:** false
**Severity:** Minor
**File:** `apps/auth-server/src/users/users.service.ts` (line 185)

**Description.** New user `publicId` is generated as `baUserId.slice(0, 12)` -- the first 12 characters of a BetterAuth UUID. All other entities (apps, orgs, roles, permissions) use Sqids derived from the auto-increment ID, which are guaranteed unique. Truncating a UUID to 12 characters significantly increases collision probability compared to full UUIDs (~2^48 possible values vs ~2^122). While collisions are still unlikely for small user bases, this inconsistency could cause `P2002` unique constraint violations at scale.

**Fix sketch.** Use the same Sqid-based pattern: create the user with a placeholder `publicId`, then update with `this.sqids.encode(createdSaUser.id)`.

**Tests needed.** Verify that 100,000 sequential user creations produce no `publicId` collisions.
