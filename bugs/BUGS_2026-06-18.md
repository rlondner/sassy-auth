## :yellow_circle: bug-0091 -- Auth-server seed `--transpile-only` change bundled into UI tooltip PR

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/package.json` (line 11 in commit `7294691c`)

**Description.** Commit `7294691c` in PR #107 (a UI tooltip standardization PR) modifies the auth-server `seed` script to add `--transpile-only` to `ts-node`. This is an unrelated change bundled into a UI PR:

1. **Scope creep:** The auth-server `package.json` has nothing to do with admin UI tooltips. Reviewing the PR, one expects only UI/i18n/test changes.
2. **Type-safety loss:** `--transpile-only` skips TypeScript type checking during seed execution. If the seed script has type errors (e.g., wrong column name after a migration), they won't surface at seed time — only a confusing runtime error will occur.
3. **Merge conflict risk:** If another branch also modifies `apps/auth-server/package.json`, this creates an unnecessary conflict.

Note: The master branch `package.json` still has the original `seed` script without `--transpile-only`, so this change only exists on the palette branch.

**Fix sketch.** Either:
1. Revert the `package.json` change from PR #107 and submit it as a separate PR with rationale.
2. Or keep `--transpile-only` but add `"seed:typecheck": "tsc --noEmit -p tsconfig.json"` so developers can opt into type checking the seed script.

**Tests needed.** CI pipeline should run `pnpm --filter @sassy-auth/auth-server seed` as part of e2e to catch seed-time errors.

## :yellow_circle: bug-0092 -- CI `e2e.yml` excludes auth-server build, masking pre-existing build errors

**Fixed:** false
**Severity:** Warning
**Files:**
- `.github/workflows/e2e.yml` (line added by commit `22ff6feb`)
- `.Jules/palette.md` (documents the workaround)

**Description.** The newly added CI step `pnpm exec turbo build --filter=!@sassy-auth/auth-server` builds all workspace packages except `@sassy-auth/auth-server`. The `.Jules/palette.md` learning doc explicitly states this "bypass[es] packages with known pre-existing errors."

This means the auth-server has build errors that have existed for an unknown period, and the CI pipeline now institutionalizes ignoring them. If the build errors indicate real issues (missing types, broken imports, stale references), they are silently carried forward. Future developers may not realize the auth-server doesn't build cleanly.

The seed step uses `ts-node` (now with `--transpile-only`) so it doesn't need a `nest build`, but any CI step that eventually needs a built auth-server (e.g., integration tests, Docker image builds) will fail.

**Fix sketch.**
1. Investigate and fix the auth-server build errors. Run `pnpm --filter @sassy-auth/auth-server build` locally to identify them.
2. Once fixed, remove the `--filter=!@sassy-auth/auth-server` exclusion so CI validates all packages.
3. If the build errors are non-trivial, track them as separate bugs and add a `# TODO: Remove filter exclusion once bug-XXXX is fixed` comment in e2e.yml.

**Tests needed.** `pnpm --filter @sassy-auth/auth-server build` should pass in CI without exclusion.

## :large_blue_circle: bug-0093 -- Global jest.mock for @sassy-auth/ui fragile when overridden by file-level mocks

**Fixed:** false
**Severity:** Minor
**Files:**
- `apps/admin/jest.setup.ts` (lines 45-57)
- `apps/admin/components/__tests__/apps-table.test.tsx` (lines 12-36)
- `apps/admin/components/__tests__/orgs-table.test.tsx` (lines 14-38)
- `apps/admin/components/__tests__/permissions-table.test.tsx`
- `apps/admin/components/__tests__/roles-table.test.tsx`
- `apps/admin/components/__tests__/users-table.test.tsx`

**Description.** The `jest.setup.ts` file adds a global `jest.mock('@sassy-auth/ui')` that includes tooltip component mocks. However, all 5 table test files also define their own `jest.mock('@sassy-auth/ui')` which completely overrides the global mock (Jest file-level mocks take precedence over setup-file mocks). The code comment in `jest.setup.ts` warns:

> "NOTE: Some test files (like apps-table.test.tsx) also mock this module. If you add new components to this list, ensure you also update any file-level mocks that might override this one."

This pattern means:
1. Every new UI component that needs mocking must be added in **6 places** (1 global + 5 per-file mocks).
2. Any new test file that mocks `@sassy-auth/ui` must remember to include tooltip mocks, or tests will fail with `TooltipProvider` context errors.
3. The global mock gives a false sense of safety — it only applies to test files that don't define their own UI mock.

**Fix sketch.** Extract a shared mock factory:

```typescript
// apps/admin/test-utils/ui-mock.ts
export function createUiMock() {
  const React = require('react')
  const actual = jest.requireActual('@sassy-auth/ui')
  const Passthrough = ({ children }: any) => React.createElement(React.Fragment, null, children)
  return {
    ...actual,
    Tooltip: Passthrough,
    TooltipTrigger: Passthrough,
    TooltipContent: () => null,
    TooltipProvider: Passthrough,
    // ... other commonly mocked components
  }
}
```

Then each test file uses: `jest.mock('@sassy-auth/ui', () => ({ ...createUiMock(), /* file-specific overrides */ }))`.
