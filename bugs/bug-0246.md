# bug-0246: `SEED_RUNNING` env var bypasses the production session-activation gate

**Severity:** Warning (security hardening / defense-in-depth)
**Status:** Open
**Fixed:** false
**Introduced by:** PR #303 (`palette/table-a11y-tooltips-16709491892231233597`, Jules bot) — not yet on `master`.

## Description

PR #303 adds an environment-variable short-circuit to the BetterAuth **session-create gate**,
which is production authentication code:

```ts
// apps/auth-server/src/auth/auth.config.ts
session: {
  create: {
    before: async (session: { userId: string }) => {
      if (process.env.SEED_RUNNING === "true") {
        return;                      // <-- gate skipped entirely
      }
      const gate = await evaluateSessionGate(prisma, session.userId);
      if (!gate.allowed) {
        // blocks non-active (pending/suspended/deleted) users from creating a session
        throw new APIError("FORBIDDEN", { message: "This account is not active." });
      }
    },
  },
},
```

The flag is set by the seed script at module load:

```ts
// apps/auth-server/src/seed/seed.ts:1
process.env.SEED_RUNNING = "true";
```

The intent is legitimate — the seed needs `signUpEmail` to succeed before an `SaUser` row
exists / is marked active. The problem is **where** the escape hatch lives: the account-status
enforcement that was hardened in **bug-0074** ("Inactive/pending users could authenticate",
one of the original 9 Criticals) can now be disabled process-wide by a single string
environment variable, and that gate is baked into the same `auth` object the running
auth-server imports.

## Why this is a bug

1. **No `NODE_ENV` fence.** The bypass triggers on `SEED_RUNNING === "true"` regardless of
   environment. If that variable is ever exported in a deployed shell, a container base image,
   a CI job that also boots the server, or a `.env` copy-paste, the session gate silently stops
   running and suspended/pending/deleted accounts can mint sessions again — a regression of
   bug-0074 with no log and no test to catch it.
2. **Seed concern leaking into prod code.** A seed-only requirement is now a permanent
   conditional in the hot path of every session creation (password, OTP, social, magic-link).
3. **Undocumented.** `SEED_RUNNING` is not in `.env.example` and not in the README env
   reference, so its security significance is invisible to operators.

## Files

- `apps/auth-server/src/auth/auth.config.ts` — session `create.before` hook (the bypass)
- `apps/auth-server/src/seed/seed.ts:1` — sets `process.env.SEED_RUNNING = "true"`

## Suggested fix

Fence the bypass so it can never fire in a real deployment, and make the intent explicit:

```ts
const SEED_BYPASS =
  process.env.SEED_RUNNING === "true" && process.env.NODE_ENV !== "production";

before: async (session: { userId: string }) => {
  if (SEED_BYPASS) return;
  const gate = await evaluateSessionGate(prisma, session.userId);
  // ...
}
```

Better still, keep the seed out of the production auth path entirely — e.g. create the seed's
BetterAuth users through a dedicated seed-only adapter/instance, or insert the active `SaUser`
row before the session is created so the real gate passes on its own merits. Whatever the
approach, add:

- a regression test asserting the gate **still runs** when `NODE_ENV=production` even if
  `SEED_RUNNING=true`, and
- a `SEED_RUNNING` entry in `.env.example` / README clearly marked *seed-internal — never set
  in a deployed environment*.

- Related: bug-0074 (original account-status enforcement), bug-0163/bug-0186 (session-gate
