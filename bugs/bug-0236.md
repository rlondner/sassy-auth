# bug-0236: OTP active-user gate uses case-sensitive email lookup while the store lowercases

**Severity:** Warning
**Status:** Open
**Fixed:** false

## Description

`sendSignInOtp` decides whether to deliver a sign-in code by looking up the SaUser
with the **raw** email supplied by the caller:

```typescript
const saUser = await db.saUser.findFirst({
  where: { betterAuthUser: { email } },   // raw, un-normalized
  select: { status: true },
});
if (!saUser || saUser.status !== 'active') { /* skip send */ return; }
```

PostgreSQL string equality is case-sensitive, so `User@Example.com` does not match a
stored `user@example.com`. The same function's test-store write normalizes the key
(`otpTestStore.set` → `email.toLowerCase()`), so the two code paths disagree on
normalization within a single function.

Consequences of the mixed-case entry for an existing, active user:
- The gate returns `null` → the request is logged as `skipped_unknown` and **no code
  is sent**, even though the account is active.
- The user sees the neutral "code sent" UI (no enumeration, by design) but never
  receives an email — a silent sign-in failure that is hard to diagnose.

## Files

- `apps/auth-server/src/auth/otp-sender.ts:36-47`
- `apps/auth-server/src/auth/otp-test-store.ts:10-16` (store lowercases — the inconsistency)

## Fix

Normalize the email once at the top of `sendSignInOtp` and use the normalized value for
both the DB gate and the store write (and confirm BetterAuth persists emails lowercased):

```typescript
const normEmail = email.trim().toLowerCase();
const saUser = await db.saUser.findFirst({
  where: { betterAuthUser: { email: normEmail } },
  select: { status: true },
});
// ...
if (isTest) store.set(normEmail, otp);
```

Add a regression test with a mixed-case address (e.g. `A@X.com`) that asserts an active
user still gets `outcome: 'sent'`. The current `otp-sender.spec.ts` only exercises
lowercase addresses, so this gap is untested.
