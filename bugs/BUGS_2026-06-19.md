## :red_circle: bug-0094 -- checkPermissionForApp silently grants access when targetAppId is undefined

**Fixed:** false
**Severity:** Critical
**File:** `apps/auth-server/src/common/permissions/check-permission-for-app.ts` (line 51)

**Description.** When `targetAppId` is `undefined` (omitted by the caller), `checkPermissionForApp` returns early without verifying app scope. Any caller holding a non-platform permission in the required list is unconditionally granted access regardless of which app the resource belongs to. The sentinel `-1` convention used in `listRoles` prevents this in practice, but the silent fallthrough is dangerous when `targetAppId` is accidentally omitted. An org-scoped `org.roles.manage` holder could be approved for operations on any app's resources.

**Fix sketch.** Change the `undefined` check to throw `ForbiddenException('targetAppId is required for non-platform permission checks')` or require `targetAppId` as a non-optional parameter.

**Tests needed.** Unit test: call `checkPermissionForApp` with `targetAppId: undefined` and a non-platform caller — should throw, not pass.

## :red_circle: bug-0099 -- Migration 20260618220100 literal publicId strings violate unique constraint on re-run

**Fixed:** false
**Severity:** Critical
**File:** `packages/db/prisma/migrations/20260618220100_seed_role_perms_and_drop_org_permissions_manage/migration.sql` (lines 14-24)

**Description.** The migration INSERTs two new `SaPermission` rows using literal strings `'pending-roles-manage'` and `'pending-org-roles-manage'` as `publicId` values. The `NOT EXISTS` guard checks by `name`, not by `publicId`. If the migration is interrupted mid-run and re-applied, the second attempt will hit the `SaPermission_publicId_key` unique constraint because a row with `publicId = 'pending-roles-manage'` may already exist from the partial first run.

**Fix sketch.** Add `ON CONFLICT ("name") DO NOTHING` to the INSERT statements, or use `ON CONFLICT ("publicId") DO NOTHING`.

**Tests needed.** Run the migration twice against a database where the first run partially completed (inserted the rows but crashed before step 3).

## :red_circle: bug-0101 -- factories.ts closeScenarioApp tears down shared NestJS server; second spec fails with ERR_SERVER_NOT_RUNNING

**Fixed:** false
**Severity:** Critical
**File:** `apps/auth-server/test/scenarios/factories.ts` (lines 30-32, 43-75)

**Description.** `sharedApp`, `sharedHttpServer`, and `sessionCookies` are module-level singletons. When Jest runs `multitenant-visibility.spec.ts` and `multitenant-grant-ceiling.spec.ts` in the same worker, the first file's `afterAll` calls `closeScenarioApp()`, setting `sharedApp = null` and closing the HTTP server. **Fix sketch.** Use a reference counter: `closeScenarioApp` only tears down when the last consumer disconnects. Or make each spec file fully independent by moving to per-file app instances.

**Tests needed.** Run both scenario spec files in the same Jest worker (`--maxWorkers=1`) and verify both complete successfully.

## :yellow_circle: bug-0095 -- TOCTOU race in OAuth authorize vs code exchange -- user org/app membership not re-validated

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/src/token/token.controller.ts` (lines 107-116, 207-213)

**Description.** At authorize time, the controller verifies `saUser.org.appId === app.id`. At exchange time (`oauthToken`), it fetches `saUser` by `userPublicId` and issues a JWT without re-checking that the user still belongs to an org whose `appId` matches the app encoded in the authorization code. If a user is moved to a different org between authorize and exchange, the JWT carries the new org's `publicId` but the `appPublicId` in the code may no longer match.

**Fix sketch.** At exchange time, after fetching `saUser`, verify `saUser.org.appId === app.id` (where `app` is resolved from the code's `appPublicId`). Reject with `UNAUTHORIZED_CLIENT` if the check fails.

**Tests needed.** E2E test: authorize as user in org A, move user to org B, exchange code — should fail.

## :yellow_circle: bug-0098 -- Migration 20260618220100 isSystem bulk UPDATE not scoped to platform app

**Fixed:** false
**Severity:** Warning
**File:** `packages/db/prisma/migrations/20260618220100_seed_role_perms_and_drop_org_permissions_manage/migration.sql` (lines 4-6)

**Description.** Step 1 runs `UPDATE "SaPermission" SET "isSystem" = true WHERE "name" LIKE 'org.%'`. This is a global bulk update that affects all apps, not just the platform app. If a customer/demo app has a permission named `org.something`, this migration silently marks it as a system permission, potentially enabling cross-app grants.

**Fix sketch.** Scope the update: `WHERE "name" LIKE 'org.%' AND "appId" = (SELECT id FROM "SaApp" WHERE "isPlatform" = true)`.

**Tests needed.** Create a non-platform app with an `org.custom` permission before running the migration — verify it is NOT marked `isSystem`.
