## :large_blue_circle: bug-0033 — Sidebar active-route matching uses `startsWith` without path boundary check

**Fixed:** false
**Severity:** Minor
**File:** `apps/admin/components/sidebar-shell.tsx` (line 66)

**Description.** The sidebar determines the active nav item using `currentPath.startsWith(item.href)`. This can produce false positives if a future route shares a prefix with an existing route. For example, navigating to `/users-settings` would incorrectly highlight the `/users` link.

Current admin routes (`/apps`, `/orgs`, `/users`, `/roles`, `/permissions`) don't collide today, but the pattern is fragile and will silently break when new routes are added.

**Fix sketch.** Use boundary-aware matching:
```typescript
const isActive = currentPath === item.href || currentPath.startsWith(item.href + '/')
```

**Tests needed.** The existing e2e test (`admin-nav.spec.ts`) already asserts `data-active` values for all 5 routes. Add a unit test or extend the e2e test with a synthetic route that shares a prefix to validate the boundary logic.

## :yellow_circle: bug-0034 — SetUserRoles / SetUserDirectPermissions DTOs lack array size limits

**Fixed:** false
**Severity:** Warning
**Files:**
- `apps/auth-server/src/users/dto/set-user-roles.dto.ts` (lines 1-8)
- `apps/auth-server/src/users/dto/set-user-direct-permissions.dto.ts` (lines 1-8)

**Description.** Both DTOs validate `@IsArray()`, `@ArrayUnique()`, and `@IsString({ each: true })` but enforce no maximum array size. A malicious or buggy client can send thousands of role/permission IDs in a single request, causing:
1. An unbounded `findMany` query in `resolveAppScopedIds` (no `take` limit).
2. An unbounded `deleteMany` + `createMany` in the set-replace transaction.
3. Potential memory pressure and slow queries on the database.

Additionally, an empty array `[]` is valid and silently clears all roles or permissions for the user. While this may be intentional for "revoke all", there is no confirmation gate or audit distinction between "set to specific IDs" and "revoke all".

**Fix sketch.**
1. Add `@ArrayMaxSize(100)` (or a reasonable limit) to both DTOs.
2. If clearing is intentional, document it. If not, add `@ArrayMinSize(1)`.
3. Add `@ArrayMaxSize` to `resolvePermissionIdsForApp()` and `resolveRoleIdsForApp()` as a defense-in-depth check.

**Tests needed.** Integration test sending an array with 101 elements and verifying 400 response. Test sending `[]` and verifying the expected behavior (accept or reject).

## :large_blue_circle: bug-0035 — New user server actions repeat brittle string-matching error pattern (bug-0032 regression)

**Fixed:** false
**Severity:** Minor
**File:** `apps/admin/app/(admin)/users/actions.ts` (lines 58-88)

**Description.** `setUserRolesAction()` and `setUserDirectPermissionsAction()` map errors using `message.includes('403')` and `message.includes('400')`. This is the exact pattern that bug-0032 identified and fixed for the permissions and roles server actions by introducing `ApiError` with a numeric `status` property.

The new user actions were written after the bug-0032 fix landed but do not use the `ApiError` pattern. A 404 response is not handled and falls through to the generic error key.

**Fix sketch.** Apply the same `ApiError` status-code matching pattern from the bug-0032 fix:
```typescript
} catch (err) {
  if (err instanceof ApiError) {
    if (err.status === 403) return { errorKey: 'users.errors.forbidden' }
    if (err.status === 400) return { errorKey: 'users.errors.rolesSetFailed' }
    if (err.status === 404) return { errorKey: 'users.errors.notFound' }
  }
  return { errorKey: 'users.errors.rolesSetFailed' }
}
```

Also update `createUserAction` (lines 37-43) and `deleteUserAction` (lines 119-127) which still use the string-matching pattern.

**Tests needed.** Unit test each action with mocked 403/400/404 `ApiError` responses to verify correct error key mapping.

## :yellow_circle: bug-0036 — `getUserDirectPermissions()` returns empty `appId` string, losing app context

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/src/users/users.service.ts` (lines ~382-410)

**Description.** The `getUserDirectPermissions()` method maps each direct permission to `{ id, name, appId: '' }`. The empty string intentionally indicates that the current query path doesn't join through to the app table. However, this creates two problems:

1. **Data loss** — The frontend `Permission` type expects `appId: string` and cannot determine which app a direct permission belongs to. The admin UI's view drawer shows direct permissions without app context.
2. **Type confusion** — The service casts the Prisma result to `unknown` then to a hard-coded shape (with `appId: number`), then returns `appId: ''` (a string). The intermediate cast hides the mismatch.

**Fix sketch.** Include the app join in the Prisma query:
```typescript
directPermissions: {
  select: {
    permission: {
      select: {
        publicId: true,
        name: true,
        app: { select: { publicId: true } }
      }
    }
  }
}
```
Then return `appId: up.permission.app.publicId` instead of `appId: ''`.

**Tests needed.** Integration test verifying that `GET /users/:id/direct-permissions` returns permissions with non-empty `appId` values.

## :large_blue_circle: bug-0037 — `TRUSTED_ORIGINS` is not validated at startup

**Fixed:** false
**Severity:** Minor
**File:** `apps/auth-server/src/configure-nest-app.ts` (CORS configuration) and `apps/auth-server/src/auth/auth.config.ts`

**Description.** The `TRUSTED_ORIGINS` environment variable is read as a comma-separated string and split into an array. There is no validation that the resulting values are valid URLs. If the variable is empty, misspelled, or contains malformed entries (e.g., `localhost:3001` without the protocol), CORS silently rejects all cross-origin requests from the admin console. This produces opaque browser errors that are difficult to debug.

**Fix sketch.** Add validation at startup:
```typescript
const origins = TRUSTED_ORIGINS.filter(o => {
  try { new URL(o); return true; }
  catch { return false; }
});
if (origins.length === 0) {
  throw new Error('TRUSTED_ORIGINS must contain at least one valid URL');
}
```

**Tests needed.** Unit test for the validation logic with edge cases: empty string, missing protocol, trailing slash, valid URLs.
