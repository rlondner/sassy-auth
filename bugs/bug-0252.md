# bug-0252: Nested double-`asChild` on the row-action trigger (`TooltipTrigger asChild` → `DropdownMenuTrigger asChild` → one `<button>`) across all 5 tables

**Severity:** Minor (correctness / a11y — behavior fragility)
**Status:** Open
**Fixed:** false
**Introduced by:** PR #316 (`palette/accessible-table-tooltips-…`, Jules bot) — created 2026-08-13.

## Description

For the "more actions" (`more_vert`) trigger, PR #316 nests two Radix `asChild` Slots onto a
single button in every table:

```tsx
<Tooltip>
  <TooltipTrigger asChild>
    <DropdownMenuTrigger asChild onClick={(e) => e.stopPropagation()}>
      <button aria-label={t('common.moreActions')} /* … */>
        <span className="material-symbols-outlined text-[20px] …">more_vert</span>
      </button>
    </DropdownMenuTrigger>
  </TooltipTrigger>
  <TooltipContent side="top">{t('common.moreActions')}</TooltipContent>
</Tooltip>
```

Both `TooltipTrigger` and `DropdownMenuTrigger` are `asChild` Slots that each try to merge their
own props, refs, and event handlers onto the **same** child `<button>`. This is the
Radix-documented "composing a tooltip with another primitive" case, which requires care with
composition order and typically has known rough edges.

## Why this is a bug

1. **Tooltip may not dismiss when the menu opens.** With both triggers on one node, opening the
   dropdown does not reliably close the tooltip; users can see the "More actions" tooltip
   floating over an open menu, or the tooltip can re-open on focus return after the menu closes.
2. **Ref / event-handler merge is order-sensitive and easy to break.** Radix `Slot` composes
   handlers, but stacking two `asChild` Slots makes the merge fragile — a future refactor that
   reorders the wrappers or adds a second child can silently break `onClick`
   (`e.stopPropagation()` guarding the row-click) or ref forwarding.
3. **Untested.** The unit tests replace `TooltipTrigger`/`DropdownMenuTrigger` with passthrough
   stubs (see bug-0251), so the real nested-Slot composition is never exercised.

This is a **plausible, low-confidence robustness observation, not a confirmed defect** — Radix's
`Slot` does compose event handlers, and Tooltip-on-a-menu-trigger is a supported combination, so
it may well behave correctly. It is flagged for a runtime check, not asserted as broken. (The
tables render fine — a `TooltipProvider` is in scope via `SidebarProvider`; the earlier
[bug-0249](./bug-0249.md) crash claim was retracted.)

## Files

- `apps/admin/components/apps-table.tsx`, `orgs-table.tsx`, `roles-table.tsx`,
  `permissions-table.tsx`, `users-table.tsx` — row-action column cell

## Suggested fix

Follow the Radix guidance for tooltip-on-a-menu-trigger — wrap the `DropdownMenuTrigger` as the
tooltip's child without double-`asChild` on the raw button, e.g.:

```tsx
<Tooltip>
  <TooltipTrigger asChild>
    <DropdownMenuTrigger
      aria-label={t('common.moreActions')}
      onClick={(e) => e.stopPropagation()}
      className="flex h-7 w-7 items-center justify-center rounded hover:bg-muted"
    >
      <span className="material-symbols-outlined text-[20px] text-muted-foreground">more_vert</span>
    </DropdownMenuTrigger>
  </TooltipTrigger>
  <TooltipContent side="top">{t('common.moreActions')}</TooltipContent>
</Tooltip>
```

(i.e. let `DropdownMenuTrigger` render the button element itself rather than stacking a second
`asChild` onto a nested `<button>`), and add an integration test that opens the menu and asserts
the tooltip is gone.
