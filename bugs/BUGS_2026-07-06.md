### bug-0173 :yellow_circle: Warning — E2E `afterAll` cleanup commented out — test data leaks across runs

**Files:**
- `apps/auth-server/test/app.e2e-spec.ts:69-80` (commented-out cleanup)

**Fix:** Uncomment the `afterAll` cleanup queries at lines 70-79, or move the cleanup logic from the final `describe` into a proper `afterAll` hook at the suite level. Cleanup should not be an `it()` block.

### bug-0175 :yellow_circle: Warning — Social provider asymmetric env validation — app crashes if client ID set but client secret missing

**Files:**
- `apps/auth-server/src/auth/auth.config.ts:26-49`

**Description:** Social provider configuration uses a truthy check on the client ID (`process.env.GOOGLE_CLIENT_ID && { ... }`) but a non-null assertion (`!`) on the client secret (`clientSecret: process.env.GOOGLE_CLIENT_SECRET!`). If an operator sets `GOOGLE_CLIENT_ID` but forgets `GOOGLE_CLIENT_SECRET`, the config object is included (truthy ID) but the secret is `undefined` cast to `string` via `!`. The same pattern applies to Microsoft, Apple, and GitHub providers. The failure mode is either a crash deep inside BetterAuth's OAuth flow or a silent misconfiguration that produces opaque errors when users try to log in via social providers.

**Impact:** Production misconfiguration — setting a client ID without its secret produces a runtime crash or broken social login instead of a clear startup error. The asymmetric validation makes this easy to miss during deployment.

**Fix:** Either validate both ID and secret together:
```typescript
const googleId = process.env.GOOGLE_CLIENT_ID;
const googleSecret = process.env.GOOGLE_CLIENT_SECRET;
...(googleId && googleSecret && { google: { clientId: googleId, clientSecret: googleSecret } }),
```
Or throw a clear error at startup if ID is set but secret is missing.

**Fixed:** false

### bug-0179 :yellow_circle: Warning — Missing database indexes on BetterAuth `Session.userId`, `Account.userId`, and `Verification.identifier`

**Files:**
- `packages/db/schema.prisma:33` (`Session.userId` — no index)
- `packages/db/schema.prisma:41` (`Account.userId` — no index)
- `packages/db/schema.prisma:56` (`Verification.identifier` — no index)

**Description:** The BetterAuth-managed tables `Session`, `Account`, and `Verification` have foreign key and lookup columns without indexes. Prisma does NOT auto-create indexes on FK columns for PostgreSQL. BetterAuth queries sessions by `userId` on every session check (to list/invalidate sessions), queries accounts by `userId` during sign-in and token refresh, and looks up verifications by `identifier` (email) for magic link/OTP flows. All three queries fall back to sequential scans.

By contrast, the SassyAuth-managed tables have proper indexes: `SaUser` has `@@index([orgId])`, `@@index([username])`, and `@@index([phoneNumber])`.

**Impact:** Authentication performance degrades linearly with table size. As users, sessions, and accounts grow, every login, session validation, and magic link lookup becomes slower. The `Session` table is especially impactful — it is queried on every authenticated request via BetterAuth's session middleware.

**Fix:** Add to `schema.prisma`:
```prisma
model Session {
  // ... existing fields ...
  @@index([userId])
}

model Account {
  // ... existing fields ...
  @@index([userId])
}

model Verification {
  // ... existing fields ...
  @@index([identifier])
}
```
Then generate a migration: `pnpm --filter @sassy-auth/db db:migrate`.

**Fixed:** false

### bug-0183 :red_circle: Critical — `createPermission` allows `platform.*`-prefixed names — privilege escalation

**Files:**
- `apps/auth-server/src/permissions/permissions.service.ts:129-156`

**Description:** `createPermission` requires `platform.permissions.manage` but does NOT block callers from choosing a name starting with `platform.`. The `NAME_REGEX` in `CreatePermissionDto` (`/^[a-z][a-z0-9]*(\.[a-z][a-z0-9]+)+$/`) accepts names like `platform.users.manage` or `platform.anything.new`. A caller with `platform.permissions.manage` can create a new permission named `platform.X.Y`, then assign it to themselves or others, effectively minting arbitrary platform-level privileges.

This is the `createPermission` counterpart to already-known bug-0096 (which covers only `updatePermission` rename). The create path is arguably worse because it does not even need to start with an existing permission.

**Impact:** Privilege escalation — any admin with `platform.permissions.manage` can create and self-assign any platform permission, gaining full platform control. This bypasses the intended permission hierarchy.

**Fix:** Add a guard before the `$transaction` block:
```typescript
if (isPlatform(dto.name)) {
  throw new ForbiddenException('Cannot create permissions with the platform.* prefix');
}
```

**Fixed:** false

### bug-0184 :yellow_circle: Warning — `AcceptInvitationDto` has no `@MaxLength()` on password — hash-DoS on unauthenticated endpoint

**Files:**
- `apps/auth-server/src/invitations/dto/accept-invitation.dto.ts:7-14`

**Description:** The `password` field has `@MinLength(12)` and a regex pattern match, but no `@MaxLength()` constraint. The `hashPassword` function from BetterAuth uses scrypt, which is CPU/memory-intensive by design. An attacker can submit a multi-megabyte password string, causing the server to spend excessive time and memory hashing it. Since the invitation accept endpoint is unauthenticated (no `BetterAuthGuard` on `InvitationsController`), this is a viable denial-of-service vector.

Similar to bug-0169 (`CreateUserDto.email` no MaxLength) but more exploitable because password hashing is intentionally expensive and the endpoint requires no authentication.

**Impact:** Denial of service — an attacker with a valid invitation token (or who is brute-forcing tokens) can send a very large password, causing the server to spend seconds or minutes hashing it. Multiple concurrent requests amplify the effect.

**Fix:** Add `@MaxLength(256)` to the `password` field in `AcceptInvitationDto`.

**Fixed:** false

### bug-0188 :large_blue_circle: Minor — LIKE wildcard characters (`%`, `_`) not escaped in search `q` parameter across all list endpoints

**Files:**
- `apps/auth-server/src/apps/apps.service.ts:38`
- `apps/auth-server/src/orgs/orgs.service.ts:63`
- `apps/auth-server/src/roles/roles.service.ts:70`
- `apps/auth-server/src/permissions/permissions.service.ts:63`

**Description:** The search term `q` is passed directly to Prisma's `contains` filter, which translates to PostgreSQL `ILIKE '%...%'`. The `%` and `_` characters are LIKE wildcards. Sending `q=%` matches all records; `q=_` matches any single-character name. While the DTO caps length at 200 chars via `@MaxLength(200)`, the special characters still alter query semantics — a search for "100% complete" would match everything.

**Impact:** Search results return unexpected results when query contains `%` or `_`. Low severity since the endpoints are all authenticated and read-only.

**Fix:** Escape `%` and `_` before passing to the filter: `q.q.replace(/%/g, '\\%').replace(/_/g, '\\_')`.

**Fixed:** false
