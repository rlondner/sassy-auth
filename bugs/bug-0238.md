# bug-0238: `_to_delete/` accumulates tracked files in git history with no policy

**Severity:** Minor
**Status:** Open
**Fixed:** false

## Description

The `_to_delete/` directory holds files that are staged for eventual removal, but they
are **committed and tracked** rather than ignored:

```
$ git ls-files _to_delete/
_to_delete/CR_2026-07-09.md
```

`_to_delete/` is not listed in `.gitignore`, so every file dropped there is permanently
recorded in git history. "Files I plan to delete later" grow the repo indefinitely and
muddy `git log` / `git blame`. This was flagged in `code_reviews/CR_2026-07-09.md` and
again in `CR_2026-07-12.md` as an unresolved follow-up.

## Files

- `_to_delete/CR_2026-07-09.md` (tracked)
- `.gitignore` (missing `_to_delete/` entry)

## Fix

Pick one policy and apply it:

1. **Treat as a local scratchpad** — add `_to_delete/` to `.gitignore` and
   `git rm --cached -r _to_delete/` so the contents stop being tracked, or
2. **Actually delete** — `git rm -r _to_delete/` and remove the directory.

Option 1 is preferable if the workflow relies on a local staging area; otherwise option 2
keeps the tree clean. Document the choice so future automated runs don't re-add cruft.
