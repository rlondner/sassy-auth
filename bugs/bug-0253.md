# bug-0253: Native `title` copy tooltip never shows "Copied!" while the pointer stays on the button — PR #316's Radix→native rewrite defeats its own dynamic copy announcement

**Severity:** Minor (a11y / UX correctness)
**Status:** Open
**Fixed:** false
**Introduced by:** PR #316 (`palette/accessible-table-tooltips-…`, Jules bot) — revision `b3acc18` (force-pushed 2026-08-13 10:14 UTC, **after** the 2026-08-13 review read head `42a518d` at 09:07 UTC, so it was not covered by that review).

## Description

The original PR #316 wrapped the Sqid copy button in a Radix `<Tooltip>`/`<TooltipContent>`
whose content re-rendered reactively from the `copied` state (`content_copy` → `check`,
"Copy" → "Copied!"). Revision `b3acc18` replaced that with a **native `title` attribute** on
the same button in all 5 admin tables:

```tsx
// apps/admin/components/apps-table.tsx (and orgs/permissions/roles tables)
<button
  type="button"
  aria-label={copied ? t('common.copied') : t('common.copy')}
  title={copied ? t('common.copied') : t('common.copy')}
  onClick={(e) => { e.stopPropagation(); void copySqid(a.publicId, a.publicId) }}
  className="text-muted-foreground hover:text-primary"
>
  <span className="material-symbols-outlined text-[14px]">{copied ? 'check' : 'content_copy'}</span>
</button>
```

`copied` is reactive React state from `useCopyFeedback()` (`apps/admin/lib/use-copy-feedback.ts`)
that flips to `true` for ~2 s after a click, then clears.

## Why this is a bug

1. **The native `title` tooltip won't update while the pointer stays on the button.** Browsers
   sample the `title` attribute when the native tooltip is scheduled (on `mouseenter`/hover
   start) and do **not** re-open or update the already-shown tooltip when the attribute mutates
   under a stationary cursor. The normal interaction here is *hover the copy icon → click it*:
   the pointer never leaves, so the user keeps seeing **"Copy"** and never sees **"Copied!"**.
   They must move the pointer away and back to see the new title — by which time the 2 s window
   has usually elapsed and it reads "Copy" again. The dynamic confirmation is effectively dead.
2. **The `aria-label` toggle no longer announces either.** Mutating `aria-label` on a static
   (non-`aria-live`) element does not reliably trigger a screen-reader re-announcement, so SR
   users also lose the "copied" feedback that PR #316 explicitly set out to add (per its own
   title/body: *"a dynamic 'copied!' announcement"*).
3. **Net regression against the PR's stated goal.** The rewrite correctly moots the retracted
   provider concern ([bug-0249](./bug-0249.md)) and the nested-`asChild` fragility
   ([bug-0252](./bug-0252.md)) by dropping Radix Tooltip entirely — but in doing so it removes
   the reactive tooltip/aria feedback that was the point of the change. The only surviving copy
   confirmation is the icon swap (`content_copy` → `check`), which is fine as a fallback but is
   not what the PR advertised, and is invisible to assistive tech.

This is a **medium-confidence static finding** grounded in standard native-`title` behavior
(not runtime-verified in this exact build). The icon swap still works, so copy is not *broken* —
the tooltip/aria layer of the feature is.

## Files

- `apps/admin/components/apps-table.tsx`, `orgs-table.tsx`, `permissions-table.tsx`,
  `roles-table.tsx` — Sqid copy-button cell (reactive `title`/`aria-label` bound to `copied`)
- `apps/admin/components/users-table.tsx` — row-action `title` (static, not affected by this bug,
  but same native-`title` pattern)

## Suggested fix

Pick one:

- **Restore the Radix `<Tooltip>` for the copy button** (its content re-renders reactively; the
  `TooltipProvider` is in scope via `SidebarProvider`, so bug-0249 does not apply) — and keep the
  native `title` off, to avoid a double tooltip.
- **Or, if staying native:** bind `title` to a *static* `t('common.copy')` (never the transient
  state), keep the icon swap as the visible confirmation, and add a visually-hidden
  `aria-live="polite"` region that announces `t('common.copied')` on copy so SR users get the
  confirmation. Do **not** rely on mutating `title`/`aria-label` under a stationary pointer.

Add a test that asserts the "copied" confirmation is conveyed by something other than a mutated
`title` (icon state and/or an `aria-live` announcement).
