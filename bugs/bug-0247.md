# bug-0247: PR #306 bundles a second, divergent unfenced session-gate bypass (`SEEDING`) into a UI-only PR

**Severity:** Warning (security hardening / defense-in-depth)
**Status:** Open
**Fixed:** false
**Introduced by:** PR #306 (`jules-1582510711986125845-28989156`, Jules bot — "🎨 Palette: Interactive Show/Hide Password Toggle for LoginForm") — created 2026-08-05, not yet on `master`.

## Description

PR #306 is titled and scoped as a **login password show/hide toggle** UI change, but its diff
also edits production authentication code — the BetterAuth **session-create gate** — adding an
environment-variable short-circuit:

```ts
// apps/auth-server/src/auth/auth.config.ts
session: {
  create: {
    before: async (session: { userId: string }) => {
      if (process.env.SEEDING === '1') {
        return;                      // <-- gate skipped entirely
      }
      const gate = await evaluateSessionGate(prisma, session.userId);
      if (!gate.allowed) {
        // blocks non-active (pending/suspended/deleted) users from creating a session
        throw new APIError("FORBIDDEN", { message: "This account is not active." });
      }
    },
  },
},
```

The flag is set by the seed script at module load:

```ts
// apps/auth-server/src/seed/seed.ts:2
process.env.SEEDING = '1';
```

This is the **same defect already filed as [bug-0246](./bug-0246.md)** (PR #303's
`SEED_RUNNING === "true"` bypass) — reintroduced here under a **different variable name**
(`SEEDING === '1'`), still with **no `NODE_ENV` fence**, **no regression test**, and **no
documentation**.

## Why this is a bug

1. **Reintroduces the bug-0074 regression risk with no environment fence.** The account-status
   enforcement hardened in bug-0074 ("Inactive/pending users could authenticate", one of the
   original 9 Criticals) can be disabled process-wide by a single env var. `SEEDING=1` triggers
   the bypass regardless of `NODE_ENV`; if that variable ever leaks into a deployed shell, a
   container base image, or a CI job that also boots the server, suspended/pending/deleted
   accounts can mint sessions again — silently, with no log and no test to catch it.
2. **Two open PRs now carry divergent, incompatible bypasses.** PR #303 uses
   `SEED_RUNNING === "true"`; PR #306 uses `SEEDING === '1'`. Both edit the same
   `create.before` hook. Whichever merges second will conflict, and the surviving flag name is
   non-deterministic — an operator who sets one variable may believe the seed is safe while the
   merged code reads the other. This is a concrete **inconsistency**, not just a duplicate.
3. **Scope creep in a UI PR.** A "password toggle" PR has no business editing
   `auth.config.ts` and `seed/seed.ts`. Bundling an auth-security change under a cosmetic title
   defeats focused review — exactly how an unfenced production bypass slips in unnoticed. (The
   same PR also silently carries the bug-0243 test fix and an unrelated `fr.json` reformat; see
   [bug-0248](./bug-0248.md).)
4. **Undocumented.** Neither `SEEDING` nor `SEED_RUNNING` appears in `.env.example` or the
   README env reference, so the security significance is invisible to operators.

## Files

- `apps/auth-server/src/auth/auth.config.ts` — session `create.before` hook (the bypass)
- `apps/auth-server/src/seed/seed.ts:2` — sets `process.env.SEEDING = '1'`

## Suggested fix

Pick **one** canonical seed flag across #303/#306, fence it so it can never fire in a real
deployment, and make the intent explicit:

```ts
const SEED_BYPASS =
  process.env.SEEDING === '1' && process.env.NODE_ENV !== 'production';

before: async (session: { userId: string }) => {
  if (SEED_BYPASS) return;
  const gate = await evaluateSessionGate(prisma, session.userId);
  // ...
}
```

Better still, keep the seed out of the production auth path entirely — create the seed's
BetterAuth users through a dedicated seed-only adapter/instance, or insert the active `SaUser`
row before the session is created so the real gate passes on its own merits. Whatever the
approach, add:

- a regression test asserting the session gate **still runs** when `NODE_ENV=production` even if
  the seed flag is set, and
- a `SEEDING` entry in `.env.example` / README clearly marked *seed-internal — never set in a
  deployed environment*.

Coordinate the resolution of #303 and #306 so only one flag name survives.
