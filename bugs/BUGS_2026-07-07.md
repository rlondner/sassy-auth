### bug-0189 :yellow_circle: Warning — `signOutAction` crashes on auth-server outage — session cookie not cleared

**Files:**
- `apps/admin/app/(admin)/actions.ts:24-44`

**Description:** `signOutAction` calls `await fetch(AUTH_SERVER/api/auth/sign-out, ...)` with no try/catch. If the auth server is unreachable (network failure, DNS error, server down), `fetch()` throws. Execution aborts before `cookieStore.delete('better-auth.session_token')` on line 35, so the session cookie is never deleted and `redirect('/')` never fires. The user sees a 500 error and remains stuck with a stale session. By contrast, the `signIn` action in `login/actions.ts` correctly wraps its fetch in try/catch (lines 111-117).

**Impact:** Users cannot sign out when the auth server has any transient failure. They are stuck with a 500 error and must manually clear cookies.

**Fix:** Wrap the fetch in try/catch. On failure, still delete the local cookie and redirect — the server-side session will expire naturally:
```typescript
try {
  await fetch(`${AUTH_SERVER}/api/auth/sign-out`, { ... })
} catch (e) {
  Sentry.captureException(e)
}
cookieStore.delete('better-auth.session_token')
```

**Fixed:** false

### bug-0190 :yellow_circle: Warning — Five users server actions propagate unhandled exceptions — drawer/form crashes

**Files:**
- `apps/admin/app/(admin)/users/actions.ts:46-55` (`getUserRolesAction`, `getEffectivePermissionsAction`, `getUserDirectPermissionsAction`)
- `apps/admin/app/(admin)/users/actions.ts:90-104` (`getRolesAction`, `getAppPermissionsAction`)
- `apps/admin/components/user-view-drawer.tsx:84-89` (caller with no `.catch()`)
- `apps/admin/components/user-create-drawer.tsx:71-78` (caller with no `.catch()`)

**Description:** These five server actions are pass-through wrappers with zero error handling — no try/catch, unlike every other server action in the codebase. If any API call fails (403 forbidden, 404 deleted user, network error), the raw Error propagates. The callers in `UserViewDrawer` and `UserCreateDrawer` call these inside `Promise.all().then().finally()` but have no `.catch()`, so failures become unhandled promise rejections. The `.finally()` sets loading to false, but the UI shows empty data with no error indicator.

**Impact:** Opening a user drawer or switching orgs in the create-user form while the API is degraded produces silent failures — loading spinner disappears but no data is shown and no error feedback. Opening a drawer for a recently-deleted user crashes.

**Fix:** Add try/catch returning empty arrays on error, or add `.catch()` handlers in the client components that set an error state.

**Fixed:** false

### bug-0191 :yellow_circle: Warning — Admin Next.js app missing security headers and Cache-Control on authenticated pages

**Files:**
- `apps/admin/next.config.ts` (no `headers()` config)
- `apps/admin/middleware.ts:37-46` (no Cache-Control on authenticated responses)

**Description:** Neither the Next.js config nor the middleware sets any security response headers. The admin dashboard is missing `X-Frame-Options: DENY` (clickjacking protection), `X-Content-Type-Options: nosniff` (MIME sniffing), `Referrer-Policy`, and `Permissions-Policy`. Additionally, authenticated HTML pages containing sensitive admin data (user lists, org configs, permissions) have no `Cache-Control` headers — they could be cached by shared caches or the browser's bfcache. A user who signs out may still see cached admin pages via the browser back button.

Note: bug-0154 covers the auth-server's missing Helmet headers; this bug is about the admin Next.js app, which is a separate deployment.

**Impact:** The admin dashboard is vulnerable to clickjacking attacks and sensitive data may persist in browser cache after sign-out.

**Fix:** Add security headers via `next.config.ts` `headers()` function, and set `Cache-Control: no-store, no-cache, must-revalidate, private` on authenticated responses in middleware.

**Fixed:** false

### bug-0192 :yellow_circle: Warning — `DirectLoginDto` password field has no `@MaxLength` — scrypt DoS vector

**Files:**
- `apps/auth-server/src/token/dto/direct-login.dto.ts:1-17`

**Description:** The `DirectLoginDto.password` field has `@IsString()` + `@IsNotEmpty()` but no `@MaxLength()` constraint. The password verification uses scrypt (via BetterAuth), which is CPU/memory-intensive by design. An attacker can submit multi-megabyte password strings to the unauthenticated `POST /api/token/direct/login` endpoint, causing excessive CPU consumption per request. Related to bug-0184 (`AcceptInvitationDto` password no MaxLength) but this is a different endpoint and DTO.

**Impact:** Denial of service — an attacker can send very large passwords, causing seconds of scrypt computation per request. Multiple concurrent requests amplify the effect.

**Fix:** Add `@MaxLength(256)` to the `password` field. Also consider `@MaxLength(256)` on `identifier`.

**Fixed:** false

### bug-0193 :yellow_circle: Warning — No graceful shutdown hooks on auth-server — in-flight requests dropped on SIGTERM

**Files:**
- `apps/auth-server/src/main.ts:20-68`

**Description:** The `bootstrap()` function never calls `app.enableShutdownHooks()`. There are no `process.on('SIGTERM')` or `process.on('SIGINT')` handlers. When a container orchestrator sends SIGTERM, Node.js exits immediately, killing in-flight HTTP requests (including mid-OAuth token exchanges). NestJS lifecycle hooks (`OnModuleDestroy`, `OnApplicationShutdown`) never fire, so Prisma connection cleanup and Sentry flush are skipped.

**Impact:** Random 502/504 errors during deployments. OAuth flows mid-token-exchange get aborted. Sentry may lose buffered error reports. Prisma connections are not cleanly released.

**Fix:** Add `app.enableShutdownHooks()` after creating the Nest app in `main.ts`.

**Fixed:** false

### bug-0194 :yellow_circle: Warning — `ValidationPipe` missing `forbidNonWhitelisted: true` — unknown properties silently stripped

**Files:**
- `apps/auth-server/src/configure-nest-app.ts:18`

**Description:** The global `ValidationPipe` is configured with `{ whitelist: true, transform: true }` but NOT `forbidNonWhitelisted: true`. **Fix:** Add `forbidNonWhitelisted: true` to the `ValidationPipe` options.

### bug-0210 :large_blue_circle: Minor — `bootstrap()` called without `.catch()` — startup failures may exit silently

**Files:**
- `apps/auth-server/src/main.ts:68`

**Description:** `bootstrap()` is called with no `.catch()` handler and the file does not use top-level `await`. If bootstrap fails (database unreachable, port in use, missing env vars), the unhandled promise rejection may cause Node.js to exit with code 0 depending on the `--unhandled-rejections` flag. **Impact:** Operators get no signal that startup failed. The orchestrator won't restart the process.

**Fix:** Add `.catch()`:

```typescript
  console.error('Fatal: bootstrap failed', err);
  process.exit(1);
});
```
