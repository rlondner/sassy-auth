### bug-0131 :yellow_circle: Warning — `raceSuccessOrError` success text check is unscoped (page-wide match)

**Files:**
- `apps/admin-e2e/pages/apps.page.ts:77`
- `apps/admin-e2e/pages/orgs.page.ts:73`
- `apps/admin-e2e/pages/permissions.page.ts:72`
- `apps/admin-e2e/pages/roles.page.ts:72`
- `apps/admin-e2e/pages/users.page.ts:92`

**Description:** In the `raceSuccessOrError` helper across all 5 E2E page objects, the error detection was correctly scoped to `[data-sonner-toaster], [role="dialog"], [role="alertdialog"]` in commit `37f738a`. However, the **success** detection still uses a bare `page.getByText(successText)` — matching the text **anywhere on the page**, not just inside the Sonner toast container.

If the success text (e.g., "App created") also appears in the page body (a table cell, a heading, or a previously visible toast that hasn't auto-dismissed), the success race resolves immediately, creating a false positive. The asymmetry is also confusing: errors are scoped to toasts, but successes are not.

**Impact:** False positive test passes when the success text exists on the page before the mutation completes. More likely as toast messages use common entity names.

**Fix:** Scope the success check to the Sonner container:
```typescript
const success = page.locator('[data-sonner-toaster]')
  .getByText(successText)
  .waitFor({ state: 'visible', timeout: 10_000 })
  .then(() => 'success' as const)
  .catch(() => null)
```

**Fixed:** false

### bug-0132 :large_blue_circle: Minor — `user-create-drawer.tsx` uses raw error string instead of i18n key

**File:** `apps/admin/components/user-create-drawer.tsx:116-118`

**Description:** The user-create-drawer server error handling uses `result.error` (a raw English string from the server) instead of `result.errorKey` with `t()` for translation:
```typescript
if ('error' in result) {
  setServerError(result.error)  // raw English string
}
```
Every other drawer (apps, orgs, permissions, roles) checks `'errorKey' in result` and passes through `t(result.errorKey)` for i18n translation. This means server errors in the user-create flow appear untranslated in the French locale.

Additionally, client-side validation messages on lines 88-91 are hardcoded English (`'Required'`, `'Invalid email'`) instead of using `t()`.

**Impact:** Untranslated error messages for French users creating new users. Inconsistent error contract across drawers.

**Fix:** Change to `'errorKey' in result` pattern matching the other drawers, and replace hardcoded validation strings with `t('common.required')` / `t('common.invalidEmail')`.

**Fixed:** false

### bug-0133 :large_blue_circle: Minor — `roles.service.spec.ts` double-awaits `rejects` on same promise

**File:** `apps/auth-server/src/roles/roles.service.spec.ts:392-398`

**Description:** The `deleteRole` P2003 test awaits `.rejects` on the same promise reference twice:
```typescript
const promise = makeService().deleteRole('ba-caller', 'sq_r1');
await expect(promise).rejects.toBeInstanceOf(ConflictException);
await expect(promise).rejects.toMatchObject({ message: expect.stringContaining('3 users') });
```
The first `await expect(promise).rejects` consumes the rejection. The second `await` on the same already-settled promise may behave inconsistently across Jest versions — in some versions the rejection is replayed, in others it returns the cached rejection reason, and in edge cases it can swallow the assertion error.

**Impact:** Test could spuriously pass or fail depending on the Jest version. Currently works but is fragile.

**Fix:** Either use a single chained assertion, or invoke `makeService().deleteRole(...)` separately for each assertion:
```typescript
await expect(makeService().deleteRole('ba-caller', 'sq_r1')).rejects.toMatchObject({
  constructor: ConflictException,
  message: expect.stringContaining('3 users'),
});
```

**Fixed:** false

### bug-0134 :large_blue_circle: Minor — Permissions matrix missing `apps.get` operation

**File:** `apps/auth-server/test/matrix/permissions-matrix.ts:47-53`

**Description:** The `GATE` matrix's `apps` area defines four operations (`list`, `create`, `update`, `delete`) but omits `get`. The `orgs`, `roles`, and `permissions` areas all include a `get` operation. If an `apps.get` endpoint exists (and it does — `GET /api/apps/:id` is documented in the API Reference), it is not covered by the permission matrix E2E tests.

**Impact:** The `getApp` endpoint's permission check is not verified by the matrix test suite. If the auth guard on that endpoint is accidentally removed or weakened, no matrix test will catch it.

**Fix:** Add a `get` operation to the `apps` area in `permissions-matrix.ts`:
```typescript
apps: {
  list: { method: 'GET', path: '/api/apps' },
  get:  { method: 'GET', path: '/api/apps/:id' },
  create: { method: 'POST', path: '/api/apps' },
  update: { method: 'PATCH', path: '/api/apps/:id' },
  delete: { method: 'DELETE', path: '/api/apps/:id' },
},
```

**Fixed:** false

### bug-0135 :white_circle: Info — `user-create-drawer.tsx` stale role/permission IDs on org switch

**File:** `apps/admin/components/user-create-drawer.tsx:64-80`

**Description:** When the user changes the org dropdown in the user-create drawer, a `useEffect` refetches the available roles and permissions for the new org. However, the previously selected `roleIds` and `directPermissionIds` are **not cleared** when the org changes. If the user selects Org A, picks some roles, then switches to Org B, the role IDs from Org A persist in `form.roleIds` even though the role dropdown now shows Org B's roles. The stale IDs from Org A would be silently submitted to the server.

**Impact:** Potential assignment of wrong-org roles to a new user. The server may reject the IDs (if they belong to a different app scope), but the client provides no feedback about the mismatch. In the worst case, if the IDs happen to overlap (integer IDs shared across orgs), the wrong roles could be assigned.

**Fix:** Clear `roleIds` and `directPermissionIds` when `orgId` changes:
```typescript
useEffect(() => {
  set('roleIds')([])
  set('directPermissionIds')([])
  // ... rest of the effect
}, [orgId])
```

**Fixed:** false
