## New bugs (15)

### bug-0214 :red_circle: Critical — directLogin timing side-channel: org/app mismatch returns 403 before scrypt

**Files:**
- `apps/auth-server/src/token/token.controller.ts:384-387`

**Description:** The `directLogin` method throws `ForbiddenException(USER_ORG_MISMATCH)` at line 386 **before** password verification. The extensive timing-guard work for bug-0209 carefully equalizes the user-not-found and wrong-password paths with a dummy scrypt verify. However, the org/app mismatch check bypasses password verification entirely and returns a different HTTP status (403 vs 401) with a different error code. An attacker can enumerate valid user identifiers by sending login requests with a valid app ID from a different tenant: a user-not-found returns `401 INVALID_CREDENTIALS` (after ~100ms scrypt), while a valid-user-wrong-tenant returns `403 USER_ORG_MISMATCH` instantly.

**Impact:** Defeats the timing guard (bug-0209) for cross-tenant probing. Allows user enumeration AND tenant-membership oracle — an attacker can confirm which users belong to which tenants.

**Fix:** Move the org/app mismatch check to **after** password verification, and return `INVALID_CREDENTIALS` (not `USER_ORG_MISMATCH`) to make the response indistinguishable.

**Fixed:** true

### bug-0215 :red_circle: Critical — directLogin timing side-channel: social-only users skip scrypt

**Files:**
- `apps/auth-server/src/token/token.controller.ts:396-402`

**Description:** When a user exists but has no credential-provider `account` row (e.g., social-only Google/GitHub login), the code throws `INVALID_CREDENTIALS` immediately without calling `verifyPassword`. Scrypt verification takes measurable time (tens to hundreds of ms). This timing difference lets an attacker distinguish "user exists with password auth" from "user exists with social-only auth" — leaking the authentication method.

**Impact:** Authentication method enumeration. An attacker can determine which accounts use password vs. social login, enabling targeted phishing (e.g., crafting a fake Google sign-in only for users known to use Google).

**Fix:** Add a dummy `verifyPassword` call before throwing when no credential row exists, matching the pattern already used for user-not-found.

**Fixed:** true

### bug-0216 :yellow_circle: Warning — Post-login OAuth redirect path missing `/api/token` prefix — always rejected

**Files:**
- `apps/auth-server/src/token/token.controller.ts:181`

**Description:** The `nextPath` for the bug-0149 post-login redirect is built as `${OAUTH_AUTHORIZE_ROUTE}?...` which evaluates to `oauth/authorize?client_id=...`. This lacks both the global prefix (`api`) and the controller path (`token`), producing a relative path without a leading `/`. The admin app's `validateNextUrl()` in `lib/safe-next.ts` rejects paths that don't start with `/` and URLs that fail `new URL()` parsing. The user is dumped at `/users` after login instead of being redirected back to the OAuth authorize flow.

**Impact:** The bug-0149 post-login redirect to the OAuth flow is completely non-functional. Users authenticating via OAuth must restart the flow after logging in.

**Fix:** Build the full path: `/${NEST_GLOBAL_PREFIX}/${TOKEN_CONTROLLER_PATH}/${OAUTH_AUTHORIZE_ROUTE}?${query.toString()}`

**Fixed:** false

### bug-0217 :yellow_circle: Warning — Helmet CSP blocks Swagger UI in development

**Files:**
- `apps/auth-server/src/configure-nest-app.ts:21-25`

**Description:** `helmet()` is applied unconditionally with its default Content-Security-Policy (which blocks inline scripts/styles). Swagger UI relies on inline scripts and styles. The code comment claims "the strict CSP is only in effect in prod, where Swagger UI isn't mounted" — this is incorrect. Helmet is applied in ALL environments; Swagger UI is mounted in all NON-production environments. Result: Swagger UI renders as a blank page with CSP violations in dev.

**Impact:** Developers cannot use Swagger UI for API exploration in development or staging. The misleading comment may delay diagnosis.

**Fix:** Disable Helmet's CSP in non-production: `app.use(helmet({ contentSecurityPolicy: process.env.NODE_ENV === 'production' }))`

**Fixed:** false

### bug-0218 :yellow_circle: Warning — updateUser status guard bypass: pending→inactive→active circumvents invitation

**Files:**
- `apps/auth-server/src/users/users.service.ts:313`

**Description:** The bug-0152 status transition guard only blocks `pending → active`. An admin can bypass it in two steps: (1) set a `pending` user to `inactive`, (2) set the now-`inactive` user to `active`. The `pending → active` guard never fires because the intermediate state is `inactive`. The user becomes active without ever accepting an invitation or setting a password.

**Impact:** Circumvents the invitation-acceptance requirement. An admin (even org-level) can activate a user who has no password credential, creating an account that cannot log in via direct login but may receive tokens through other flows.

**Fix:** Guard all transitions to `active` that don't come from `active` itself. Only `inactive → active` (reactivation) should be allowed; `pending → active` by any path should be blocked.

**Fixed:** false

### bug-0219 :yellow_circle: Warning — updateUser missing self-modification guard

**Files:**
- `apps/auth-server/src/users/users.service.ts:298-337`

**Description:** `deleteUser`, `setUserRoles`, and `setUserDirectPermissions` all guard against self-modification with `if (user.betterAuthUserId === callerBaId)`. `updateUser` has no such guard. An admin can change their own `status` to `inactive`, locking themselves out and causing operational disruption.

**Impact:** Self-lockout risk. An org-level admin could accidentally or maliciously deactivate their own account.

**Fix:** Add a self-modification check for the `status` field: `if (dto.status !== undefined && existing.betterAuthUserId === callerBaId) throw new ForbiddenException('...')`

**Fixed:** false

### bug-0220 :yellow_circle: Warning — Expired SaOauthCode rows accumulate unboundedly

**Files:**
- `apps/auth-server/src/token/oauth.service.ts` (no cleanup)
- `packages/db/schema.prisma:234` (explicit comment acknowledging this)

**Description:** The fix for bug-0039 moved OAuth authorization codes from an in-memory Map to the `SaOauthCode` database table. Expired codes (5-minute TTL) from abandoned OAuth flows are never deleted. The exchange path correctly rejects expired codes, but stale rows accumulate indefinitely. The schema comment explicitly acknowledges this: "periodic cleanup job is optional (not shipped in v1)."

**Impact:** Unbounded table growth. At thousands of OAuth starts per day, millions of stale rows would accumulate, degrading insert performance and wasting storage. Supersedes bug-0040 (memory leak) and bug-0073 (memory purge), which are now resolved by the DB migration.

**Fix:** Add a scheduled cleanup: `prisma.saOauthCode.deleteMany({ where: { expiresAt: { lt: new Date() } } })` on a 15-minute cron or NestJS `@Cron` decorator.

**Fixed:** true

### bug-0221 :yellow_circle: Warning — updateUserAction lacks try/catch; swallows NEXT_REDIRECT sentinel

**Files:**
- `apps/admin/app/(admin)/users/actions.ts:141-145`
- `apps/admin/components/user-view-drawer.tsx:165`

**Description:** `updateUserAction` is the only mutating server action without try/catch — it lets exceptions propagate directly. The caller in `user-view-drawer.tsx` (line 165) wraps it in `.catch()`, producing `{ ok: false, error: e.message }`. When the auth-server session expires mid-edit, `apiFetch` throws a `redirect('/login')` sentinel (a Next.js NEXT_REDIRECT error). The drawer's `.catch()` swallows this sentinel, preventing the 401 redirect and instead showing a generic error toast. Related to bug-0061 (first reported 2026-06-06), but adds the redirect-sentinel dimension introduced by the recent bug-0136 fix.

**Impact:** Expired sessions during profile edits show a generic error toast instead of redirecting to `/login`. The user is stuck on a non-functional page.

**Fix:** Add try/catch to `updateUserAction` that re-throws NEXT_REDIRECT errors and returns a structured result for other errors, matching sibling actions.

**Fixed:** true

### bug-0222 :yellow_circle: Warning — user-view-drawer initial-load effect lacks cancellation flag

**Files:**
- `apps/admin/components/user-view-drawer.tsx:78-91`

**Description:** The initial-load `useEffect` (lines 78-91) fetches roles, permissions, and direct permissions via `Promise.all().then().finally()` without a cancellation flag. The permission-view-drawer and role-view-drawer both implement `let cancelled = false` with cleanup returns (fixed in bug-0145), but the user-view-drawer was missed. Rapid drawer open/close can cause user A's data to overwrite user B's displayed data.

**Impact:** Race condition showing incorrect access data for the wrong user in the admin console. An admin could see user A's roles/permissions while looking at user B, leading to incorrect access decisions.

**Fix:** Add `let cancelled = false` and `return () => { cancelled = true }` matching the pattern in the sibling drawers.

**Fixed:** false

### bug-0223 :large_blue_circle: Minor — Admin security headers missing HSTS

**Files:**
- `apps/admin/next.config.ts:18-23`

**Description:** The SECURITY_HEADERS array includes X-Frame-Options, X-Content-Type-Options, Referrer-Policy, and Permissions-Policy but omits `Strict-Transport-Security`. Without HSTS, a user typing `http://admin.example.com` is not automatically upgraded to HTTPS, enabling SSL-stripping attacks.

**Impact:** Protocol downgrade risk in production. The middleware already sets Cache-Control for authenticated pages, but HSTS is the standard defense against SSL-stripping.

**Fix:** Add `{ key: 'Strict-Transport-Security', value: 'max-age=63072000; includeSubDomains' }` to SECURITY_HEADERS, gated behind a production check in middleware if the app also runs over HTTP in dev.

**Fixed:** false
