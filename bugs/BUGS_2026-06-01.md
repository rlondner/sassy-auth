## :red_circle: bug-0024 — Missing org/tenant isolation in `PermissionsService`

**Fixed:** true (commit `f8cb355`, merged to master via `feat/test-coverage-campaign`)
**Severity:** Critical
**File:** `apps/auth-server/src/permissions/permissions.service.ts` (lines 47, 93, 121, 150, 181)

**Description.** Every method in `PermissionsService` gates access with `checkPermission(callerBaId, 'platform.permissions.manage')` but never passes `targetOrgId`. The `checkPermission` helper supports org-scoped checks — when `targetOrgId` is supplied, it verifies the caller holds the permission within that org's scope. Without it, **any caller holding `platform.permissions.manage` (or an org-scoped equivalent) can list, create, update, and delete permissions across all organizations and apps**, violating tenant isolation.

This is the same class of bug as bug-0001 (RBAC isolation broken in `checkPermission`) but specific to the new permissions CRUD surface added in commit `7f966df`.

**Fix sketch.**
1. When the operation targets a specific permission, resolve the permission's `appId` to the owning org.
2. Pass `{ targetOrgId: app.orgId }` to `checkPermission`.
3. For `listPermissions`, if an `appId` filter is provided, scope the check to that app's org; if no filter, require `platform.permissions.manage` (platform-only).

**Tests needed.** Integration test where an org-admin with `org.permissions.manage` for Org A attempts to read/mutate a permission belonging to Org B and receives 403.

## :red_circle: bug-0025 — Missing org/tenant isolation in `RolesService`

**Fixed:** true (commit `072ad5b`, merged to master via `feat/test-coverage-campaign`)
**Severity:** Critical
**File:** `apps/auth-server/src/roles/roles.service.ts` (lines 118, 160, 207)

**Description.** Same class of bug as bug-0024, applied to the roles CRUD surface expanded in commit `379a1db`. All mutating operations (`createRole`, `updateRole`, `deleteRole`) check `platform.permissions.manage` without passing `targetOrgId`. Read operations (`listRoles`, `getRole`) check `['platform.permissions.manage', 'org.permissions.manage']` but also without org scoping.

A caller with `org.permissions.manage` in Org A can create, update, and delete roles in any app across any org.

**Fix sketch.** Same as bug-0024 — resolve the target role's `appId` to its owning org, pass `targetOrgId` to `checkPermission`.

**Tests needed.** Same pattern as bug-0024 — cross-org role mutation should be rejected.

## :yellow_circle: bug-0026 — Permission `name` unique constraint is global, not per-app

**Fixed:** true (commit `77fab18`, merged to master via `feat/test-coverage-campaign`)
**Severity:** Warning
**File:** Prisma schema — `SaPermission` model (currently `name String @unique`)

**Description.** The `SaPermission` model declares `name` as globally `@unique`. This prevents two different apps from having a permission with the same name (e.g., both apps want `users.read`). The code in `PermissionsService.createPermission` catches Prisma P2002 and returns "Permission name already exists", but this fires even when the duplicate is in a completely different app — which is almost certainly unintended for a multi-tenant system.

**Fix sketch.** Change the schema constraint from `name String @unique` to:
```prisma
@@unique([appId, name])
```
Then create a migration. The `PermissionsService` P2002 catch already handles this gracefully.

**Tests needed.** Test that creating `users.read` in App A succeeds, then creating `users.read` in App B also succeeds, but creating `users.read` in App A again returns 409.

## :yellow_circle: bug-0027 — Role `name` has no unique constraint (missing `@@unique([appId, name])`)

**Fixed:** true (commit `dfc8ac7`, merged to master via `feat/test-coverage-campaign`)
**Severity:** Warning
**File:** Prisma schema — `SaRole` model

**Description.** The `SaRole` model has no uniqueness constraint on `name` at all (only `publicId` is globally unique). The code in `RolesService.createRole` and `updateRole` catches P2002 and returns "Role name already exists", but since there's no DB-level constraint on `(appId, name)`, the P2002 can only fire on `publicId` collisions. Two roles with the exact same name can be created in the same app without error.

**Fix sketch.** Add to the Prisma schema:
```prisma
@@unique([appId, name])
```
Then create a migration.

**Tests needed.** Attempt to create two roles with the same name in the same app; second should return 409.

## :yellow_circle: bug-0028 — Admin UI type narrowing uses weak `'publicId' in res` check

**Fixed:** true (commit `88f9ec1`, merged to master via `feat/test-coverage-campaign`)
**Severity:** Warning
**Files:**
- `apps/admin/components/permission-view-drawer.tsx:35`
- `apps/admin/components/role-view-drawer.tsx:33`
- `apps/admin/components/role-edit-drawer.tsx:46`

**Description.** These drawer components check whether an API response is a success or error by testing `if ('publicId' in res)`. If an error response ever includes a `publicId` field (e.g., a validation error that echoes back the submitted data), this guard would incorrectly treat it as success, potentially rendering garbage data.

**Fix sketch.** Invert the check to test for the error shape first:
```ts
if ('errorKey' in res) { setError(t(res.errorKey)); return; }
setDetail(res);
```
This is the safer pattern already used in some other drawers.

**Tests needed.** Unit test rendering the drawer with a mock error response that includes a `publicId` field alongside `errorKey`.

## :large_blue_circle: bug-0029 — Role names have no input validation in admin UI

**Fixed:** true (commit `ba66b80`, merged to master via `feat/test-coverage-campaign`)
**Severity:** Minor
**Files:**
- `apps/admin/components/role-create-drawer.tsx` (lines 94-101)
- `apps/admin/components/role-edit-drawer.tsx`

**Description.** Permission names are validated with `NAME_REGEX = /^[a-z][a-z0-9]*(\.[a-z][a-z0-9]+)+$/` before submission in the create and edit drawers. Role names have no validation regex at all — any string (including empty after trim, or strings with special characters) can be submitted. While the backend DTOs have `@MinLength(1)`, they don't enforce a naming convention, so inconsistent role names can be created.

**Fix sketch.** Add a role-name validation regex (e.g., 1-100 alphanumeric + spaces + hyphens) to the admin UI drawers. Consider also adding `@Matches()` to the backend DTO.

**Tests needed.** Attempt to create a role with special characters; UI should reject before submission.

## :large_blue_circle: bug-0030 — Delete buttons use `data-disabled` instead of `disabled`, breaking keyboard a11y

**Severity:** Minor
**Files:**
- `apps/admin/components/permissions-table.tsx:147`
- `apps/admin/components/roles-table.tsx:138-139`

## :large_blue_circle: bug-0031 — Matrix test cleanup queue is module-scoped, never reset between test files

**Fixed:** true (commit `b0ae4d2`, merged to master via `feat/test-coverage-campaign`)
**Severity:** Minor
**File:** `apps/auth-server/test/matrix/factories.ts` (lines 10-26)

**Description.** The `queue` array and `drainCleanup()` function are module-scoped singletons. When multiple matrix spec files (`apps.matrix.e2e-spec.ts`, `orgs.matrix.e2e-spec.ts`, etc.) import from the same module, they share the same cleanup queue. If tests run in band (Jest default for e2e), cleanup callbacks from one spec file can leak into the next. The session cookie cache in `harness.ts` has the same issue — it's module-scoped and only cleared on `closeApp()`.

Additionally, cleanup errors are silently swallowed (line 25: empty `catch {}`), making orphaned test data invisible.

**Fix sketch.**
1. Export a `resetCleanup()` function that empties the queue; call it in `beforeAll` of each spec.
2. Clear the session cookie cache between spec files.
3. Log cleanup failures at DEBUG level instead of swallowing silently.
4. Consider running matrix specs with `--runInBand` and documenting this requirement.

**Tests needed.** N/A — test infrastructure fix.

## :large_blue_circle: bug-0032 — Error mapping in admin server actions uses brittle string matching

**Fixed:** true (commit `989f005`, merged to master via `feat/test-coverage-campaign`)
**Severity:** Minor
**Files:**
- `apps/admin/app/(admin)/permissions/actions.ts` (lines 16-29)
- `apps/admin/app/(admin)/roles/actions.ts` (lines 15-26)

**Description.** Server actions map API errors to i18n keys by checking `message.includes('409')`, `message.includes('403')`, etc. The error messages come from `apiFetch()` in `lib/api.ts` which formats them as `"API error ${res.status}: ${path}"`. If the error message format changes (e.g., adding a JSON body), the substring match will silently break and all errors will fall through to the generic `unknownError` key.

**Fix sketch.** Throw a typed error from `apiFetch` that carries the HTTP status code as a numeric property:
```ts
class ApiError extends Error {
  constructor(public status: number, path: string) {
    super(`API error ${status}: ${path}`);
  }
}
```
Then match on `error.status` instead of string contents.

**Tests needed.** Unit test for each server action with a mocked 409/403/404 response to verify correct error key mapping.
