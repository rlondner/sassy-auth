### bug-0239 :yellow_circle: Warning — French locale regressed to English for user CRUD toasts and the "Resend" action

**Files:**
- `apps/admin/messages/fr.json:404` (`users.actions.resend`)
- `apps/admin/messages/fr.json:407-410` (`users.toast.created`, `.updated`, `.deleted`, `.resent`)

**Description:** Five user-facing strings in the **French** message catalog contain the
**English** copy instead of a translation:

| key | `fr.json` value (wrong) | should be (approx.) |
|-----|-------------------------|---------------------|
| `users.actions.resend` | `"Resend Invitation"` | `"Renvoyer l’invitation"` |
| `users.toast.created` | `"User created"` | `"Utilisateur créé"` |
| `users.toast.updated` | `"User updated"` | `"Utilisateur mis à jour"` |
| `users.toast.deleted` | `"User deleted"` | `"Utilisateur supprimé"` |
| `users.toast.resent` | `"Invitation resent"` | `"Invitation renvoyée"` |

The adjacent keys (`resetLinkGenerated`, `activated`, `deactivated`) *are* correctly
translated, so this is a partial-translation slip introduced with the user-lifecycle
actions feature (`6ca2d12`, 2026-07-09) — the same class of defect previously fixed under
**bug-0112** (`fix/bug-0112-french-toast-i18n`). A French operator creating, updating,
deleting, or re-inviting a user sees an English toast.

**Impact:** Broken localization on the primary admin CRUD path for `fr` users; regression
of a previously-fixed bug class.

**Fix:** Translate the five strings in `fr.json`. Add a lightweight test/lint that fails
when a `fr.json` leaf value is byte-identical to its `en.json` counterpart for the
`users.toast.*` / `users.actions.*` subtrees (would have caught both this and bug-0112).

**Fixed:** false

### bug-0240 :large_blue_circle: Minor — `TWO_FACTOR_TRUST_DAYS` is an operative config var but is undocumented in `.env.example`

**Files:**
- `apps/admin/lib/two-factor-prompt.ts:23-28` (`getSystemTrustDaysClient` reads `process.env['TWO_FACTOR_TRUST_DAYS']`)
- `.env.example` (missing the key; only `PLATFORM_REQUIRE_2FA` is listed under "2FA / Security")

**Description:** The 2FA "trust this device / don't re-prompt" window is configurable via
`TWO_FACTOR_TRUST_DAYS` (consumed at `login/actions.ts:213,330` and
`login/two-factor/page.tsx:14`). The value materially changes how often users are asked to
set up / re-confirm 2FA, yet it is **absent from `.env.example`** and from the README
Environment-Variables tables — only the sibling `PLATFORM_REQUIRE_2FA` was added. Operators
cannot discover the knob; the code silently falls back to `14` for any missing/invalid
value, so a misconfigured deployment looks fine while ignoring intent.

**Impact:** Undiscoverable configuration; silent divergence between intended and actual 2FA
re-prompt cadence.

**Fix:** Add `TWO_FACTOR_TRUST_DAYS` (with the default-14 note) to `.env.example` under the
existing "2FA / Security" block and to the README Environment-Variables section. (README
side addressed in the 2026-07-20 review commit.)

**Fixed:** false

### bug-0241 :large_blue_circle: Minor — OTP request-step error renders an untranslated raw key ("invalidCredentials")

**Files:**
- `apps/admin/app/login/actions.ts:180` (`requestOtp` returns `{ error: 'invalidCredentials' }`)
- `apps/admin/app/login/login-otp-form.tsx:38-39` (`errKey` allowlist)

**Description:** `requestOtp` returns `{ error: 'invalidCredentials' }` when the email field
is empty, but the OTP form's `errKey` helper only maps `invalidCode | inactive |
serverUnavailable` through `t()`. Any other value — including `invalidCredentials` — is
rendered **verbatim**, so the user would see the literal string `invalidCredentials` rather
than a localized message. Separately, `"Invalid email or password."` is the wrong copy for
a **passwordless** flow (there is no password on this screen).

**Impact:** Untranslated developer-facing key leaks to the UI on the code-login screen;
misleading error copy for the passwordless path. (The browser-level `required` attribute
usually prevents the empty-email trigger, but a server action can still be invoked directly
and the `errKey` fall-through is a latent defect.)

**Fix:** Introduce a passwordless-appropriate key (e.g. `error.emailRequired`) and include
it — plus any other value `requestOtp` can return — in the `errKey` allowlist so no raw key
reaches the DOM.

**Fixed:** false

### bug-0242 :large_blue_circle: Minor — Dead i18n key `login.otp.resend`; no "resend code" control is wired in the OTP form

**Files:**
- `apps/admin/messages/en.json:472` and `apps/admin/messages/fr.json:472` (`login.otp.resend`)
- `apps/admin/app/login/login-otp-form.tsx:92-98` (renders only "change email", no resend)

**Description:** Both message catalogs define `login.otp.resend` ("Resend code" /
"Renvoyer le code"), but `login-otp-form.tsx` never references it — the code step offers
only a "Use a different email" button. A user whose emailed code never arrives (spam,
delivery delay, the silent `skipped_*` paths in `otp-sender.ts`) has **no resend path**
short of navigating back and re-entering their email. The translation key is dead weight
that implies a feature the UI does not provide.

**Impact:** Missing recovery affordance on the passwordless sign-in screen; orphaned
translation keys (maintenance noise / false implication of a shipped feature).

**Fix:** Either wire a "Resend code" button that re-submits `requestOtp` (ideally rate-limit
aware, since BetterAuth caps at 5/60s), or remove the `login.otp.resend` keys from both
catalogs until the control exists.

**Fixed:** false

credential-leak defects were found in the 2FA feature.** The security-sensitive parts hold
up: the session-less `verifyUserTotp` on the direct/login path is fail-closed (no row →

observations (rate-limit is per-process only; direct-login throttle vs BetterAuth-endpoint
parity; the duplicated `shouldPromptTwoFactor` server/client copies) are recorded in
`todo/TODO_2026-07-20.md`, not filed as bugs.
