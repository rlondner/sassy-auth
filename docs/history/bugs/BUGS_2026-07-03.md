### bug-0136 :yellow_circle: Warning — `apiFetch` doesn't handle HTTP 401 (session expiry) — cryptic errors instead of login redirect

**File:** `apps/admin/lib/api.ts:18`

**Description:** The `apiFetch` function throws a generic `Error("API error ${res.status}: ${path}")` for all non-OK responses, including HTTP 401. When a user's BetterAuth session expires mid-use, every server action that calls `apiFetch` throws "API error 401" shown as an error toast. The user sees cryptic error messages on every action and must manually navigate to `/login`. No special handling redirects the user to the login page.

**Impact:** Users with expired sessions see confusing "API error 401" messages on every admin action. They must discover on their own that they need to re-login, degrading the user experience significantly.

**Fix:** Check for 401 in `apiFetch` and redirect to `/login`:
```typescript
if (res.status === 401) {
  redirect('/login');
}
```

### bug-0137 :yellow_circle: Warning — Table search/filter useEffects lack request cancellation — stale responses overwrite newer data

**Files:**
- `apps/admin/components/apps-table.tsx:39-49`
- `apps/admin/components/orgs-table.tsx:39-55`
- `apps/admin/components/permissions-table.tsx:39-54`
- `apps/admin/components/roles-table.tsx:44-59`

**Description:** All four table components use a `useEffect` with a 300ms debounced `setTimeout` to fetch list data when `query`, `page`, or `pageSize` changes. The cleanup function clears the timeout, but if the timeout has already fired and the `await list*Action()` call is in-flight, a subsequent dependency change creates a new effect without cancelling the previous request. When the old request resolves after the new one, it overwrites `data` with stale results.

The `role-create-drawer.tsx` (line 44) and `role-edit-drawer.tsx` correctly use a `cancelled` flag pattern for their fetch effects, but the four table components do not.

**Impact:** When a user types quickly in the search box (e.g., "abc" then "abcd"), if the "abc" response returns after the "abcd" response, the table shows results for "abc" while the search box reads "abcd". More likely on slow networks.

**Fix:** Add a `cancelled` flag to the effect:
```typescript
React.useEffect(() => {
  let cancelled = false
  const timer = setTimeout(async () => {
    const result = await listAppsAction({ q: query || undefined, page, pageSize })
    if (!cancelled && result && 'items' in result) setData(result)
  }, 300)
  return () => { cancelled = true; clearTimeout(timer) }
}, [query, page, pageSize])
```

**Fixed:** false

### bug-0138 :yellow_circle: Warning — `removeRole` unhandled Prisma P2025 causes 500 on non-existent assignment

**File:** `apps/auth-server/src/users/users.service.ts:381`

**Description:** The `removeRole` method calls `prisma.saUserRole.delete()` with the compound key `userId_roleId` but has no try-catch for the Prisma `P2025` error (RecordNotFoundError) that is thrown when the row does not exist. Every other delete path in the codebase handles this — `assignRole` catches `P2002`, `deleteOrg`/`deleteRole`/`deletePermission` catch `P2003`.

**Impact:** When an admin removes a role from a user who doesn't actually have that role (e.g., concurrent removal by another admin, or a stale request), the server returns a raw 500 Internal Server Error with a Prisma stack trace, leaking implementation details.

**Fix:** Wrap the delete in try-catch:
```typescript
try {
  await prisma.saUserRole.delete({
    where: { userId_roleId: { userId: user.id, roleId: role.id } },
  });
} catch (e: unknown) {
  if (e instanceof Prisma.PrismaClientKnownRequestError && e.code === 'P2025') {
    throw new NotFoundException('Role is not assigned to this user');
  }
  throw e;
}
```

**Fixed:** false

### bug-0139 :yellow_circle: Warning — `resendInvitation` expire + create is non-atomic — partial failure orphans user

**File:** `apps/auth-server/src/users/users.service.ts:536-547`

**Description:** `resendInvitation` first expires all existing unused invitation tokens (`updateMany`, line 536) and then creates a new token (`create`, line 545) as two separate Prisma calls outside of a `$transaction`. The `acceptInvitation` method correctly uses `$transaction`, but `resendInvitation` does not.

**Impact:** If the `create` fails after the `updateMany` succeeds (e.g., transient DB error, publicId collision), all existing tokens are expired but no new valid token exists. The user is stuck in `pending` status with zero usable tokens. An admin would need to notice and retry, but nothing in the response or logs makes this partial-failure state obvious.

**Fix:** Wrap both operations in `$transaction`:
```typescript
const invitation = await prisma.$transaction(async (tx) => {
  await tx.saInvitation.updateMany({
    where: { userId: user.id, usedAt: null },
    data: { expiresAt: new Date(0) },
  });
  return tx.saInvitation.create({
    data: { publicId, token, userId: user.id, expiresAt },
  });
});
```

**Fixed:** false

### bug-0140 :yellow_circle: Warning — `listUsers` returns unbounded results with no pagination

**File:** `apps/auth-server/src/users/users.service.ts:79`

**Description:** `listUsers` calls `prisma.saUser.findMany({ where, include: USER_INCLUDE })` with no `take` or `skip` parameters. Every other list endpoint in the codebase (`listApps`, `listOrgs`, `listRoles`, `listPermissions`) implements pagination with default `pageSize: 25`. The users endpoint returns ALL matching rows in a single response.

**Impact:** In production with thousands of users, a `platform.users.manage` holder listing without filters returns every user across every org, causing high memory usage, slow responses, and potential client-side rendering failures.

**Fix:** Add `page` and `pageSize` parameters matching the pattern used by `listOrgs`/`listRoles`:
```typescript
const page = filters.page ?? 1;
const pageSize = filters.pageSize ?? 25;
const [users, total] = await Promise.all([
  prisma.saUser.findMany({ where, include: USER_INCLUDE, skip: (page - 1) * pageSize, take: pageSize }),
  prisma.saUser.count({ where }),
]);
return { items: users.map(formatUser), total, page, pageSize };
```

**Fixed:** false

**Files:**

- `apps/admin/components/org-edit-drawer.tsx:35-39`

**Description:** Unlike their create-drawer counterparts (which check `!name.trim()`), the edit drawers have no validation that `name.trim()` is non-empty before submission. A user can clear the name field, type a space, and submit. The HTML `required` attribute prevents fully empty submission, but a single space bypasses native validation and `name.trim()` produces `""`.

The `AppCreateDrawer` correctly checks `if (!name.trim())` and `if (!url.trim())`, but `AppEditDrawer` does not. The `OrgCreateDrawer` correctly checks `if (!name.trim())`, but `OrgEditDrawer` does not.

**Impact:** Empty app name or org name could be persisted if the backend does not independently validate, corrupting the entity record.

**Fix:** Add the same trim check present in the create drawers:
```typescript
if (!name.trim()) return
```

### bug-0143 :large_blue_circle: Minor — `deletePermission` P2003 guard is unreachable due to cascade delete

**File:** `apps/auth-server/src/permissions/permissions.service.ts:189-209`

**Description:** The `deletePermission` method catches `P2003` (foreign key constraint violation) and counts both `saRolePermission` and `saUserPermission` assignments to produce a meaningful error message. However, the Prisma schema defines `onDelete: Cascade` on both the `SaRolePermission` and `SaUserPermission` join tables' permission foreign key. Prisma cascades the delete before any FK violation can occur, so the P2003 catch block never fires.

This means deleting a permission silently removes all role and direct-user assignments without any warning — the admin is not told that 5 roles and 12 users lost that permission.

**Impact:** Permission deletion silently revokes access for all users and roles that referenced it. The admin receives a success response with no indication of the blast radius.

**Fix:** Before attempting the delete, explicitly count dependents and block if any exist:
```typescript
const counts = await prisma.saPermission.findUnique({
  where: { id: permission.id },
  select: { _count: { select: { roles: true, users: true } } },
});
if (counts._count.roles > 0 || counts._count.users > 0) {
  throw new ConflictException(
    `Permission is in use by ${counts._count.roles} role(s) and ${counts._count.users} user(s)`
  );
}
```

**Fixed:** false

### bug-0145 :large_blue_circle: Minor — PermissionViewDrawer and RoleViewDrawer fetch effects have no cancellation guard

**Files:**
- `apps/admin/components/permission-view-drawer.tsx:32-39`
- `apps/admin/components/role-view-drawer.tsx:28-35`

**Description:** Both view drawers fetch detail data in a `useEffect` when `open` changes, but neither uses a `cancelled` flag. If a user opens the drawer for entity A, then quickly switches to entity B (by clicking a different table row), the fetch for entity A is still in-flight. When it resolves, it calls `setDetail()` with entity A's data and `setLoading(false)`, potentially overwriting entity B's data or prematurely clearing the loading state.

The `role-create-drawer.tsx` (line 44) and `user-create-drawer.tsx` (line 64) correctly use a `cancelled` flag for their fetch effects.

**Impact:** Rapid drawer switching can briefly show stale entity data. More likely on slow networks.

**Fix:** Add a `cancelled` flag:
```typescript
React.useEffect(() => {
  if (!open) return
  let cancelled = false
  setLoading(true)
  setDetail(null)
  getPermissionAction(permission.publicId)
    .then((res) => { if (!cancelled && 'publicId' in res) setDetail(res) })
    .finally(() => { if (!cancelled) setLoading(false) })
  return () => { cancelled = true }
}, [open, permission.publicId])
```
