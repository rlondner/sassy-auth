# bug-0269: BetterAuth's Account table has no DB-level uniqueness on (providerId, accountId)

**Severity:** Warning
**Status:** Open
**Fixed:** false

## Description

The `Account` table (BetterAuth's account-linking table — `accountId` +
`providerId` + `userId`, defined in the original
`20260526054018_betterauth_init` migration, predating yesterday's social
auth feature) has no unique constraint of any kind, not even
`(providerId, accountId)`. Nothing in the database prevents the same
external identity (e.g. the same Google `sub`) from being linked to two
different local `userId` rows.

Yesterday's social-authentication feature is what makes this newly
exploitable/relevant: it's the first thing in this codebase that actually
links external provider identities to local users. The application-layer
mitigations are real and carefully reasoned through
(`apps/auth-server/src/social/build-social-providers.ts:54-66`:
`disableSignUp: true` on every provider, and a deliberate decision not to
add any provider to `trustedProviders` so implicit linking still requires
`emailVerified`) — but that's not a substitute for a DB constraint. The
integrity guarantee currently rests entirely on there being no race and no
future bug in BetterAuth's own find-or-create account-linking logic, which
is third-party code this repo doesn't control.

## Impact

Medium. No known exploit today — this closes a gap in defense-in-depth
rather than fixing an observed break. If BetterAuth's linking logic ever
has a bug or a race (concurrent callback requests for the same identity),
today the database would silently accept a duplicate link; after this fix
it would reject one.

## Files

- `packages/db/schema.prisma` (`Account` model)

## Fix

Add `@@unique([providerId, accountId])` to the `Account` model
(`packages/db/migrations/20260824070000_account_provider_unique/migration.sql`).
Applied in this PR.

**Deploy note:** if this migration fails to apply because duplicate
`(providerId, accountId)` rows already exist in a target database, that is
itself a genuine data-integrity issue to investigate and resolve by hand
(this repo's own data, so a duplicate-check query against a live DB wasn't
run as part of filing this from within the review sandbox) — do not weaken
the constraint to work around a migration failure without first confirming
why duplicates exist.
