# bug-0270: stub-idp's "refuse concurrent identity writes" guard has a check-then-act race

**Severity:** Warning (test-infrastructure only, not reachable in production)
**Status:** Open
**Fixed:** false

## Description

`apps/admin-e2e/fixtures/stub-idp/server.mjs`'s `POST /__set-identity`
handler exists specifically to turn a `playwright.config.ts` `workers`
bump into a loud, immediate `409 identity_write_conflict` instead of two
specs silently interleaving against the same process-global `nextIdentity`
variable (see the module's own extensive comment at lines 70-95).

The guard checked `isPending()` synchronously but didn't claim the pending
slot (`pendingSince = Date.now()`) until *after* `await readBody(req)`
(line 157, pre-fix). `readBody` is a genuine async yield point — it
resolves on the request's `'data'`/`'end'` events — so two `POST
/__set-identity` requests that both arrive before either finishes reading
its body both observe `isPending() === false`, both proceed past the guard,
and the second silently overwrites `nextIdentity`/`pendingSince` instead of
getting the 409 the comments promise. The check and the claim were not
atomic with each other.

Today's impact is contained — `playwright.config.ts` pins `workers: 1`, so
no two specs actually run concurrently against this process right now — but
that also means the guard was untested in the one scenario it exists for.
As written, a future worker-count regression would reproduce exactly the
silent-interleaving failure mode this code was built to catch, rather than
surfacing the readable CI failure its own comments describe.

## Files

- `apps/admin-e2e/fixtures/stub-idp/server.mjs:140-172`

## Fix

Claim the pending slot (`pendingSince = Date.now()`) immediately after the
`isPending()` check, before the `await readBody(req)` — removing the yield
point between check and claim. Also release the slot
(`pendingSince = null`) on the pre-existing `invalid_json` early return, so
a malformed body doesn't wedge the slot for the full 30s TTL. Applied in
this PR.

Not covered by an automated test: this is plain Node `http` fixture code
with no existing unit-test harness (it's exercised only indirectly through
Playwright specs, which run with `workers: 1` and can't reproduce the race).
The fix was verified by inspection — the only `await` in the handler now
runs after the slot is claimed, so there is no remaining window between the
`isPending()` read and the write that claims it.
