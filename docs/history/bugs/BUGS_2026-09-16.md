### bug-0291 🟠 High — activation-email `message` branding spliced into HTML unescaped (stored HTML injection)

**Fixed:** false

**Files:**
- `apps/auth-server/src/email/templates/verify-email.template.ts`
- `apps/auth-server/src/email/templates/templates.spec.ts`

Full writeup: [`docs/history/bugs/bug-0291.md`](./bug-0291.md).

**Summary:** PR #394 let any caller holding `platform.apps.manage` set a
per-app `activationEmailOverride.message` string. `apps.service.ts`
validates it's a string with no embedded newlines (a header-injection
guard for the sibling `subject`/`fromAddress` fields) but, correctly, does
not reject markup — it's meant to hold free-form admin copy.
`verify-email.template.ts` then spliced that raw string directly into the
HTML email body (`<p>${message}</p>`) with no escaping, so an app admin
could inject arbitrary HTML — a look-alike link overlaying the real
"Confirm your email address" button, a remote tracking pixel, hidden
content — into every activation email sent to that app's end users. This
is stored HTML injection with cross-user impact (the injecting party and
the affected recipients differ), not self-XSS.

**Fix:** PR #395. Added a narrow `escapeHtml()` (the five standard
HTML-text-content entities) applied only to `message` at its one HTML
interpolation site; `text` stays an unescaped plain-text copy and
`subject` is untouched (already newline-guarded, never rendered as HTML
body content).

**Verification:** New regression test in `templates.spec.ts` asserting a
`message` containing `<a href="...">`/`&`/`"` renders escaped in `html`
and literal in `text`, with the real activation URL/button unaffected.
`pnpm --filter @sassy-auth/auth-server exec jest templates.spec.ts` —
10/10 passing. `pnpm --filter @sassy-auth/auth-server exec tsc --noEmit`
— clean. Not verified against a live email render in an actual mail
client in this environment.
