## bug-0293 🟡 Medium — staging and production session cookies collide in the same browser's cookie jar

**Fixed:** false (fix coded in this review — see PR [#436](https://github.com/rlondner/sassy-auth/pull/436), branch `bug-0293`, open against `dev` as of this writing)

**Files:**
- `render.staging.yaml` (introduced the collision)
- `apps/auth-server/src/auth/auth.config.ts`
- `packages/types/index.ts` (`getBetterAuthCookieName`)
- `apps/admin/app/login/actions.ts`, `apps/admin/middleware.ts`,
  `apps/admin/app/login/page.tsx`, `apps/admin/app/account/security/actions.ts`,
  `apps/admin/app/(admin)/actions.ts`

**Description:** PR #435 (`5329d1e`) fixed a real bug — federated (Google/
Microsoft/Apple) sign-in silently dropping the user back at `/login` in
production, because BetterAuth issues a host-only session cookie mid-OAuth-
callback and `auth-api.milissai.com`/`auth.milissai.com` are sibling
subdomains. The fix sets `COOKIE_DOMAIN=.milissai.com` on both the
production **and staging** environments in `render.yaml` /
`render.staging.yaml`. But staging's own two hosts
(`auth-staging.milissai.com` / `auth-api-staging.milissai.com`) don't share
a narrower suffix than `.milissai.com` either — so staging is forced onto
the *exact same* `COOKIE_DOMAIN` as production. Combined with an identical
cookie name (`better-auth.session_token`, or `__Secure-` prefixed since
both environments run with `NODE_ENV=production`) and identical `Path`,
staging and production write to the **same slot in a browser's cookie
jar**.

**Failure scenario:** An operator (or a browser shared across environments,
e.g. someone testing staging and production back-to-back) signs into
staging, then visits production — the production tab's session cookie is
silently overwritten by staging's, and vice versa. The overwritten
environment's own session check correctly rejects the foreign cookie
(`BETTER_AUTH_SECRET` differs per environment, so the signature doesn't
validate) and bounces to `/login` — not an account-takeover risk, but a
confusing "I was just signed in and now I'm signed out" bug that will
reliably reproduce for anyone who uses both environments in the same
browser. `render.staging.yaml`'s own commit already flagged this exact
mechanism in a code comment ("A browser that has an active session cookie
from BOTH environments will only keep whichever one it set/received most
recently") but shipped it as an accepted "UX quirk" rather than fixing it.

**Fix applied:** Added an optional `COOKIE_PREFIX` env var, wired through
BetterAuth's `advanced.cookiePrefix` on the auth server and through
`getBetterAuthCookieName` (`@sassy-auth/types`) on every admin-console call
site that has to independently compute the same cookie name. Production
leaves `COOKIE_PREFIX` unset (defaults to BetterAuth's own `better-auth`
prefix, so no currently-valid production session cookie is invalidated by
this change); `render.staging.yaml` sets it to `sassy-staging`, giving the
two environments distinct cookie names and therefore distinct jar slots
despite sharing `COOKIE_DOMAIN`. New test coverage: `auth.config.spec.ts`
(`advanced.cookiePrefix` defaults/override) and
`better-auth-cookie-name.test.ts` (custom-prefix case).
