### bug-0290 🔴 Critical — auth-server crashes on boot outside production when dev TLS certs are absent

**Fixed:** false (PR open, unmerged as of this review)

**Files:**
- `apps/auth-server/src/main.ts`
- `apps/auth-server/src/https-options.ts` (new)
- `apps/auth-server/src/https-options.spec.ts` (new)

Full writeup: [`docs/history/bugs/bug-0290.md`](./bug-0290.md).

**Summary:** `0002a11` made `bootstrap()` read two gitignored,
per-machine mkcert certificates via unconditional `fs.readFileSync`
whenever `NODE_ENV !== 'production'`, with no existence check. That
condition is true — and the certs are absent — on a fresh clone, in
`docker compose up` (the Dockerfile deliberately runs with `NODE_ENV`
unset), and in CI's `admin-e2e` job (`NODE_ENV: test`), so the process
now crashes with an uncaught `ENOENT` before it can bind a port,
breaking the documented one-command Quick Start.

**Fix:** PR #392. Extracted cert resolution into a separate
`https-options.ts` module (importing `main.ts` directly triggers its
top-level `bootstrap()` call, which needs a live Postgres connection, so
it can't be unit tested in place) with an `fs.existsSync` check that
falls back to plain HTTP with a `console.warn` instead of throwing. Also
added the missing mkcert setup step to `README.md`.

**Verification:** `pnpm --filter @sassy-auth/auth-server exec jest
https-options` — 4/4 passing. `pnpm --filter @sassy-auth/auth-server exec
tsc --noEmit` — clean. Not run against a live `docker compose up` or a
full CI e2e run in this environment (no Docker daemon here, and CI on
PR #392 is the first real signal); the crash itself was confirmed by
reading the code path against the actual CI env config
(`.github/workflows/e2e.yml`) and `docker-compose.yml`, not by
reproducing a live failure, since the pre-existing bug-0282 build error
currently fails the `admin-e2e` job earlier in the pipeline than this
code path.

## Verified — not filed

- **PR #386 (bug-0287, "revert auth-server local-dev URLs from https to
  http") is now obsolete.** It was filed 2026-09-10 on the premise that
  `main.ts` had no TLS wiring at all, so the `https://localhost:3010`
  defaults `ccf2cea`'s port renumber introduced were simply wrong.
  `0002a11` (today) gave `main.ts` real TLS wiring, so the correct fix
  direction reversed — keep `https://`, make the server actually serve
  it — and that's what shipped. Merging #386 now would revert the
  intended, now-working HTTPS setup. Recommend closing #386 rather than
  merging; not closed by this review (out of scope — the task only
  covers filing/fixing new bugs, not managing existing PRs). Called out
  again in `TODO_2026-09-15.md`.
- **`admin` still hardcodes the literal string `'better-auth.session_token'`
  in ~10 files** (`app/login/actions.ts`, `app/login/page.tsx`,
  `app/account/security/actions.ts`, `app/(admin)/actions.ts`,
  `lib/api.ts`, plus tests) instead of importing
  `BETTER_AUTH_SESSION_COOKIE` from `apps/auth-server/src/common/constants.ts`
  (there's no shared package boundary between the two apps for this).
  This is exactly the class of defect `953e42d` had to work around today
  (BetterAuth silently renaming the cookie broke every one of these
  lookups) — genuine tech debt, but not a currently-reproducible failure
  on `dev` (the strings match today), so not filed as a bug. Recommend a
  shared constant in a follow-up; flagged in TODO.
- **Env-gate scope (`NODE_ENV !== 'production'` also matching `'test'`)**
  — considered filing separately from bug-0290, but it's the same root
  cause and the same fix (existence-check + fallback handles both the
  missing-certs case and the `'test'`-env case identically), so folded
  into bug-0290 rather than filed twice.
- **`apps/admin` and `apps/auth-server` may not share the same mkcert
  local CA**, which would produce browser TLS warnings navigating between
  `localhost:3001` (admin, Next's self-generated cert) and
  `localhost:3010` (auth-server, now a manually mkcert'd cert) even
  though both are "trusted" independently. Not verified — would require
  inspecting both certs' issuers on a machine that has actually run both
  dev servers, which this review environment cannot do (no certs present
  here at all). Flagged in TODO as a follow-up check, not filed as a bug
  without reproduction.
