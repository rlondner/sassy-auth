## bug-0306: `pnpm-lock.yaml`'s `better-auth` specifier doesn't match `package.json`, breaking every CI install since 997f614

**Fixed:** false

### Summary

`997f614` ("fix: upgrade next/sentry/better-auth to patch known CVEs") bumped
`apps/auth-server/package.json`'s `better-auth` dependency to `"^1.7.7"`, but
the corresponding `pnpm-lock.yaml` entry was hand-edited (or generated by a
tool that didn't preserve the range) to the bare exact string `"1.7.7"` —
no caret. `pnpm install --frozen-lockfile`, which every CI workflow in this
repo uses for its install step, treats a specifier mismatch between
`package.json` and the lockfile as fatal (`ERR_PNPM_OUTDATED_LOCKFILE`),
regardless of whether the *resolved version* is still correct.

Consequence: **every** push to `dev` since `997f614` landed (`e258416`
onward — 8 pushes, ~5 hours) has had `unit tests`, `typecheck`, `e2e`, and the
brand-new `Version bump` workflow fail at the install step, before any actual
test or build runs. Verified via `gh run list --branch dev`:

```
unit tests      failure   2c8f837
Version bump    failure   2c8f837
typecheck       failure   2c8f837
e2e             failure   2c8f837
...
typecheck       failure   e258416   ← first push after 997f614
unit tests      failure   e258416
```

The `Version bump` workflow (new today, see below) failing at the same step
also means no app version has actually been bumped yet despite several
version-affecting commits landing, and the chained staging deploy dispatch
never ran.

This is a **false-negative-free, no-code-risk** lockfile bug — the better-
auth 1.7.7 migration itself (the actual risky part of `997f614`: a major
version jump, `auth.api`'s narrowed `InferAPI` type, the new
`auth-api-extras.ts` hand-written type) is correct. Verified locally in an
isolated worktree, once the lockfile is fixed:
- `pnpm install --frozen-lockfile` succeeds
- `pnpm --filter @sassy-auth/admin typecheck:ci` and `@sassy-auth/ui
  typecheck:ci` are clean
- `pnpm --filter @sassy-auth/auth-server build` (the e2e workflow's
  typecheck gate) succeeds
- `pnpm --filter @sassy-auth/auth-server test` — **110 suites, 1279 tests,
  all pass**

### Fix

Regenerated the lockfile entry via `pnpm install` so the specifier matches
`package.json` again (`1.7.7` → `^1.7.7`); no dependency version change.
PR: **#482** (`bug-0306` → `dev`).

## bug-0307: turbo's new `start` task drops `COOKIE_SECURE`/`COOKIE_DOMAIN`/`AUTH_SERVER_HTTPS` and other documented production-run vars

**Fixed:** false

### Summary

`61d37af` ("build: add turbo start task for production runs") added a root
`pnpm start` → `turbo start` script, with a `passThroughEnv` allowlist in
`turbo.json` copied verbatim from the existing `dev` task.

This repo's `turbo.json` runs under turbo 2.x's default `envMode: "strict"`
(confirmed via `turbo run start --dry=json` → `"envMode": "strict"`). In
strict mode, only env vars named in a task's `env`/`passThroughEnv` (or a
global allowlist, which this repo doesn't define) are passed to the spawned
child process — everything else is silently stripped, not merely excluded
from the cache key.

Because the `start` list is an untouched copy of `dev`'s, it's missing every
var the README and DEPLOYMENT.md specifically call out as mattering for a
**production-mode** run — the exact scenario `start` exists for:

- `COOKIE_SECURE`, `COOKIE_DOMAIN`, `COOKIE_PREFIX` — README's "Cookie
  security" section and DEPLOYMENT.md's bug-0293 note; getting these wrong
  is documented there as breaking cross-subdomain sign-in or corrupting
  cookies between environments.
- `AUTH_SERVER_HTTPS` — README's own Caddy-proxy note names this var
  *explicitly* for `pnpm start`: "set this explicitly when a
  `NODE_ENV=production` run still needs the dev TLS listener (e.g. `pnpm
  start` behind the Caddy proxy below...)". The var it tells you to set is
  the one this task was dropping.
- `GEOIP_DB_PATH`, `TWO_FACTOR_TRUST_DAYS`, `TWO_FACTOR_PROMPT_ENABLED`,
  `TURNSTILE_SECRET_KEY`, `DEFAULT_RATE_LIMIT`/`DEFAULT_RATE_WINDOW_MS`,
  `AUTH_RATE_LIMIT`/`AUTH_RATE_WINDOW_MS`, `E2E_ADMIN_EMAIL`/
  `E2E_ADMIN_PASSWORD`, and the whole `OTEL_*` family — all documented
  optional vars with no other wildcard covering them.

Render itself is unaffected — `render.yaml`/`render.staging.yaml` call
`node dist/main.js` and `next start` directly, never through turbo, so the
real production deployment inherits its environment normally. This only
bites the local "production-like" flow the README and DEPLOYMENT.md §8
describe (and the brand-new `pnpm start` this task adds), where an operator
sets one of these vars expecting it to take effect and it silently doesn't —
falling back to a default instead of erroring, which makes it look like the
app ignored a documented setting rather than that it never saw it.

### Fix

Added the missing vars to the `start` task's `passThroughEnv` list in
`turbo.json`. Verified via `turbo run start --filter=@sassy-auth/auth-server
--dry=json` that `AUTH_SERVER_HTTPS` and `COOKIE_DOMAIN` now resolve into
the task's `passThroughEnv`. PR: **#483** (`bug-0307` → `dev`, stacked on
#482 so its own CI can run green).
