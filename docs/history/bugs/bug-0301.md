# bug-0301 🔴 High — Signed JWTs (access + ID tokens) logged in full, unconditionally, on every mint

**Fixed:** true

**Files:**
- `apps/auth-server/src/token/token.service.ts:174` (`issueAccessToken`)
- `apps/auth-server/src/token/token.service.ts:236` (`issueIdToken`)

**Description:** `issueAccessToken` and `issueIdToken` each ran
`console.log('[minted access_token]', token, payload)` /
`console.log('[minted id_token]', idToken, payload)` on **every** call,
with no `NODE_ENV` guard. This logged the complete signed RS256 JWT —
plus its full claim set (`sub`, `org`, `permissions`, `roles`) — to
stdout on every single token mint, in every environment including
production.

A sibling pattern already exists in the same codebase:
`auth.config.ts`'s magic-link URL logger is explicitly wrapped in
`if (process.env.NODE_ENV !== 'production')` with a comment explaining
that production stdout is captured by shared log streams (Docker logs,
Sentry, Datadog, etc.) that operators and log-forwarding pipelines can
read. The two `console.log` calls in `token.service.ts` got no such
treatment.

**Failure scenario:** In production, any log aggregator that captures
stdout (Docker logs, Sentry breadcrumbs, Datadog log pipeline, etc.)
permanently retains a valid, replayable RS256 access token and ID token
for every sign-in, OAuth code exchange, and token refresh — until each
token's natural expiry (up to `TOKEN_TTL_SECONDS` / 3600s for access
tokens). Anyone with read access to that log stream (an operator, a
misconfigured log-forwarding destination, a compromised logging
integration) can replay the token directly against the API or any
relying party, bypassing authentication entirely. For an identity
provider this is a direct token-theft vector and very likely a
compliance finding (SOC 2 / ISO 27001 logging controls generally
prohibit storing credentials/secrets in plaintext logs).

**Fix:** Removed both `console.log` calls entirely rather than gating
them behind `NODE_ENV`, since even a dev-only log of a real signed
token is unnecessary — `recordTokenIssueDuration` and the existing
OpenTelemetry span already provide mint-time observability without
persisting token material.

**Verification:** `pnpm --filter @sassy-auth/auth-server exec jest
token.service.spec.ts` — all tests pass unchanged (none of the existing
specs asserted on `console.log` output for these two methods).
