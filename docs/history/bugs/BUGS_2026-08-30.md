### bug-0276 🟠 High — password reset doesn't revoke other sessions

**Files:**
- `apps/auth-server/src/auth/auth.config.ts`

**Description:** BetterAuth's `/reset-password` endpoint only calls
`deleteSessions(userId)` when `emailAndPassword.revokeSessionsOnPasswordReset`
is explicitly `true` (`node_modules/better-auth/dist/api/routes/password.mjs:164`)
— it defaults to off, and this codebase's `emailAndPassword` block
(`auth.config.ts:247-273`) never set it.

Failure scenario: an attacker has a live stolen/hijacked session for a user.
The user notices something is wrong and does the standard incident-response
move — resets their password via the forgot-password flow
(`apps/admin/app/forgot-password` → `apps/admin/app/reset-password`). The
password changes, but the attacker's session is completely untouched and
keeps working indefinitely, because nothing revoked it. This is the same
class of gap as bug-0275 (2FA enrollment didn't revoke sibling sessions
either), just a different entry point into the same underlying pattern:
better-auth's own session hygiene on account-security-state changes is
opt-in, not default.

**Fix:** PR #365. Set `revokeSessionsOnPasswordReset: true` in the
`emailAndPassword` config block. **Verified:**
`pnpm --filter auth-server test -- --testPathPattern=auth.config.spec` —
12/12 pass, including a new assertion; `npx tsc --noEmit` in
`apps/auth-server` — no errors.

**Fixed:** false
