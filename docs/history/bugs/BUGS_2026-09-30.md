## bug-0294 🟡 Medium — Caddy dev proxy sends plaintext HTTP to a TLS-only backend, and its new `predev` hook could hard-block `pnpm dev`

**Fixed:** false (fix coded in this review — see PR
[#444](https://github.com/rlondner/sassy-auth/pull/444), branch
`bug-0294`, open against `dev` as of this writing)

**Files:**
- `Caddyfile` (introduced today, `8d487f2`)
- `scripts/start-caddy.ps1` (introduced today, `8d487f2`)
- `package.json` (`predev` script, introduced today, `8d487f2`)
- `README.md` (§6/§7, now stale)

**Description:** `8d487f2` added a local Caddy reverse proxy so
`https://auth-dev.milissai.com` / `https://auth-api-dev.milissai.com` mimic
the production hostnames, and dropped `apps/admin`'s own
`--experimental-https` dev flag in favor of it. Two problems:

1. The `auth-api-dev.milissai.com` block does `reverse_proxy
   127.0.0.1:3010` with no scheme, which is Caddy's default *plaintext*
   HTTP backend transport. `apps/auth-server` was **not** changed by this
   commit — it still terminates its own TLS on `:3010` using the mkcert
   certificate from `README.md` step 6
   (`apps/auth-server/src/https-options.ts`). Caddy speaking plaintext
   HTTP to a TLS-only listener is a protocol mismatch; anyone who actually
   visited `https://auth-api-dev.milissai.com` (rather than the
   `localhost:3010` URL every `.env.example` still points at) would hit a
   broken proxy, not the auth server.
2. The new `predev` script (`powershell -NoProfile -ExecutionPolicy Bypass
   -File ./scripts/start-caddy.ps1`) has no platform guard, and
   `start-caddy.ps1` ran under `$ErrorActionPreference = 'Stop'`. On any
   machine without a `powershell` binary on `PATH` (macOS, Linux), the
   `predev` lifecycle script fails outright with `ENOENT`, and npm/pnpm
   abort before running `dev` at all — turning an *optional* convenience
   into a hard dependency of `pnpm dev`. The same script also throws
   (rather than degrading) if `caddy` itself isn't installed, or if
   `Start-Process -Verb RunAs` fails for any reason (e.g. the user declines
   the UAC elevation prompt).

**Failure scenario:** A developer runs `pnpm dev` on a machine without
Caddy — or without PowerShell at all — and the whole aggregated dev command
fails before either `auth-server` or `admin` starts, even though neither
app actually depends on Caddy to run. A developer who *does* try the new
`https://auth-api-dev.milissai.com` hostname sees a broken/empty response
instead of the auth server, with no indication the proxy itself is
misconfigured.

**Fix applied:** Caddy's upstream for the auth-server hop now uses
`reverse_proxy https://127.0.0.1:3010` with an explicit `http` transport
that trusts the local mkcert cert
(`transport http { tls_insecure_skip_verify }` — safe only because this
proxy never leaves the developer's own machine, and the cert being
verified is issued for `localhost`, not the `127.0.0.1` IP literal being
dialed here, so hostname verification would fail regardless of trust).
`predev` was replaced with a small cross-platform `scripts/predev.mjs`
that only attempts to start Caddy on `win32` and no-ops elsewhere;
`start-caddy.ps1` now warns and exits `0` instead of throwing when `caddy`
isn't on `PATH` or fails to launch. `README.md` updated to describe the
Caddy proxy as optional Windows-only tooling and to stop citing the
removed `--experimental-https` flag.

**Verification:** `caddy validate --config Caddyfile` passes (`caddy fmt`
applied). While hardening `start-caddy.ps1`, a genuine parse bug was found
and fixed along the way: a new catch-block warning string mixed a
double-quoted string with an em dash, which Windows PowerShell 5.1's
default console encoding mis-decodes into bytes that prematurely
terminate the string —
`[System.Management.Automation.PSParser]::Tokenize` failed on it
(reproduced locally; Caddy is actually installed on this review's
machine). Rewritten as a single-quoted `-f` format string; the tokenizer
now reports no errors on the full file. Did not exercise a live elevated
`caddy run` in this environment (would trigger a real UAC prompt / start a
real background process on whoever runs this review, which an automated
review shouldn't do unprompted) — verified statically instead.

## bug-0295 🟢 Low — signup email field shows "invalid email" error when blurred while still empty

**Fixed:** false (fix coded in this review — see PR
[#445](https://github.com/rlondner/sassy-auth/pull/445), branch
`bug-0295`, open against `dev` as of this writing)

**Files:**
- `apps/admin/app/signup/signup-form.tsx`
- `apps/admin/app/signup/__tests__/signup-form.test.tsx`

**Description:** `65aa0d5` added client-side email format validation to
the signup form: `validateEmail()` reads the native
`emailRef.current.validity.valid` on blur and shows
`signup.errors.invalidEmail` ("Please enter a valid email address.") when
false. `ValidityState.valid` is `false` for **any** constraint violation
on the input, including `valueMissing` (an empty `required` field) — not
only `typeMismatch` (a malformed address). The three new tests for this
feature all blur the field only after typing a value (`'not-an-email'`);
none exercise blurring the field while still empty.

**Failure scenario:** A user tabs into the email field and back out again
without typing anything — accidentally, or intending to fill it in
later — and immediately sees "Please enter a valid email address." on an
untouched, empty field. Misleading (the problem isn't the *format*, it's
that nothing was entered yet) and appears before any submit attempt.

**Fix applied:** `validateEmail()` now returns early and clears (rather
than sets) the error when the field's value is empty, before consulting
`validity.valid`. Emptiness itself is still caught by the input's native
`required` attribute at submit time and by the existing submit-time
checks — this only narrows the *blur* check to the format concern it was
meant to cover.

**Verification:** Added
`does not show an invalid email error when blurring an untouched, empty
email field (bug-0295)` to `signup-form.test.tsx`. `pnpm --filter
@sassy-auth/admin exec jest signup-form.test.tsx` — 23/23 passing
(previous 22 plus the new case). `tsc --noEmit` on `apps/admin` was run but
is not clean independent of this change (pre-existing errors from
un-built workspace packages — `@sassy-auth/telemetry/*` — and unrelated
test-fixture type drift in several `components/__tests__/*` files); none
of the reported errors reference `signup-form.tsx` or this change.
