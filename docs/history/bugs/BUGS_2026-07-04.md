### bug-0147 :red_circle: Critical — `username`/`phoneNumber` direct-login lookup uses `findFirst` on non-unique columns — cross-tenant authentication collision

**Files:**
- `apps/auth-server/src/token/token.controller.ts:281-311`
- `packages/db/prisma/schema.prisma` (`SaUser` model — `username`/`phoneNumber` are `@@index`, not `@@unique`)

**Description:** The `directLogin` endpoint resolves users by username or phone number using `prisma.saUser.findFirst({ where: { username: dto.identifier } })`. Neither `username` nor `phoneNumber` has any uniqueness constraint — not even per-org. Nothing in `createUser` (`users.service.ts:148-230`) prevents duplicate usernames/phones across orgs or apps. `findFirst` with no `orderBy` returns an arbitrary row when duplicates exist.

The org/app match check (`saUser.org.appId !== app.id`, line 315) happens *after* the lookup. When a collision exists:
- If the wrong-tenant user's app happens to match, the login authenticates as the wrong user.
- If it doesn't match, a legitimate login is incorrectly rejected with `USER_ORG_MISMATCH`.

**Impact:** Two users in different orgs/apps sharing a username (e.g., "admin") is trivially common. Direct login by username against app A may authenticate as a user from app B, or may reject a valid user. This is a cross-tenant authentication flaw.

**Fix:** (1) Add `@@unique([orgId, username])` and `@@unique([orgId, phoneNumber])` constraints. (2) Scope the login lookup to the target app: `where: { username: dto.identifier, org: { appId: app.id } }`.

**Fixed:** false

### bug-0148 :red_circle: Critical — All entity-creation flows race on a shared literal `publicId: 'placeholder'` — concurrent creates fail with wrong error

**Files:**
- `apps/auth-server/src/apps/apps.service.ts:53`
- `apps/auth-server/src/orgs/orgs.service.ts:95`
- `apps/auth-server/src/roles/roles.service.ts:142`
- `apps/auth-server/src/permissions/permissions.service.ts:137`
- `packages/db/prisma/schema.prisma` (`publicId String @unique` on all four models)

**Description:** Every create flow (apps, orgs, roles, permissions) does:
```typescript
const draft = await tx.saModel.create({ data: { publicId: 'placeholder', name: dto.name, ... } });
return tx.saModel.update({ where: { id: draft.id }, data: { publicId: this.sqids.encode(draft.id) } });
```

`publicId` is `@unique`. If two concurrent create requests execute, the second insert of `publicId: 'placeholder'` hits the unique constraint (P2002). The catch block interprets any P2002 as a duplicate **name**, so the caller receives `ConflictException('App with this name already exists')` even when the name is unique.

**Impact:** Under any concurrent admin usage (two admins creating different apps/orgs/roles at the same moment), one request fails with a confusing, incorrect error. Reproducible under normal multi-user admin usage.

**Fix:** Use a per-request unique placeholder (e.g., `crypto.randomUUID()`) instead of the literal `'placeholder'`, or distinguish which column triggered the P2002 by inspecting `e.meta.target`.

**Fixed:** false

### bug-0149 :yellow_circle: Warning — OAuth authorize endpoint returns JSON 401 to unauthenticated browser users instead of redirecting to login

**File:** `apps/auth-server/src/token/token.controller.ts:100-105`

**Description:** When a user visits `GET /api/token/oauth/authorize?...` without a BetterAuth session (the normal case for a resource server initiating the PKCE flow), the controller throws `UnauthorizedException` (line 105). The code comment at line 141–142 says "UnauthorizedException keeps the existing login-redirect flow — Nest's global filter handles it", but `SentryExceptionFilter` (`apps/auth-server/src/common/filters/sentry-exception.filter.ts:70`) only returns a JSON response. There is no redirect to a login page. The OAuth Authorization Code flow (RFC 6749 §4.1.1) requires the authorization server to authenticate the resource owner.

**Impact:** Third-party resource servers implementing the PKCE flow get a broken first-time login experience. Users see raw JSON instead of a login page. The sample FastAPI resource server will exhibit this on every first login.

**Fix:** Redirect to the admin login with a `next` parameter:
```typescript
if (!session) {
  const adminUrl = process.env.ADMIN_URL ?? 'http://localhost:3001';
  const loginUrl = new URL('/login', adminUrl);
  loginUrl.searchParams.set('next', `${req.protocol}://${req.get('host')}${req.originalUrl}`);
  return { url: loginUrl.toString(), statusCode: 302 };
}
```

**Fixed:** false

### bug-0150 :yellow_circle: Warning — `redirect_uri` at `/token` endpoint is not bound to the code issued at `/authorize` (RFC 6749 §4.1.3 violation)

**Files:**
- `apps/auth-server/src/token/oauth.service.ts:5-11,31-46`
- `apps/auth-server/src/token/token.controller.ts:90,178`

**Description:** The `AuthCode` record stored by `OauthService.generateCode` only tracks `userId`, `appPublicId`, `codeChallenge`, `codeChallengeMethod`, and `expiresAt` — it never stores the `redirect_uri` used at `/authorize`. At `/token`, `assertRedirectUriMatchesApp(dto.redirect_uri, app.url)` only checks the redirect_uri's origin matches the app's registered URL — it never checks it's the *same* redirect_uri supplied when the code was minted, as RFC 6749 §4.1.3 requires.

PKCE (S256, constant-time compared) substantially mitigates exploitability today, but the binding is a spec requirement and a defense-in-depth mechanism.

**Impact:** Low today (PKCE covers the main attack). If PKCE were weakened, or a same-origin open redirect exists in a registered app, a code could be redeemed against a different path than the one it was issued for.

**Fix:** Store `redirectUri` on the `AuthCode` record and compare for exact equality in `exchangeCode`.

**Fixed:** false

### bug-0151 :yellow_circle: Warning — `deleteUser` never removes BetterAuth `User`/`Account`/`Session` rows — orphaned credentials persist

**File:** `apps/auth-server/src/users/users.service.ts:307-324`

**Description:** `deleteUser` only calls `prisma.saUser.delete()`. There is no cascade relationship from `SaUser.betterAuthUserId` back to the BetterAuth `User` table. After deleting a user:
1. Their `User.email` (globally `@unique`) remains permanently taken — they can never be re-invited with the same email.
2. Any live `Session` rows remain valid — a deleted user can continue using existing session tokens.
3. Their `Account` (password credential) row survives.

**Impact:** "Deleted" users retain login credentials and active sessions. Their email address is permanently consumed. An admin who deletes a user expects the user to be fully removed, but they are only removed from the SassyAuth layer, not from BetterAuth.

**Fix:** Wrap `deleteUser` in a transaction that also deletes the BetterAuth `User` row (which cascades to `Session`/`Account`), or implement soft-delete for `SaUser`.

**Fixed:** false

### bug-0152 :yellow_circle: Warning — `updateUser` allows `pending` → `active` status transition without invitation acceptance

**Files:**
- `apps/auth-server/src/users/users.service.ts:294`
- `apps/auth-server/src/users/dto/update-user.dto.ts:8`

**Description:** `UpdateUserDto` validates `@IsEnum(['active','inactive'])` for the `status` field, correctly blocking invalid literals. But there's no state-machine check preventing an admin from setting `status: 'active'` on a user whose current status is `pending` — a user who never accepted their invitation and never set a password. This produces an "active" `SaUser` with no corresponding `Account` credential row, which is inconsistent with the system's invariant that "active" users have a usable credential.

**Impact:** An admin can "activate" a pending user who has no password, creating an account that can't authenticate via direct login but exists as active in the system. Edge case but violates the intended user lifecycle.

**Fix:** In `updateUser`, reject status changes from `pending`: `if (existing.status === 'pending' && dto.status !== undefined) throw new BadRequestException('Cannot change status of a pending user')`.

**Fixed:** false

### bug-0156 :yellow_circle: Warning — `SaUser`/`SaInvitation` publicId derived from slicing a single UUID — correlated IDs and collision risk

**File:** `apps/auth-server/src/users/users.service.ts:197,219,244`

**Description:** `createUser` generates one `crypto.randomUUID()` and slices it to produce two publicIds:
```typescript
const baUserId = crypto.randomUUID();
publicId: baUserId.slice(0, 12),      // SaUser
publicId: baUserId.slice(12, 24),     // SaInvitation
```

Issues: (1) The invitation publicId is derivable from the user publicId (correlated, not independent). (2) Unlike all other models (SaApp, SaOrg, SaRole, SaPermission) which use the collision-free `sqids.encode(id)` pattern, these use raw UUID substrings with no retry on P2002. (3) `resendInvitation` (line 542) also uses `randomUUID().slice(0, 12)` with no collision handling.

**Impact:** Low probability but non-zero collision risk without retry. The correlation between user and invitation publicIds could aid enumeration. Inconsistent with the rest of the codebase's publicId generation pattern.

**Fix:** Use the same `sqids.encode(id)` pattern used by other entities, or generate independent UUIDs.

**Fixed:** false

### bug-0157 :large_blue_circle: Minor — `TokenService.resolvePermissions` returns all user permissions unscoped by app — JWT `scope` claim lacks defense-in-depth

**File:** `apps/auth-server/src/token/token.service.ts:30-64`

**Description:** `resolvePermissions` fetches all roles and direct permissions for a user with no filter on the target app. The resulting permission names are placed into the JWT's `scope` claim. A JWT with `aud: app-A` may include permissions from app-B.

Defense-in-depth gap — the root cause is at the assignment layer (bug-0077), but the token issuance layer has no independent guard.

**Impact:** Practically exploitable only via bug-0077 or platform admin action.

**Fix:** Filter permissions by the target app (matching `appId`) before building the scope.

**Fixed:** false

### bug-0161 :large_blue_circle: Minor — Seed script idempotency gap can permanently strand a half-provisioned platform admin

**Description:** The seed script checks `prisma.user.findUnique({ where: { email } })` for existing admins. ### bug-0162 :large_blue_circle: Minor — Duplicate permission-graph queries per request in user mutation endpoints

**File:** `apps/auth-server/src/users/users.service.ts` — `createUser`, `assignRole`, `setUserRoles`, `setUserDirectPermissions`

**Description:** Each of these methods calls both `checkPermission(...)` and `assertCallerCanGrantSystemPerms(...)`. Both helpers independently run the identical deep query (`prisma.saUser.findUnique` with nested roles→permissions and directPermissions includes) for the same caller in the same request — doubling the permission-resolution query cost on every mutating endpoint.

**Fix:** Extract a shared "resolve caller permissions" helper, call it once, pass the result to both checks.
