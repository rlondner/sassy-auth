### bug-0275 🟠 High — 2FA enrollment doesn't revoke sessions that skipped the MFA challenge

**Files:**
- `apps/auth-server/src/token/derive-auth-methods.ts`
- `apps/admin/app/account/security/actions.ts`

**Description:** `deriveAuthMethods` stamps the OAuth `amr` claim from the
account's *live* `twoFactorEnabled` flag, not from whether the specific
session actually completed a 2FA challenge. `confirmEnable` (the server
action behind 2FA enrollment) only rotates the session on the device where
enrollment happened — better-auth creates a new session there and deletes
the old one, but does not touch any other active session for the same user
(unlike account deactivation, which already revokes every session — see
`users.service.ts`).

Failure scenario: a user is signed in on two devices. On device B they
enroll in 2FA. Device A's session, still valid, was never challenged for
2FA. The next time device A drives an OAuth `/authorize` flow,
`token.controller.ts` calls `deriveAuthMethods` with the account's now-`true`
`twoFactorEnabled`, and the minted authorization code — and the token issued
from it — carries `amr: ['otp', 'mfa']`, falsely telling the relying
resource server that this specific session passed an MFA challenge.

**Fix:** PR #363. `confirmEnable` now calls better-auth's built-in
`POST /api/auth/revoke-other-sessions` immediately after 2FA is confirmed,
authenticating with the **rotated** session cookie from the response (the
stale cookie on the incoming request is deleted by that same response).
Best-effort — a failure to revoke does not turn a successful enrollment into
a reported error. **Verified:** `pnpm --filter admin test -- --testPathPattern=account/security`
— 56/56 pass, including 3 new tests (revoke call uses the rotated token, no
call is made when the response carries no rotated cookie, enrollment still
reports success if the revoke call fails); `pnpm --filter admin typecheck` —
no new errors.
