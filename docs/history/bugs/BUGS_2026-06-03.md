## :red_circle: bug-0038 — JWT payload breaking change: `permissions` array replaced with `scope` string

**Fixed:** false
**Severity:** Critical
**Files:**
- `packages/types/index.ts` (diff: `permissions: string[]` → `scope: string`)
- `apps/auth-server/src/token/token.service.ts` (line 75: `scope: permissions.join(' ')`)

**Description.** The JWT `permissions` claim (a JSON array of strings) was silently renamed to `scope` (a space-separated string) to align with OAuth 2.0 conventions. This is a breaking change for any existing consumer that parses `decoded.permissions`. The `SassyAuthJwtPayload` type was updated, but no migration notes exist. The `TokenErrorCode` enum also changed: `INVALID_CODE` and `CODE_EXPIRED` were removed and replaced with `INVALID_REQUEST`, `INVALID_REDIRECT_URI`, `INVALID_GRANT`, `UNAUTHORIZED_CLIENT`.

**Fix sketch.** Either:
1. Keep both claims during a transition period (`permissions` array + `scope` string) and document a deprecation timeline, or
2. Document the breaking change in the CHANGELOG and bump a version marker so existing consumers know to update their JWT parsing.

**Tests needed.** Verify the admin console and any other existing JWT consumer correctly handles the new `scope` format. Add a unit test asserting the JWT payload shape matches `SassyAuthJwtPayload`.

## :red_circle: bug-0039 — In-memory OAuth authorization codes not persisted; lost on restart

**Fixed:** false
**Severity:** Critical
**File:** `apps/auth-server/src/token/oauth.service.ts` (line 29)

**Description.** Authorization codes are stored in a JavaScript `Map<string, AuthCode>()` in the `OauthService` singleton. If the auth server restarts between the `/authorize` redirect and the `/token` exchange (typically a 5-minute window), all pending codes are lost and users get `invalid_grant` errors. This also prevents horizontal scaling — two server instances have independent code stores.

This is documented in the README ("Known Limitations" section) but has been **escalated to Critical** because the PKCE branch is intended for production use with the FastAPI resource server.

**Fix sketch.** Move authorization codes to the database (a new `sa_oauth_code` table with `code`, `userId`, `appPublicId`, `codeChallenge`, `codeChallengeMethod`, `expiresAt`, `usedAt` columns) or Redis. Add a periodic cleanup job for expired codes.

**Tests needed.** Integration test verifying code exchange works across different `OauthService` instances (simulating multi-instance deployment).

## :red_circle: bug-0040 — No garbage collection for expired authorization codes (memory leak)

**Fixed:** false
**Severity:** Critical
**File:** `apps/auth-server/src/token/oauth.service.ts` (lines 31-82)

**Description.** Expired authorization codes are only deleted when someone attempts to exchange them. Codes that are never exchanged (user abandons flow) remain in the `Map` forever. Under sustained traffic this grows unbounded and will eventually cause an OOM crash.

**Fix sketch.** If keeping in-memory storage, add a periodic cleanup via `setInterval` (e.g., every 60 seconds, sweep entries where `expiresAt < now`). Better: use the database fix from bug-0039 with a cron/cleanup query.

**Tests needed.** Unit test verifying expired codes are removed during cleanup.

## :yellow_circle: bug-0041 — PKCE `code_verifier` lacks RFC 7636 format validation

**Fixed:** false
**Severity:** Warning
**Files:**
- `apps/auth-server/src/token/dto/oauth-token-exchange.dto.ts` (lines 13-17)
- `apps/auth-server/src/token/token.controller.ts` (line 60, `codeChallenge` query param)

**Description.** The `code_verifier` DTO field only validates `@IsString()` and `@IsNotEmpty()`. Per RFC 7636 §4.1, the verifier must be 43-128 characters using unreserved characters `[A-Za-z0-9\-._~]`. Any string is currently accepted.

Similarly, the `code_challenge` query parameter on `/authorize` is checked for presence but not for base64url format (should be exactly 43 characters of `[A-Za-z0-9_-]`).

**Fix sketch.**
```typescript
// code_verifier
@Matches(/^[A-Za-z0-9\-._~]{43,128}$/)
code_verifier!: string;
```
On the controller, validate `code_challenge`:
```typescript
if (!/^[A-Za-z0-9_-]{43}$/.test(codeChallenge)) {
  throw new BadRequestException(TokenErrorCode.INVALID_REQUEST);
}
```

**Tests needed.** Unit tests with too-short verifier (42 chars), too-long verifier (129 chars), and invalid characters.

## :yellow_circle: bug-0042 — FastAPI resource server exposes access token to client-side JavaScript

**Fixed:** false
**Severity:** Warning
**Files:**
- `apps/resource-server-fastapi/app/oauth/routes.py` (lines 115-120)
- `apps/resource-server-fastapi/app/templates/authorized.html`
- `apps/resource-server-fastapi/app/static/app.js`

**Description.** After the OAuth callback, the access token is embedded directly in the `authorized.html` template as a JSON data attribute and stored in `sessionStorage`. This exposes the token to any JavaScript running in the same origin (XSS risk). The token should be stored server-side (e.g., in an encrypted httpOnly cookie or server session) and proxied through a BFF pattern.

This is acceptable for a demo/reference application, but should be clearly flagged as insecure for production.

**Fix sketch.** Store the token in a server-side session (e.g., `starlette.middleware.sessions.SessionMiddleware`) and proxy API calls through the FastAPI app so the token never reaches the browser.

**Tests needed.** Verify that the `/api/properties` endpoint works with cookie-based auth after switching to BFF pattern.

## :yellow_circle: bug-0043 — FastAPI JWKS verifier swallows all exceptions with generic 401

**Fixed:** false
**Severity:** Warning
**File:** `apps/resource-server-fastapi/app/oauth/verifier.py` (lines 14-30)

**Description.** The `verify()` function catches all exceptions (`except Exception`) and returns a generic 401. This masks distinct failure modes:
1. JWKS endpoint unreachable → should be 502 or 503
2. Token expired → should be 401 with `error="invalid_token", error_description="token expired"`
3. Invalid signature → should be 401 with reason
4. Missing required claims → should be 401 with reason

Operators cannot distinguish between a bad token and a broken JWKS endpoint from error logs alone.

**Fix sketch.** Catch specific PyJWT exceptions (`ExpiredSignatureError`, `InvalidAudienceError`, `InvalidIssuerError`, `PyJWKClientError`) and return appropriate status codes and error descriptions. Log the specific failure reason server-side.

**Tests needed.** Unit tests for each exception type verifying the correct HTTP status code and error description.

## :yellow_circle: bug-0044 — FastAPI `scope` claim parsing returns `{"None"}` when scope is missing

**Fixed:** false
**Severity:** Warning
**File:** `apps/resource-server-fastapi/app/oauth/verifier.py` (lines 34-38)

**Description.** The scope parsing logic is:
```python
scopes = set(str(claims.get("scope", "")).split())
```
If the `scope` claim is absent, `claims.get("scope", "")` returns `""`, which is correct. But if `scope` is `None` (present but null), `str(None)` produces `"None"`, which splits to `{"None"}`. A token with `"scope": null` would pass a `require_scope("None")` check.

**Fix sketch.**
```python
raw = claims.get("scope", "")
scopes = set(raw.split()) if isinstance(raw, str) and raw else set()
```

**Tests needed.** Unit test with `scope: null` and `scope: ""` in the JWT claims.

**Fixed:** false

**Description.** The demo seed script contains:

```typescript
const APP_URL = process.env.DEMO_RS_URL ?? 'http://localhost:8010';
const PASSWORD = process.env.DEMO_PASSWORD ?? 'Pass@word1234';
```

**Tests needed.** None required; configuration change.

## :large_blue_circle: bug-0046 — No rate limiting on `/api/token/oauth/token` endpoint

**Fixed:** false
**Severity:** Minor
**Files:**
- `apps/auth-server/src/token/token.controller.ts` (line ~138)
- `apps/resource-server-fastapi/app/oauth/routes.py` (all OAuth endpoints)

**Description.** The token exchange endpoint accepts unlimited requests. An attacker who intercepts an authorization code can brute-force `code_verifier` values without throttling. While S256 makes brute-forcing computationally infeasible for random verifiers, the absence of rate limiting allows:
1. Unbounded requests against the auth server
2. Log flooding
3. Potential DoS via repeated code lookups

The FastAPI resource server's `/auth/login` and `/auth/callback` endpoints also lack rate limiting.

**Fix sketch.** Add per-IP rate limiting on the token exchange endpoint (e.g., 10 requests/minute). On FastAPI, use `slowapi` or similar middleware.

**Tests needed.** Integration test verifying 429 response after exceeding rate limit.

## :large_blue_circle: bug-0047 — `redirect_uri` validation allows all paths under the registered origin

**Fixed:** false
**Severity:** Minor
**File:** `apps/auth-server/src/token/redirect-uri.ts` (lines 8-23)

**Description.** `assertRedirectUriMatchesApp()` validates that the `redirect_uri` origin matches the app's registered URL origin. Any path under that origin is accepted. While this is standard OAuth2 behavior and explicitly documented ("Paths under the registered origin are allowed"), it means an attacker who controls a subdirectory (e.g., via an uploaded HTML file at `https://app.example.com/uploads/evil.html`) could redirect authorization codes to their endpoint.

**Fix sketch.** Consider adding a per-app `allowedRedirectUris` field to `SaApp` that stores explicit path patterns. For now, document the current behavior in the security model.

**Tests needed.** Already covered by `redirect-uri.spec.ts`.
