# bug-0305: `/authorize` can report the wrong error for an unregistered custom-scheme redirect_uri

**Fixed:** false

## Summary

`TokenController.oauthAuthorize` (`apps/auth-server/src/token/token.controller.ts`) computed
whether PKCE is mandatory — `pkceRequired = !isConfidential || isCustomSchemeRedirect(redirectUri)`
— and checked it against the presented `code_challenge` **before** calling
`assertRedirectUriAllowed(redirectUri, app)`. `isCustomSchemeRedirect` reads the raw,
attacker-controlled `redirect_uri` query parameter.

Consequence: a request with an **unregistered** custom-scheme `redirect_uri` and no
`code_challenge` failed with the generic PKCE `invalid_request` (`INVALID_REQUEST`) instead
of `INVALID_REDIRECT_URI` — masking the real problem (the redirect URI was never valid for
this app) behind an unrelated error code. Downstream, because `redirectUriValidated` was still
`false` when the PKCE check threw, the error also went to the admin's JSON/error page instead
of being treated consistently with every other post-validation failure.

This does **not** bypass anything — the request still fails closed either way, and no
redirect to an unvalidated `redirect_uri` is ever issued — but it is a real correctness bug:
wrong error code, and (once fixed) inconsistent error-handling behavior for a
PKCE failure versus every other `/authorize` failure (`USER_ORG_MISMATCH`, `USER_NOT_FOUND`,
etc.), which — once `redirect_uri` is validated — are redirected back to the client per
RFC 6749 §4.1.2.1 rather than returned as bare JSON.

Found while reviewing `apps/auth-server/src/token/token.controller.ts` on `dev` (merged via
PR #478, 2026-11-19) — the custom-scheme redirect-URI feature. No existing test in
`token.controller.spec.ts` exercised an *unregistered* redirect_uri together with a missing
PKCE challenge; every PKCE test used an origin-matching or explicitly-registered `redirect_uri`,
so the ordering bug had no coverage.

## Fix

Reordered `oauthAuthorize` so `assertRedirectUriAllowed` runs first; the PKCE-requirement
check (which depends on the now-validated `redirectUri`) runs after. This also means a missing
PKCE challenge on an otherwise-valid request is now correctly redirected back to the client as
an `invalid_request` OAuth error, consistent with every other post-validation failure on this
endpoint.

Added a regression test (`/authorize reports INVALID_REDIRECT_URI, not a PKCE error, for an
unregistered custom-scheme redirect`) and updated the two existing PKCE tests
(`/authorize refuses to omit PKCE for a public app`, `.../for a confidential app using a
custom-scheme redirect`) whose `redirect_uri` is valid — they now correctly assert a 302
OAuth-error redirect instead of a bare 400, matching the corrected behavior.

Verified: full `token.controller.spec.ts` + `redirect-uri.spec.ts` suites pass (101/101),
`tsc --noEmit` on `apps/auth-server` is clean.
