## bug-0292 🟡 Medium — GDPR geo-detection resolves the admin server's IP, not the end user's, for every login/signup path except social sign-in

**Fixed:** false

**Files:**
- `apps/auth-server/src/common/net/resolve-client-ip.ts`
- `apps/auth-server/src/common/geoip/geoip.service.ts`
- `apps/admin/lib/consent.ts`
- `apps/admin/app/signup/actions.ts`
- `DEPLOYMENT.md` (already documents this as a known limitation — see below)

**Description:** The new optional GDPR-consent gate (PR #425) additionally
requires the GDPR checkbox only when the request is geo-detected as
originating from the EU/EEA, UK, or Switzerland, via a local MaxMind
GeoLite2-Country lookup keyed off the resolved client IP
(`resolve-client-ip.ts`, `trust proxy: 1`). That resolver correctly sees
the real browser IP only for social sign-in, which hits the auth-server
directly. Every other path this feature is supposed to gate — self-serve
signup, and password/OTP/TOTP/backup-code login — is proxied server-side
through the admin console's own Next.js server (`apps/admin/lib/consent.ts`,
`apps/admin/app/signup/actions.ts` make their own server-to-server calls to
the auth-server), so `trust proxy: 1` resolves the *admin server's* egress
address, not the end user's.

**Failure scenario:** If an operator configures `GEOIP_DB_PATH` (the
GeoLite2 database path), a user in the EU signing up or logging in via
password/OTP/TOTP could be geo-resolved to the admin server's own country
and silently skip the mandatory GDPR checkbox for an app that requires it —
or conversely a non-EU user could be wrongly forced through it. This is
**not currently exploitable in the default/documented deployment**: the
authors identified the same gap during PR #425 and added an explicit
instruction in `DEPLOYMENT.md` (§4, "Known limitation — leave
`GEOIP_DB_PATH` unset for now") to leave the env var unset everywhere,
which makes the feature fail closed (GDPR consent always required when an
app configures a GDPR URL) rather than silently wrong. Filed as a tracked
bug rather than closed because:
1. That mitigation depends entirely on every future operator reading and
   following a prose instruction in a deployment doc — nothing in code
   prevents `GEOIP_DB_PATH` from being set.
2. If it *is* set today, the failure mode is silent (wrong-but-plausible
   country, not an error) and only affects the 4 of 5 traffic paths that
   go through the admin console.

**Suggested fix:** Move `trust proxy` from a hop-count (`1`) to an explicit
trusted-address list (Render's edge proxy plus the admin server's own
address), so the resolver can tell "hop from Render's edge" (trust the
forwarded IP) apart from "hop from the admin server" (don't trust it —
there's no further forwarded-for value to trust). Until that lands, this
bug intentionally has **no PR fix in this review**: the correct code
change requires knowing production's actual proxy topology (Render's edge
IP ranges, whether admin and auth-server share a private network), which
isn't something to guess at from the repo alone — doing so risked either a
no-op change or, worse, a `trust proxy` config that fails open (trusts an
untrustworthy hop) instead of the current fail-closed default. Recommend a
human decision on the trusted-address list before this is fixed in code;
tracked here so it isn't lost.
