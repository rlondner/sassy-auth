### Custom-scheme redirect URI work-in-progress — gap is real but not yet merged, not filed as a bug

`d20c06c` (Task 2) makes `apps.service.ts` accept a reverse-domain
custom-scheme redirect URI at registration. Taken alone, that would
reopen a PKCE-bypass gap at `/authorize` (a confidential app could
register `com.example.app://auth` and skip PKCE, since the existing
"confidential ⇒ PKCE optional" check didn't know about custom schemes).
`dc7aa0d` (Task 3), committed 7 minutes later on the same branch, closes
that exact gap at `/authorize`. Since both commits are on a single
unpushed, unmerged local branch and were never exposed on `dev` even
momentarily, this isn't filed as a bug — it's expected
write-test-then-implement sequencing within one TDD plan. See
[TODO_2026-11-18.md](../todo/TODO_2026-11-18.md) item 1 for why Task 4
(the equivalent gap in `registration.service.ts`) must land before this
branch merges.

Reviewed the new code itself (`CUSTOM_SCHEME_RE`, `isCustomSchemeRedirect`,
the `/authorize` PKCE gate) for correctness — no defects found:
- `CUSTOM_SCHEME_RE` correctly requires ≥2 dot-separated labels, so a
  bare `javascript:` scheme (no dot) still fails the check exactly as
  the pre-existing `javascript:alert(1)` test expects.
- `isCustomSchemeRedirect` returning `false` for an unparseable URI is
  safe: every caller runs `assertRedirectUriAllowed`/`new URL()`
  immediately after, which rejects the URI anyway via the existing
  parse-failure path.
- The `/authorize` PKCE gate reads `redirectUri` before
  `assertRedirectUriAllowed` validates it, but `isCustomSchemeRedirect`
  only ever consults `new URL(redirectUri).protocol` in a `try`, so an
  unparseable or missing `redirect_uri` can't throw there — it falls
  through to the existing rejection path below unaffected.
