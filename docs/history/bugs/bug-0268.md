# bug-0268: federated sign-in audit trail only records rejections, never successes

**Severity:** Warning
**Status:** Open
**Fixed:** false

## Description

`apps/auth-server/src/social/record-federation-event.ts` declares four
event types — `'social.link.created'`, `'social.signin.ok'`,
`'social.signin.rejected'`, `'social.link.removed'` — and documents
`SaAuditEvent` as "the durable record" answering "who linked this Google
account to alice@acme.com, and when a year later"
(`docs/social-auth-setup.md`'s framing of the feature makes the same
promise).

But before this fix, `recordFederationEvent` was called from exactly one
call site in the entire codebase: `auth.config.ts`'s `/callback/:id`
`hooks.after` handler, with `type: 'social.signin.rejected'` — and only
reached when `classifyCallbackOutcome` returns non-null, which by its own
doc comment happens only for a refused callback ("Returns null for a
successful sign-in"). `'social.signin.ok'`, `'social.link.created'`, and
`'social.link.removed'` were declared types with no emitter anywhere.
**Every successful federated sign-in produced zero audit-trail rows.** The
one thing the audit trail's own stated purpose cares most about — a
successful, unexpected, or disputed account link — was the one thing it
never recorded.

## Impact

Medium. Not a security hole (the actual authorization/invite-only
enforcement is unaffected — see the security-regression and authz review
findings from the same review round, which found 0 issues there) but a real
functional gap in a feature explicitly documented as a compliance-relevant
audit trail.

## Files

- `apps/auth-server/src/auth/auth.config.ts` (`databaseHooks.session.create.after`)
- `apps/auth-server/src/social/sign-in-method.ts`

## Fix

Added `providerFromSignInMethod` (the inverse of the existing
`signInMethodFromPath`) as a small, independently-tested pure function.
Wired it into `databaseHooks.session.create.after` — the hook that already
fires on every successful session creation (it's what updates
`SaUser.lastLoginAt`, bug-0186) — to call `recordFederationEvent({type:
'social.signin.ok', ...})` when the session's `signInMethod` is a federated
one.

Verified `session.signInMethod` is actually available in this hook at
runtime (not just typed loosely): read
`better-auth@1.6.11/dist/db/with-hooks.mjs`'s `createWithHooks` — the
`before` hook's returned `data` is merged into what gets inserted, and the
same inserted row (including `signInMethod`) is what's passed to `after`.

**Deliberately out of scope for this fix:** `'social.link.created'` and
`'social.link.removed'` still have no emitter. Detecting "this session
create was the FIRST time this provider identity linked to this user" vs.
"an already-linked identity signing in again" requires either querying
`Account` before/after or hooking BetterAuth's own account-linking
internals (the codebase's own `classify-callback-outcome.ts` comments
document how deep that archaeology gets for the rejection path alone).
Scoping this fix to the mechanical, low-risk half (successful sign-in,
which the existing hook infrastructure already supports) rather than
attempting the harder linking-detection logic inside an autonomous review
run. Noted in today's TODO as follow-up work.
