# bug-0261: `resolveSeedPassword` treats an unset `NODE_ENV` as `development`, defeating today's own seed-password hardening

**Severity:** Critical (credential exposure)
**Status:** Open — fix included in this PR, pending merge
**Fixed:** false
**Introduced by:** `3b6078f` ("chore: prepare repository for public release", 2026-08-18) — the very commit that added this safety check.

## Description

`3b6078f` (part of today's 34-day-freeze-breaking batch — see
[CHANGELOG.md](../../../CHANGELOG.md)) added `resolveSeedPassword` specifically so
that "seeding any other environment now throws rather than provisioning platform
admins — including the super admin — with a publicly known password." The
implementation:

```ts
const nodeEnv = env.NODE_ENV ?? 'development';
if (!DEV_LIKE.has(nodeEnv)) {
  throw new Error(/* ... */);
}
```

treats a **missing** `NODE_ENV` the same as an *explicit* `NODE_ENV=development` —
i.e. the fail-safe check only fires when `NODE_ENV` is set to something it
recognizes as unsafe. An unset `NODE_ENV` is a common real-world condition: a bare
`node`/`ts-node` invocation, many container base images, some PaaS deployment
targets, or simply a deploy script that forgot the line. In every one of those
cases, this "hardening" silently does nothing and seeds `s@sa.io` (the super admin)
and 6 other platform admins with the publicly documented password
`Pass@word1234` — exactly the outcome the commit describes preventing.

The existing test suite had already encoded this as intended behavior
(`seed-password.spec.ts`: *"returns the documented dev default when NODE_ENV is
unset"*), so this wasn't caught by the commit's own tests — the test proved the
function did what it was written to do, not that what it was written to do was
safe.

## Files

- `apps/auth-server/src/seed/seed-password.ts:25` — the `?? 'development'` fallback.
- `apps/auth-server/src/seed/demo-multitenant.ts:14`,
  `apps/auth-server/src/seed/demo-resource-server.ts:57` — both call
  `resolveSeedPassword()` with no arguments and inherit the same gap.

## Fix (this PR)

- `resolveSeedPassword` no longer defaults an unset `NODE_ENV` into the permissive
  branch — only an explicit `development` or `test` is accepted; anything else,
  including unset, throws.
- To keep the documented local quickstart working (`cp .env.example .env.local`
  then `pnpm --filter @sassy-auth/db db:seed`), `.env.example` now sets
  `NODE_ENV=development` explicitly, so local development affirmatively declares
  itself instead of relying on the previously-permissive default. CI is unaffected
  — the e2e workflow already sets `NODE_ENV: test` directly.
- `seed-password.spec.ts` updated: the "unset NODE_ENV" case now asserts a throw
  (referencing this bug number), plus a new case confirming an unset `NODE_ENV`
  still seeds correctly when `SEED_ADMIN_PASSWORD` is supplied explicitly.

## Verification

- `npx jest src/seed/seed-password.spec.ts` — 10/10 passing, including the new and
  updated fail-closed cases.
- Traced both call sites that invoke `resolveSeedPassword()` with the real
  `process.env` (`demo-multitenant.ts`, `demo-resource-server.ts`) — both inherit
  the fix automatically since neither passes its own env object.
- Confirmed CI does not regress: `.github/workflows/e2e.yml` sets `NODE_ENV: test`
  directly in the job env, independent of `.env.local`/`.env.example`.
