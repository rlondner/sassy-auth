# bug-0262: first completed e2e run in 34+ days surfaces 5 failing tests across unrelated areas — needs investigation

**Severity:** Critical (unknown blast radius — could be CI flakiness or real regressions)
**Status:** Open
**Fixed:** false
**Found by:** verifying [bug-0259](./bug-0259.md)'s fix (PR #335) — once the login-setup blocker was removed, this became the first `admin-e2e` run to reach the actual test suite since 2026-07-09.

## Description

PR #335's own CI run (`gh run view 32265048205`) is the first `admin-e2e` execution
in over a month to get past the `[setup]` project. Result: **108 passed, 5 failed**
(20.2 minutes). The failures span unrelated features, which argues against a single
obvious root cause in any one of them:

1. `tests/2fa-enforcement.spec.ts:159` — "RS round-trip with enrolled tfa@sa.io →
   JWT amr contains mfa" — `requestfailed POST /login/two-factor?next=...`
2. `tests/multitenant-tenant-admin.spec.ts:21` — "Tenant admin (acme-admin) sees
   only their own scope" — `requestfailed POST /login — net::ERR_ABORTED`
3. `tests/otp-signin.spec.ts:9` — "active user signs in with an emailed code" —
   `Error: test-only OTP endpoint should return the stored code` /
   `Received: false` at `pages/login.page.ts:49`
4. `tests/rs-round-trip.spec.ts:46` — "FastAPI RS round-trip ... Signed in" —
   `requestfailed POST /login?next=...`
5. `tests/two-factor.spec.ts:186` — "password login → TOTP → authorize code
   issued" — `Error: GET /api/apps failed: 401 Unauthorized` at
   `lib/oauth-fixtures.ts:42`
6. `tests/authed/admin-nav.spec.ts:27` (chromium-super project) — "stays signed in
   and sidebar highlights the active route" — `TimeoutError: page.waitForURL`
7. `tests/matrix/roles.matrix.spec.ts:40` — "Create row appears in table" —
   `expect(locator).toBeVisible() failed`

(Playwright's summary line reports "5 failed" — some of the above are the same
underlying test counted once per retry/project; the unique-spec list above is what
matters for triage.)

## Leading hypothesis: dev-server resource contention, not a deterministic bug

The admin Next.js dev server log (`[WebServer]` lines) shows, in the same failure
window:

```
[WebServer]  ⨯ [Error: aborted] { code: 'ECONNRESET' }
[WebServer]  ○ Compiling /_error ...
[WebServer]  GET /permissions 200 in 3208ms
```

and again a few seconds later for a different route. This is the dev server
dropping an in-flight connection and falling back to its error page mid-request —
consistent with the shared GitHub Actions runner running Postgres + auth-server +
admin (Next dev, which compiles routes on first hit) + FastAPI resource-server +
many parallel Playwright projects simultaneously, for the first time against the
current (much larger, post-2FA, post-multitenant) codebase. Several of the failures
above (`net::ERR_ABORTED`, `page.waitForURL` timeouts, "waiting for navigation
until load") are exactly what a client sees when the server it's talking to hangs
or resets a connection.

The OTP (`test-only OTP endpoint should return the stored code`) and `/api/apps`
401 failures could be downstream/cascading effects of the same instability (a
request that should have set up test fixture state silently failed earlier), rather
than independent regressions — but this isn't confirmed.

**Ruled out:** the Express-level auth rate limiter (`bbfef27`, bug-0232, shipped in
the same 08-18 batch) is not the cause — `createDefaultAuthRateLimiter` explicitly
sets `max: 10_000` under `NODE_ENV=test`, and CI sets `NODE_ENV: test` directly, so
the 10/min/IP production limit does not apply here.

## Why this isn't fixed in this PR

Unlike [bug-0259](./bug-0259.md) (a single, precisely-located test-harness gap) and
[bug-0261](./bug-0261.md) (a single-function logic fix), this finding spans 5+
unrelated specs with a hypothesis, not a confirmed root cause. Guessing at a fix
here — e.g. bumping timeouts, adding retries, or reducing parallelism — without
first confirming whether these are flaky-under-load or genuine regressions risks
either masking a real bug or landing a change that doesn't actually help. The
responsible next step is a rerun (to see if the same 5 fail again, which would argue
against pure flakiness) and, if they repeat, a focused investigation per failure.

## Suggested next steps

1. Re-run PR #335's `admin-e2e` job (or push an empty commit) to see whether the
   same 5 tests fail again — repetition would rule out pure resource-contention
   flakiness and point at real regressions from the 2FA/multitenant features that
   merged at `a78d4a7` and have never had a completed e2e run since.
2. If they repeat, investigate each independently — they may not share a root
   cause despite the superficial `ECONNRESET`/timeout pattern.
3. Consider whether the CI runner needs more resources (or the Playwright config
   needs fewer parallel workers) now that `master` is actually moving again and
   e2e runs are no longer silently skipped by the setup failure.
