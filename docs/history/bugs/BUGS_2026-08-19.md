## New bugs (3)

### [bug-0259](./bug-0259.md) :red_circle: Critical — `master` e2e CI has been red for 34 days; the login setup never learned to dismiss the 2FA interstitial

**Fixed:** false (fix included in PR #335, pending merge + confirmed-green CI)

**Files:** `apps/admin-e2e/auth-state.setup.ts`, `apps/auth-server/src/auth/should-prompt-two-factor.ts`

**Summary:** Every seeded admin (`a@sa.io`, `o@sa.io`, `u@sa.io`, `r@sa.io`,
`p@sa.io`, `s@sa.io`) has `twoFactorEnabled: false` and no recorded
`twoFactorPromptedAt` on a fresh CI database, so `shouldPromptTwoFactor` always
routes them to `/login/two-factor-prompt` after login. `auth-state.setup.ts` — the
Playwright global-setup project every other e2e spec depends on — asserts the final
landing URL immediately after submitting the login form and never handles this
interstitial, unlike three other spec files in the same suite that already do. The
result: `master`'s `admin-e2e` GitHub Actions workflow has failed on **every single
push since `a78d4a7`** (2026-07-15, the commit that merged the 2FA feature) — the
last green run was 2026-07-09. This went uncaught through the entire 34-day freeze
because the daily review checks PR/commit activity via the GitHub API, not the
Actions dashboard.

**Fix:** `auth-state.setup.ts` now waits for either the landing page or the
interstitial and clicks "Skip for now" if it lands on the latter — the same pattern
already used in `two-factor.spec.ts`, `2fa-enforcement.spec.ts`, and
`rs-round-trip.spec.ts`. Test-harness-only change; no production/seed code touched.

### [bug-0261](./bug-0261.md) :red_circle: Critical — `resolveSeedPassword` silently no-ops when `NODE_ENV` is unset, defeating the safety check added the same day

**Fixed:** false (fix included in PR #337, pending merge)

**Files:** `apps/auth-server/src/seed/seed-password.ts`, `.env.example`

**Summary:** `3b6078f` (part of today's unfreeze batch) added `resolveSeedPassword`
specifically to stop the well-known default admin password
(`Pass@word1234`) from being provisioned outside development/test. Its
`env.NODE_ENV ?? 'development'` fallback treats a **missing** `NODE_ENV` as an
explicit `development`, so any deployment that simply forgets to set it — a common
gap in bare `node`/container/PaaS invocations — silently seeds every platform
admin, including the super admin `s@sa.io`, with the public password. The commit's
own test suite had encoded this as intended, so it went uncaught. Found by a
background review pass over all 17 commits in today's `master` batch.

**Fix:** `resolveSeedPassword` now fails closed on unset `NODE_ENV`; `.env.example`
sets `NODE_ENV=development` explicitly so the documented local quickstart is
unaffected. CI already sets `NODE_ENV: test` directly, so it's unaffected too.
