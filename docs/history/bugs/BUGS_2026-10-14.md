## bug-0297 🔴 High — admin-proxied login, OTP/TOTP/backup-code verify, and password-reset calls share one rate-limit bucket (same root cause `110ce7a` just fixed for signup)

**Fixed:** false (fix coded in this review — see PR
[#456](https://github.com/rlondner/sassy-auth/pull/456), branch
`bug-0297`, open against `dev` as of this writing)

**Files:**
- `apps/admin/app/login/actions.ts` (`signIn`, `requestOtp`, `verifyOtp`,
  `verifyTotp`, `verifyBackupCode`)
- `apps/admin/app/forgot-password/actions.ts` (`requestPasswordResetAction`)
- `apps/admin/app/reset-password/actions.ts` (`resetPasswordSubmitAction`)

**Description:** Today's reviewed commit, `110ce7a`, fixed
`RateLimitGuard`/`AppLookupRateLimitGuard` (used by `GET /api/register/app`)
to key on `resolveClientIp()` instead of raw `req.ip`, because that endpoint
is called server-to-server from the admin console and `req.ip` resolves to
the admin server's own egress address for every visitor — collapsing every
browser's signup-page load onto one shared budget.

The exact same mechanism protects every other credential-bearing BetterAuth
endpoint: `apps/auth-server/src/auth/auth-rate-limit.ts`'s `clientKey` (one
shared bucket across `/sign-in`, `/sign-up`, `/forget-password`,
`/reset-password`, `/magic-link`, `/email-otp`, `/two-factor`, per its
`SENSITIVE_PREFIXES` list) also calls `resolveClientIp()`, which prefers the
left-most `X-Forwarded-For` entry over the raw socket peer. That only
recovers the real client when the caller actually re-sends the browser's
`X-Forwarded-For` header on its outgoing server-to-server `fetch()` —
`apps/admin/lib/forward-client-ip.ts`'s `getForwardedClientIpHeader()`
exists for exactly this, and `apps/admin/app/signup/actions.ts`,
`apps/admin/app/signup/wizard-actions.ts`, `apps/admin/lib/app-info.ts`, and
`apps/admin/app/login/consent/actions.ts` all already call it (added in
`593e82c`).

`apps/admin/app/login/actions.ts` (`signIn`'s `POST
/api/auth/sign-in/email`, `requestOtp`'s `send-verification-otp`,
`verifyOtp`'s `sign-in/email-otp`, `verifyTotp`'s
`two-factor/verify-totp`, `verifyBackupCode`'s
`two-factor/verify-backup-code`), `apps/admin/app/forgot-password/actions.ts`
(`request-password-reset`), and `apps/admin/app/reset-password/actions.ts`
(`reset-password`) never picked up that helper — each only forwards
`Origin` (and, where relevant, specific named cookies), never
`X-Forwarded-For`. Every one of those BetterAuth paths is in
`SENSITIVE_PREFIXES`, so `resolveClientIp()` sees the admin server's own
egress address for all of them, the same way it did for `GET
/api/register/app` before today's fix.

**Failure scenario:** Two different visitors sign in (or request a
password-reset / OTP / TOTP challenge) through the admin console within the
same rate-limit window. Both requests key on the admin server's own egress
IP rather than their own addresses, so they share one budget: one
visitor's failed login attempts (or an actual credential-stuffing
attacker's) can exhaust the shared bucket and make a *different*,
legitimate visitor's next login attempt bounce with 429 — the inverse of
the brute-force protection this limiter exists to provide, and the same
"combined load across visitors trips a shared bucket" failure class
documented in `main-trust-proxy.spec.ts`'s bug note (2026-09-17, sporadic
429s on `GET /api/social-providers`), just one layer further down the call
chain (admin → auth-server, not browser → auth-server).

**Fix applied:** Added the same `getForwardedClientIpHeader()` call and
header spread already used by `signup`/`consent`/`wizard` actions to every
touched call site in `login/actions.ts`, `forgot-password/actions.ts`, and
`reset-password/actions.ts`. See PR #456 for the full diff and new
regression tests (one per action, asserting the header is forwarded when
present and omitted when absent).

**Not in scope for this fix:** `apps/admin/app/account/security/actions.ts`
(`two-factor/enable`, `two-factor/verify-totp`, `two-factor/disable`,
`two-factor/generate-backup-codes`, `revoke-other-sessions`) has the same
gap, but every one of those calls requires an already-authenticated admin
session (forwarded via the existing session cookie), so the anonymous
brute-force exposure this bug is about doesn't apply there the same way —
an attacker without a valid session cookie gets a 401 before the rate
limiter's bucket choice matters. Still worth closing for defense-in-depth
and bucket-sharing consistency; carried to `TODO_2026-10-14.md` rather than
bundled into this PR to keep it reviewable.

**Verification:** `apps/admin`'s full Jest suite (736 tests, 88 suites) and
`tsc --noEmit` both pass on the fix branch with no new failures. Manual
trace of the full proxy chain (browser → Render edge in front of admin →
admin server → Render edge in front of auth-server → auth-server) confirms
`main.ts`'s existing `trust proxy: 1` setting correctly treats the
Render-edge hop in front of auth-server as the one trusted proxy and
`admin`'s re-sent header as the (correct) client-supplied value — the same
reasoning already applies to the signup-side fix PR #445/`593e82c` covers,
so no new `trust proxy` changes were needed, only the missing header
forward on these specific actions.
