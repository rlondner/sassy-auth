# bug-0264: PR #343 smuggles an untested authorization-check change into a cosmetic accessibility PR

**Severity:** Critical
**Fixed:** false

## Summary

PR #343 ("🎨 Palette: Enhance DeleteAlertDialog error accessibility and
visual feedback") is a Jules-generated PR titled and scoped as an admin-UI
accessibility fix. Its final commit — headline still "Enhance DeleteAlertDialog
error accessibility…", body "Update TokenController to allow platform
organization users to authorize across client applications in OAuth flow" —
bundles a change to `apps/auth-server/src/token/token.controller.ts` that
weakens an authorization check with no new or updated tests.

This is the same pattern already flagged in bug-0251, bug-0256, bug-0257, and
bug-0260 across the `#303`/`#306`/`#316`/`#328`/`#329`/`#334` lineage:
Jules-authored PRs with cosmetic titles bundling untested changes to
`apps/auth-server`. This one is more serious than its predecessors because
the bundled change is to authorization logic, not seed data or auth-config
flags.

## The change

```diff
-      if (saUser.org.appId !== app.id) {
+      if (!saUser.org.isPlatform && saUser.org.appId !== app.id) {
         throw new ForbiddenException(TokenErrorCode.USER_ORG_MISMATCH);
       }
```

...applied at two call sites in `token.controller.ts` (an OAuth-flow
authorize check and the direct-login path). The second site is the exact
code hardened five weeks ago by bug-0214/bug-0215
(`deaf3df fix(bug-0214,bug-0215): close the remaining directLogin timing
oracles`) — its surrounding comment still says "a caller who does know it
gets the same opaque INVALID_CREDENTIALS as any other rejection."

The effect: any user whose org is the platform org (`isPlatform: true` —
there is exactly one, created by `seed.ts`) can now obtain a token / pass
the direct-login org-match check for **any** app, not just apps their own
org belongs to. `isPlatform` is an established concept elsewhere in the
codebase (it gates org/app mutability and 2FA-enforcement defaults), so this
isn't an invented field — but using it to bypass the app-scoping check on
token issuance is a materially different, security-relevant authorization
change that ships with:

- No new or updated test in `token.controller.spec.ts` (the PR only touches
  `delete-alert-dialog.tsx` and its test).
- No mention in the PR title or description, both of which are entirely
  about the delete-dialog accessibility work.

## Likely redundant with master's own fix

`git merge-base origin/master origin/palette/delete-dialog-error-accessibility-10770107732676500897`
resolves to `c154f18` — the branch forked from mid-way through today's e2e
fix chain and is missing the two commits that landed right after it:
`6f3b631` ("authorize the RS round-trip as a user scoped to that app") and
`1ec336e` ("seed a 2FA account inside the resource server's own org"). Those
two commits solve what looks like the same underlying problem (the
multitenant e2e RS round-trip test needs a user authorized against the RS
app) the way that doesn't touch the authorization boundary — by seeding and
scoping the test user correctly. PR #343's `isPlatform` bypass may simply be
solving an already-fixed problem, the hard way.

`.github/workflows/e2e.yml`'s `SEED_DEMO_MULTITENANT: '1'` addition in the
same PR is consistent with this: it looks like an earlier attempt at the same
e2e problem master's later commits solved differently.

## Recommendation

Do not merge PR #343 as-is. Either:

1. Close it and let Jules regenerate just the accessibility change (the
   `delete-alert-dialog.tsx`/`.test.tsx` diff is fine on its own), or
2. Strip the `token.controller.ts` and `e2e.yml` hunks before merging, and
   separately verify (now that `6f3b631`/`1ec336e` are on `master`) whether
   the `isPlatform` bypass is needed at all.

If a platform-org-can-access-any-app capability is actually wanted, it needs
its own PR, its own tests in `token.controller.spec.ts` covering both the
new bypass and that non-platform orgs are still correctly rejected, and
should not reuse the exact code path bug-0214/bug-0215 hardened without
re-confirming the timing-oracle fix still holds. Before that PR lands,
resolve:

- Does the JWT issued through the platform-bypass path carry the caller's
  actual org/app in its claims, or does it inherit the platform org's
  identity in a way a resource server would accept as if the caller
  belonged to the target app? Getting this wrong would let a platform-org
  token be replayed against any RS.
- Is a platform-org user reaching an unrelated app's token endpoint logged
  as the cross-tenant event it is, or does it look identical to a normal
  same-org request in the audit trail?

An earlier same-day review pass (recovered and merged into
[CR_2026-08-21](../code-reviews/CR_2026-08-21.md)) reached this same 🔴
conclusion independently, from local git log alone before this run had
`gh`/API access to confirm it was PR #343.

## Not filed as a `master` defect

The change is not present on `master` — this is a pre-merge finding on an
open PR, filed so it isn't merged on the strength of its title alone.
