# bug-0299 🔴 Critical — four CRITICAL CVEs live on `dev` since before 2026-10-21, invisible because the daily Trivy scan never hard-fails outside a PR

**Fixed:** false

**Files:**
- `apps/admin/package.json` (`@sentry/nextjs`, `next`)
- `apps/auth-server/package.json` (`better-auth`, `@better-auth/utils`)
- `package.json` (new `pnpm.overrides.dompurify`, for the transitive `redoc` dependency)
- `pnpm-lock.yaml`
- `.github/workflows/trivy.yml`

**Description:** `pnpm-lock.yaml` on `dev` (unchanged since `b481bc2`,
2026-11-03) pins four packages with published CRITICAL CVEs, none of which
have ever caused a visible CI failure on `dev` itself:

| Library | Installed | Vulnerability | Fixed version |
|---|---|---|---|
| `@sentry/nextjs` | 10.54.0 | CVE-2026-114139 — Sentry middleware bypass via Tunnel route | 10.75.2 |
| `better-auth` | 1.6.11 | CVE-2026-114607 — OAuth state usable as a Magic Link to sign in as another user | 1.7.7 |
| `dompurify` (transitive, via `redoc`) | 3.4.15 | GHSA-cg2g-xh64-v4q7 — `SAFE_FOR_TEMPLATES` bypass, template expressions survive in shadow-root content | 3.4.17 |
| `next` | 15.5.25 | GHSA-2464-fhr4-w9xw — unauthenticated RCE in the Image Optimization API for SVGs | 15.5.28 |

The `better-auth` one (OAuth state reusable as a magic link) is the most
concerning for an auth product specifically.

**Why it went unnoticed:** `.github/workflows/trivy.yml` runs two Trivy
steps. The first (`Generate SARIF Report`) always runs and uploads to the
Security tab, but never fails the job. The second — the one that actually
turns CI red — was gated `if: github.event_name == 'pull_request'` only:

```yaml
- name: Enforce PR Block on Critical CVEs
  if: github.event_name == 'pull_request'
```

The workflow also runs on a daily `schedule` trigger specifically "to
catch new vulnerabilities even if no code changes occur" (per its own
comment), but the schedule-triggered run skips the only step that can fail
the build — it only re-uploads a SARIF nobody is watching. Confirmed by
diffing the failing run on PR #467 (`gh run view 42057206230 --log-failed`,
4 CRITICAL findings, exit code 1) against the same day's scheduled run on
`dev`, and again against today's scheduled run (`gh run view
42766901247` / job `129665401946`) — both green, same unchanged
`pnpm-lock.yaml`. This is also why the issue was never caught by any prior
daily-review run: `dev`'s own CI status (the only thing those reviews
check) has stayed green through all of it.

**Failure scenario:** An attacker captures or predicts an OAuth `state`
value issued to another user (e.g. via referrer leakage, a shared/XSS'd
subdomain, or log exposure) and replays it as a Magic Link to sign in as
that user — no password or token required (CVE-2026-114607). Separately,
a crafted SVG through `next/image`'s Image Optimization API can reach
unauthenticated RCE (GHSA-2464-fhr4-w9xw) on any deployment that serves
untrusted image URLs through it. Both have been exploitable on `dev` for
at least 20 days with no CI signal.

**Fix:**
1. Bump `@sentry/nextjs` to `^10.75.2` and `next` to `^15.5.28` in
   `apps/admin/package.json`.
2. Bump `better-auth` to `^1.7.7` in `apps/auth-server/package.json`
   (pulled in `1.7.20`); bumped its peer `@better-auth/utils` from
   `^0.4.0` to `^0.5.1` to satisfy `better-auth`'s new peer range.
3. Added `pnpm.overrides.dompurify: ">=3.4.17"` to the root
   `package.json` — `dompurify` is a transitive dependency of `redoc`
   (used by `apps/auth-server` for OpenAPI docs rendering), which has not
   released a version pinning the patched `dompurify` yet.
4. Regenerated `pnpm-lock.yaml` via `pnpm install --no-frozen-lockfile`.
5. Changed `.github/workflows/trivy.yml`'s `Fail build on Critical CVEs`
   step to also run `if: ... || github.event_name == 'schedule'`, so a
   newly-published CVE against an already-merged dependency turns the
   daily scheduled run red instead of only appearing in the Security tab.

**Verification:** `pnpm install --no-frozen-lockfile` completed cleanly
(no unmet peer warnings after the `@better-auth/utils` bump). Confirmed
the new resolved versions in `pnpm-lock.yaml`
(`@sentry/nextjs@10.78.0`, `better-auth@1.7.20`, `dompurify@3.4.17`,
`next@15.5.29` — all past their fixed versions). Ran
`pnpm run lint --filter=admin --filter=auth-server`,
`pnpm run build --filter=admin --filter=auth-server`, and
`pnpm run test --filter=auth-server` — all green. Trivy's own CI job on
this PR is the authoritative verification that the CRITICAL findings are
gone (no local `trivy` binary available in this environment).
