## :yellow_circle: bug-0050 — `apiFetch` discards server error response body; admin UI shows generic messages

**Fixed:** false
**Severity:** Warning
**File:** `apps/admin/lib/api.ts` (line 18)

**Description.** The centralized `apiFetch` helper throws on non-2xx responses but never reads the response body:

```typescript
if (!res.ok) throw new Error(`API error ${res.status}: ${path}`)
```

When the auth-server returns structured error details in the response body (validation messages like "Name is required", conflict messages like "Email already exists", or NestJS exception responses with `message` and `statusCode`), they are discarded. The admin console catches the error and renders a generic "Something went wrong" or "API error 400" message. Users have no indication of what went wrong or how to fix their input.

This affects every mutation in the admin UI: create user, update org, assign role, etc.

**Fix sketch.** Read the response body before throwing:

```typescript
if (!res.ok) {
  let detail: string
  try {
    const body = await res.json()
    detail = body.message ?? JSON.stringify(body)
  } catch {
    detail = `status ${res.status}`
  }
  throw new Error(detail)
}
```

**Tests needed.** Unit test verifying that `apiFetch` surfaces the server's error message. Integration test confirming the admin UI renders actionable error text for common 400/409/422 responses.

## :yellow_circle: bug-0051 — Invitation token leaked in Error message strings

**Fixed:** false
**Severity:** Warning
**Files:**
- `apps/admin/lib/api.ts` (line 168)
- `apps/admin/lib/api-public.ts` (line 7)

**Description.** Both `validateInvitation` implementations include the raw invitation token in the Error message:

```typescript
if (!res.ok) throw new Error(`API error ${res.status}: /api/invitations/${token}`)
```

This is distinct from bug-0002 (invitation tokens in HTTP request URL logs). Here, the leak path is through the Error object's `message` property, which can propagate to:

1. **Sentry error tracking** — `Sentry.captureException(err)` sends the full message, including the token, to the Sentry dashboard.
2. **Next.js error boundaries** — `error.tsx` renders `error.message` to the browser.
3. **Browser console** — unhandled rejections print the full message.
4. **Server-side logs** — any Winston/console catch handler that logs `err.message`.

An attacker with access to any of these channels could extract invitation tokens and use them to activate accounts or set passwords for other users.

**Fix sketch.** Remove the token from the error message:

```typescript
if (!res.ok) throw new Error(`Invitation validation failed (${res.status})`)
```

**Tests needed.** Unit test asserting that the error message from `validateInvitation` does not contain the input token.

## :large_blue_circle: bug-0052 — `getEffectivePermissions` synthesizes Permission objects with fake IDs

**Fixed:** false
**Severity:** Minor
**File:** `apps/admin/lib/api.ts` (line 124)

**Description.** The auth-server's `GET /api/users/:id/effective-permissions` endpoint returns `{ userId: string, permissions: string[] }` (permission names only). The admin client wrapper needs to return `Permission[]` (with `id`, `name`, `appId`), so it synthesizes fake objects:

```typescript
return body.permissions.map((name) => ({ id: name, name, appId: '' }))
```

This creates Permission objects where:
- `id` equals the permission name (a string like `"platform.users.manage"`), not a Sqid identifier.
- `appId` is an empty string, not a valid app identifier.

If any downstream component uses `permission.id` for an API call (e.g., `deletePermission(permission.id)`, `updatePermission(permission.id, ...)`), the auth-server will receive a name string where it expects a Sqid, resulting in a 404 or unexpected behavior.

Currently the effective permissions drawer is read-only, so this is latent. It becomes a bug when anyone adds inline actions (edit, remove) to the effective permissions view.

**Fix sketch.** Either:
1. Extend the auth-server endpoint to return full Permission objects (with `publicId` and `appId`), or
2. Add a distinct return type (`EffectivePermission = { name: string }`) to the client instead of reusing `Permission[]`, making the type system enforce that only the name is available.

**Tests needed.** If option 1: verify the endpoint returns `publicId` and `appId`. If option 2: verify the drawer component does not access `.id` or `.appId`.

## :large_blue_circle: bug-0053 — Missing `setTimeout` cleanup in drawer components and accept-invite form

**Fixed:** false
**Severity:** Minor
**Files:**
- `apps/admin/components/app-edit-drawer.tsx` (line 98)
- `apps/admin/components/app-view-drawer.tsx` (line 24)
- `apps/admin/components/org-edit-drawer.tsx` (line 84)
- `apps/admin/components/org-view-drawer.tsx` (line 25)
- `apps/admin/components/role-edit-drawer.tsx` (line 127)
- `apps/admin/components/role-view-drawer.tsx` (line 40)
- `apps/admin/components/permission-edit-drawer.tsx` (line 84)
- `apps/admin/components/permission-view-drawer.tsx` (line 42)
- `apps/admin/components/user-create-drawer.tsx` (line 125)
- `apps/admin/app/accept-invite/accept-invite-form.tsx` (line 42)

**Description.** Multiple components use `setTimeout` in click handlers without storing the timer ID or providing cleanup:

```typescript
// In drawer copy-to-clipboard handlers:
setCopied(true)
setTimeout(() => setCopied(false), 2000)

// In accept-invite form:
setTimeout(() => router.push('/login'), 2000)
```

If the component unmounts before the 2-second timeout fires (e.g., user closes the drawer or navigates away), the callback will attempt to update state or navigate on an unmounted component. React 18 silently ignores state updates after unmount, but this can cause:
- A stale navigation in the accept-invite form (user closes the page, then gets unexpectedly redirected 2 seconds later).
- Console warnings in development mode.
- Potential issues under React 19+ strict mode.

The main data tables (`apps-table.tsx`, etc.) correctly clean up their debounce timers in `useEffect`, showing the pattern is known but not applied to click-handler timeouts.

**Fix sketch.** Use a ref to track the timer and clean up on unmount:

```typescript
const timerRef = useRef<ReturnType<typeof setTimeout>>()
useEffect(() => () => clearTimeout(timerRef.current), [])

// In click handler:
setCopied(true)
timerRef.current = setTimeout(() => setCopied(false), 2000)
```

**Tests needed.** Unit test verifying no state update occurs after unmount (render, trigger copy, unmount, advance timers).
