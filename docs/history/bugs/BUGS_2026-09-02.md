### bug-0277 🟡 Medium — OIDC discovery doc advertises a logout endpoint that doesn't exist

**Files:**
- `apps/auth-server/src/token/oauth-metadata.ts`

**Description:** `/.well-known/openid-configuration` advertised
`end_session_endpoint` at `/api/token/oauth/logout`, but no controller
route was ever registered for it — RP-Initiated Logout was in the
original OIDC design doc as its own task, but only the discovery
advertisement and an unused `assertPostLogoutRedirectUriAllowed` helper
shipped, not the controller. A conformant relying party calling the
advertised endpoint gets a 404. See
[bug-0277.md](./bug-0277.md) for the full writeup.

**Fix:** PR #370. Removed `end_session_endpoint` and the unused
`OAUTH_LOGOUT_ROUTE` constant from the discovery doc until the endpoint
is actually implemented. **Verified:** `npx tsc --noEmit` in
`apps/auth-server` — no errors; `npx jest --testPathPattern=oauth-metadata`
— 14/14 pass; `npx jest --testPathPattern="discovery.controller|token.controller"`
— 46/46 pass.

**Fixed:** false

## Verified — not filed

- **`id_token` signing** (`token.service.ts:issueIdToken`) — signed RS256
  with the same key/`kid` as the access token and JWKS doc, includes
  `at_hash` computed correctly per the OIDC Core spec (SHA-256 left half,
  base64url, matching the RS256 alg), `auth_time`, `amr`, and `nonce` only
  when one was presented. `sub`/`aud`/`iss`/`org` all match the access
  token's claims. No issue found.
- **`nonce` validation** — this server *carries* `nonce` end-to-end
  (query param → `SaOauthCode.nonce` → `id_token.nonce`) but does not
  itself validate it, which is correct per spec: nonce validation is the
  *relying party's* responsibility (compare the returned `id_token`'s
  `nonce` against the one it generated and stored client-side before the
  redirect), not the authorization server's. Nothing to fix here, but
  flagged in TODO as a documentation gap — nothing in the README's new
  OIDC section says the RP must do this.
- **PKCE timing-safe comparison** (`oauth.service.ts:exchangeCode`) —
  `crypto.timingSafeEqual` restored (per `b2af7a2`'s commit message) and
  correctly guarded by a length check first (`timingSafeEqual` throws on
  mismatched buffer lengths rather than returning `false`, which the code
  handles by checking `expected.length !== actual.length` before calling
  it). No issue found.
- **`redirect_uri` registered-set matching** (`redirect-uri.ts`) —
  exact-match protocol+host+port+path+query with tolerance for exactly one
  trailing slash, same-origin fallback preserved for apps with zero
  registered URIs (pre-migration behavior). `post_logout` kind has no
  caller yet (expected — no logout endpoint exists, see bug-0277).
- **Prisma migration** (`20260821203951_oidc_compatibility`) — additive:
  new `SaAppRedirectUri` table, nullable `SaApp.clientSecretHash`/
  `clientSecretUpdatedAt`, nullable `SaOauthCode.nonce`, defaulted
  `SaOauthCode.scope`/`authTime`, `codeChallenge`/`codeChallengeMethod`
  relaxed from `NOT NULL` to nullable (widening, not narrowing). The
  `callbackUrl` drop is preceded by an `INSERT ... SELECT` backfill into
  the new table for every app with a non-null/non-empty `callbackUrl`,
  landing before the `DROP COLUMN`. No data loss, no breaking change for
  existing sessions or codes.
- **New rate-limit env vars** (`DEFAULT_RATE_LIMIT`,
  `DEFAULT_RATE_WINDOW_MS`, `AUTH_RATE_LIMIT`, `AUTH_RATE_WINDOW_MS`) —
  `envInt()` in `app.module.ts` treats unset, blank, zero, negative, and
  non-numeric values all as "use the fallback" (`120`/`60_000`/`10`/
  `60_000` respectively), so misconfiguration fails toward the
  conservative built-in default rather than toward unlimited/disabled.
  Confirmed this differs on purpose from `REGISTER_RATE_LIMIT`'s existing
  "`0` = unlimited" semantics (a pre-existing, unrelated guard) — noted in
  TODO as worth a one-line README callout since the two "similar-looking"
  rate-limit knobs now behave differently on `0`.
- **Login `next=` open-redirect risk** (`4dd3e4b`, `5e24b3e`) — the
  absolute `next` URL is built from `resolveIssuer()` (server-controlled
  `BETTER_AUTH_URL`) + a fixed path constant; the only attacker-influenced
  input (`client_id`, `redirect_uri`, `state`, `scope`, `nonce`) is
  appended as encoded query-string values on that fixed origin+path, never
  concatenated into the host or scheme. No open-redirect vector found.
- **`claims_supported` / `response_types_supported` /
  `grant_types_supported`** in the discovery doc — cross-checked against
  the real implementation: `code` / `authorization_code` only (no implicit
  or refresh-token grant exists, and the doc correctly omits
  `offline_access`/`refresh_token`, per the existing
  `oauth-metadata.spec.ts` assertion). `claims_supported` lists exactly
  the claims `issueIdToken`/`buildScopedClaims` can actually emit. No
  issue found beyond `end_session_endpoint` (bug-0277).
