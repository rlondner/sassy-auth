# bug-0259: `master` e2e CI has been red for 34 days — every seeded admin gets stuck on the 2FA interstitial that `auth-state.setup.ts` never learned to dismiss

**Severity:** Critical (CI signal / regression detection)
**Status:** Open — fix included in this PR, pending merge
**Fixed:** false
**Introduced by:** `a78d4a7` ("Merge 2FA (core 2a + per-app enforcement 2b) into master", 2026-07-15) — the 2FA feature merge that finally broke the daily-review's 34-day master freeze on 2026-08-18.

## Description

The `admin-e2e` GitHub Actions workflow has failed on every push to `master` since
`a78d4a7` (2026-07-15) — the commit that merged the 2FA feature. It was still failing
on today's HEAD (`7a56c4e`, 2026-08-18) and on every commit in between
(`546581d`, `6e0a690`, `3b6078f`, `02261fb`, `4b48e45`). The last green run on
`master` was `dbcba1a` on 2026-07-09.

Root cause: `apps/admin-e2e/auth-state.setup.ts` is the Playwright global-setup
project — every other e2e spec depends on it to log in the 6 seeded admins and
capture their storage state before the real tests run. It asserts:

```ts
await expect(page).toHaveURL(/\/(users|apps|orgs|permissions|roles)$/, { timeout: 20_000 })
```

immediately after submitting the login form. But on a fresh CI database none of the
seeded admins have `twoFactorEnabled` or a recorded `twoFactorPromptedAt`, so
`shouldPromptTwoFactor` (`apps/auth-server/src/auth/should-prompt-two-factor.ts:20`)
unconditionally returns `true` and every admin is redirected to the
`/login/two-factor-prompt` interstitial instead. The assertion above never matches,
retries 3× per admin (24s each), and the whole job fails after ~11 minutes with:

```
Received string: "http://localhost:3001/login/two-factor-prompt"
6 failed
```

Every *other* e2e spec that logs in already handles this exact interstitial —
`two-factor.spec.ts`, `2fa-enforcement.spec.ts`, and `rs-round-trip.spec.ts` all
check `page.url().includes('/login/two-factor-prompt')` and click "Skip for now"
before asserting the final destination. `auth-state.setup.ts` is the one login path
in the suite that was never updated for this, because it was last touched before the
2FA feature merged.

## Why this matters beyond the immediate test failure

This is the reason the "master is frozen" narrative in every daily review since
2026-07-15 (`CR_2026-07-20.md` through `CR_2026-08-17.md`) never surfaced a broken
build: the reviews check PR/commit activity via the GitHub API, not the Actions
dashboard. `master`'s CI was silently red for over a month — through the entire 2FA
feature landing — and nobody would have known until the freeze broke and someone
looked at `gh run list`. **Recommend the daily review checks `gh run list --branch
master` going forward** (see today's TODO).

## Files

- `apps/admin-e2e/auth-state.setup.ts` — the login helper missing the interstitial
  handling.
- `apps/auth-server/src/auth/should-prompt-two-factor.ts:20` — the unconditional
  (not gated by `PLATFORM_REQUIRE_2FA`) soft-nudge logic that any user without 2FA
  and a stale/absent `promptedAt` hits on every fresh login.

## Fix (this PR)

`auth-state.setup.ts` now waits for either the normal landing page or the
interstitial, and if it lands on `/login/two-factor-prompt`, clicks "Skip for now"
(the same `getByRole('button', { name: /skip for now/i })` pattern already used in
`two-factor.spec.ts`) before asserting the final URL. This matches real user
behavior — a user declining 2FA enrollment — rather than suppressing the prompt
server-side (which is exactly what [bug-0250](./bug-0250.md) flags as a defect when
PR #316 does it via a seeded `twoFactorPromptedAt`). No production/seed code
changes; this is a test-harness-only fix.
