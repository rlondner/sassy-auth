# bug-0298 🟠 High — `refresh-token.service.spec.ts` compares fixture dates to the real wall clock, going red once the calendar passes them

**Fixed:** false

**Files:**
- `apps/auth-server/src/token/refresh-token.service.spec.ts`
- `apps/auth-server/src/token/refresh-token.service.ts` (unchanged — the bug is in the test, not the production code)

**Description:** `RefreshTokenService.rotate()` rejects a presented token
when `row.expiresAt < now || row.absoluteExpiresAt < now`, using the real
`new Date()` (`refresh-token.service.ts:84,92`). The spec's `existingRow`
fixture hardcodes `expiresAt: new Date('2026-10-17T00:00:00Z')` and
`absoluteExpiresAt: new Date('2026-12-16T00:00:00Z')` as "the valid, not-yet-expired"
case, but three of the `rotate` tests never install fake timers, so `now`
inside the service is the actual system clock. The fixture was valid when
written (comfortably in the future) but became permanently expired the
moment the real calendar passed 2026-10-17 — a classic test time-bomb.

**Failure scenario:** No user-facing impact — this is CI-only. But it has
been **silently red on `dev` since the 2026-10-19 05:34 UTC push
(`4151407`)**, invisible in the normal PR/commit view because that push's
own diff (GCP Cloud Run deploy workflow + Dockerfiles) never touches
`token/`, so nothing about the failure looked related to what shipped.
Confirmed via `gh run view 39205218871 --log-failed` and reproduced locally
on current `dev` HEAD:

```
FAIL token/refresh-token.service.spec.ts
  ● rotates a valid token: ... UnauthorizedException: invalid_grant
  ● rolls back the whole transaction ...: Expected substring "db error", Received "invalid_grant"
  ● concurrent replay ...: updateMany was never called (rotate() threw before reaching it)
```
All three fail at `refresh-token.service.ts:93` — the "expired" branch,
not the behavior each test actually intends to exercise. This masks real
regressions in rotation/rollback/race-handling behind an unrelated,
permanent false failure, and every PR against `dev` now inherits a red
`unit-tests` job unrelated to its own changes (already noted as a shared
annoyance in the untracked 2026-10-20 review draft, but not root-caused
there).

**Fix:** Pin the clock for the whole `describe('rotate', ...)` block with
`jest.useFakeTimers().setSystemTime('2026-10-01T00:00:00Z')` in a
`beforeEach` (before `existingRow`'s `expiresAt`/`absoluteExpiresAt`) and
`jest.useRealTimers()` in an `afterEach`. This decouples the "valid token"
fixtures from wall-clock date entirely — they test relative ordering
(fixture dates vs. a fixed mock "now"), not absolute future dates that will
themselves eventually lapse. The two intentionally-expired-token tests
(`'2020-01-01T00:00:00Z'`) are unaffected since they test the opposite
condition and stay in the past under any fake or real clock.

**Verification:** `pnpm --filter @sassy-auth/auth-server exec jest
refresh-token.service.spec.ts` — 12/12 passing (was 9/12). Also ran the
full `apps/auth-server` suite's `token/` directory to confirm no other spec
in that folder has the same pattern (grepped for hardcoded future
`expiresAt`/`absoluteExpiresAt` literals outside already-fake-timed blocks
— none found).

**Worth a follow-up, not fixed here:** this is the second time-bomb-shaped
test issue this project has hit (first was the 08-19 `master` e2e freeze,
a different mechanism — a missing 2FA-interstitial dismissal, not a clock
issue). Recommend a lint/review habit of flagging any `new Date('20XX-...')`
literal compared against `Date.now()`/`new Date()` in test fixtures without
an adjacent `jest.useFakeTimers()` — noted in today's TODO.
