# bug-0272: AI security review's env-file sanitization glob misses this repo's actual dotenv convention

**Severity:** Warning
**Status:** Open
**Fixed:** false

## Description

`.github/workflows/ai-security-review.yml`'s "Pre-scan Context Sanitization" step exists
specifically to delete secret-bearing files from the checkout before the AI reviewer can
read them:

```bash
find . -name "*.env" -type f -delete
find . -name "*.pem" -type f -delete
find . -name "*_rsa" -type f -delete
```

`find -name "*.env"` only matches filenames that literally *end* in `.env` (`foo.env`,
or the bare `.env` itself, since `*` matches the empty prefix). It does **not** match
this repo's actual dotenv convention — `.env.local`, `.env.production`, or the backup
pattern `.env.local.bak-<timestamp>` documented in `.gitignore`:

```
# The trailing * matters: `.env*.local` alone does not match backup copies such
# as `.env.local.bak-1787084941`, which is how one got committed.
.env*.local
.env*.local.*
.env*.local-*
```

That comment is not hypothetical: this exact file-naming pattern has already been
accidentally committed to this repository once. If a `.env.local`/`.env.production`
-style file ever lands in a PR diff again, this workflow's own hardening step — whose
entire purpose is to strip such files before the AI model reads the tree — silently
does not catch it, because the glob only covers the suffix form.

## Files

- `.github/workflows/ai-security-review.yml:38-42`

## Fix

Add a second `find` invocation for the dotfile form (`.env*`), matching the same
convention already codified in `.gitignore`, alongside the existing suffix-form pattern.

Verified the gap and the fix by reproducing both glob behaviors directly: `find -name
"*.env"` against a scratch directory containing `.env`, `foo.env`, `.env.local`, and
`.env.production` returns only `.env` and `foo.env`; adding `find -name ".env*"` catches
all four.
