### bug-0280 🟡 Medium — `prisma.config.ts` has no fail-fast guard for missing `DATABASE_URL`

**Fixed:** true

**Files:**
- `packages/db/prisma.config.ts`
- `.github/workflows/typecheck.yml`

**Description:** `packages/db/index.ts` (added by the Prisma 7 migration,
`d7bc85c`) throws a clear `DATABASE_URL is not set` error at import time
when the env var is missing — a deliberate improvement over Prisma's own
opaque connection error. `packages/db/prisma.config.ts` (added the same
migration, `0ae109a`), which every Prisma CLI invocation now resolves its
datasource from since v7 dropped the CLI's implicit env/schema
resolution, had no equivalent guard: it passes `process.env.DATABASE_URL`
straight into `defineConfig()` regardless of whether it's set.

**Impact:** An unset `DATABASE_URL` hitting `prisma generate` or
`prisma migrate deploy` would surface as a less obvious Prisma
CLI/schema-validation error instead of the same clear message the app's
own runtime code already gives — the two guards should be symmetric.

**Fix:** PR #375. Mirrored the `index.ts` guard in `prisma.config.ts`.
Since `prisma generate` runs via `packages/db`'s `postinstall` on every
`pnpm install`, the new guard means `typecheck.yml` — which builds
`packages/db` but never previously needed a database — now needs
`DATABASE_URL` set too; added the same dummy-but-valid connection string
`unit-tests.yml` already uses for the identical reason. **Verified**
locally: `prisma generate` throws the new error with `DATABASE_URL`
unset, and both `prisma generate` and `pnpm --filter @sassy-auth/db test`
succeed once it's set.

### bug-0281 🟠 High — FastAPI RS's CI dependency list drifted from `pyproject.toml`, breaking e2e

**Fixed:** true

**Files:**
- `.github/workflows/e2e.yml`

**Description:** The e2e workflow's "Install FastAPI RS dependencies"
step hand-lists a subset of packages (`fastapi`, `uvicorn[standard]`,
`httpx`, `pyjwt[crypto]`, `pydantic-settings`, `jinja2`) instead of
installing from `apps/resource-server-fastapi/pyproject.toml`, which is
the actual source of truth (and what local dev already uses via `uv sync`
— `package.json`'s `setup:resource-server-fastapi` script). It had
drifted: `app/telemetry.py` and `app/oauth/verifier.py` unconditionally
`import opentelemetry` (added for the Sentry/OTel observability work),
and none of the four `opentelemetry-*` packages, nor `sentry-sdk`, were
ever in the CI list.

**Impact:** This was live-broken, not theoretical — the `prisma-7-migration`
e2e run
(<https://github.com/rlondner/sassy-auth/actions/runs/33788905397>)
failed with `ModuleNotFoundError: No module named 'opentelemetry'` when
Playwright's FastAPI RS `webServer` tried to start, taking the entire e2e
job down. Unrelated to that PR's actual Prisma changes — and, since `dev`
has no branch protection (see TODO_2026-09-04.md), the red e2e check
didn't block the merge.

**Fix:** PR #376. Changed the step to `pip install .`, which installs
`pyproject.toml`'s `[project.dependencies]` directly — the same set `uv
sync` installs locally — so this can't drift out of sync again.
**Verified** locally: `pip install .` in a fresh venv followed by
`import app.main` succeeds cleanly (previously reproduces the CI failure
with the old hand-list).

## Verified — not filed

- **`packages/db/index.ts` eager `DATABASE_URL` throw** (Prisma 7
  migration, not this run's change) could in principle break a local
  `pnpm --filter @sassy-auth/auth-server test` run for a developer who
  hasn't exported `DATABASE_URL` in their shell (Jest has no
  `.env`-loading `setupFiles` for unit specs, unlike the e2e-spec suite
  which loads dotenv explicitly). Checked: this is a real local-dev
  ergonomics risk, not a CI bug (CI jobs that build `packages/db` all set
  `DATABASE_URL` now — see bug-0280's fix for `typecheck.yml`). Filed as
  a TODO rather than a bug since it's a deliberate, reasonable design
  choice (fail fast beats a silent misconfiguration) with one rough edge,
  not an incorrect behavior.
- **`.github/workflows/{e2e,typecheck,unit-tests}.yml`'s `push` trigger**
  still reads `branches: [master]` only, unchanged by yesterday's `33e074c`
  which extended `pull_request` to include `dev`. Investigated whether
  this is an oversight (parallel `dev`-only `push` coverage would catch a
  bad merge commit) or intentional (avoid re-running the same checks a
  PR's `pull_request` trigger already ran, right after merge) — found
  reasonable arguments either way and no way to confirm intent from the
  commit message alone, so not filed as a bug. Flagged in
  TODO_2026-09-04.md as a call for whoever owns CI config.
- **`docker/Dockerfile.auth-server`'s generated-client handling** — the
  Prisma 7 migration's `output = "./generated/prisma"` directory is
  gitignored and produced by `postinstall: prisma generate` during the
  `deps` stage's `pnpm install`; the `build` stage (`FROM deps`) inherits
  that filesystem state and the `runner` stage's
  `COPY --from=build /app/packages/db ./packages/db` picks up the
  generated directory along with everything else. Traced the full
  multi-stage copy chain — confirmed the runtime image does ship the
  generated client. Not a bug.
