### bug-0164 :yellow_circle: Warning — `GET /api/apps/:id` endpoint documented in README but missing from `AppsController`

**Files:**
- `apps/auth-server/src/apps/apps.controller.ts` (entire file — no `@Get(':publicId')` handler)
- `apps/auth-server/src/apps/apps.service.ts` (no `getApp` method)
- `README.md:513` (API Reference row: `GET /api/apps/:id — Get app`)

**Description:** The README API Reference table documents `GET /api/apps/:id` as a supported endpoint. However, `AppsController` only defines four routes: `@Get()` (list), `@Post()` (create), `@Patch(':publicId')` (update), and `@Delete(':publicId')` (delete). There is no `@Get(':publicId')` handler. The `AppsService` likewise has no `getApp` method. All other entity controllers (orgs, roles, permissions, users) have a corresponding get-by-id route.

**Impact:** Any client or integration following the README to fetch a single app by public ID receives a 404. The admin frontend's `AppViewDrawer` works around this by using data from the list endpoint, but external consumers are broken.

**Fix:** Add a `@Get(':publicId')` handler to `AppsController` and a `getApp(callerBaId, publicId)` method to `AppsService`, mirroring the pattern in `OrgsService.getOrg()`.

**Fixed:** false

### bug-0165 :yellow_circle: Warning — Admin middleware validates session on every request with no caching — full round-trip to auth-server per request

**Files:**
- `apps/admin/middleware.ts:14-20`

**Description:** The Next.js Edge middleware calls `fetch('${AUTH_SERVER}/api/auth/get-session', ...)` on every request that isn't in `PUBLIC_PATHS` or `/_next`. The fetch uses `cache: 'no-store'`, so no caching occurs at any layer. Every page navigation, every RSC data fetch, and every prefetch triggers a full HTTP round-trip from the Edge runtime to the auth-server.

The middleware matcher already excludes `_next/static` and `_next/image`, but the `isPublic` check inside the function adds `/_next` as a prefix, covering `_next/data` and `_next/webpack-hmr` as well. However, all authenticated page loads still incur the latency.

**Impact:** Significant performance degradation — each authenticated admin page load adds the auth-server round-trip latency (typically 50–200ms LAN, higher on WAN). Under load, the auth-server receives N× the traffic it needs. No session caching means zero tolerance for auth-server slowdowns.

**Fix:** Cache the session validation result for a short window (e.g., 30–60 seconds) using a cookie-based cache token or an Edge KV store. Alternatively, move session validation to a layout-level server component and use `unstable_cache` or a cookie-timestamp approach.

**Fixed:** false

### bug-0166 :large_blue_circle: Minor — Admin middleware `fetch` to auth-server has no explicit timeout — slow auth-server hangs all admin requests

**File:** `apps/admin/middleware.ts:14`

**Description:** The `fetch()` call in `validateSession` uses `cache: 'no-store'` but no `signal` (AbortController with timeout). If the auth-server is slow (under load, DNS resolution stall, or network issue), the middleware blocks indefinitely (until the Edge runtime's own hard timeout, typically 25–30 seconds in Vercel). During this window, the admin console is completely unresponsive.

The `catch` block on line 22 handles transport errors (connection refused), but a slow-but-not-failing server is not caught.

**Impact:** Admin console availability degrades proportionally to auth-server response time. A 10-second auth-server response turns into a 10-second TTFB for every admin page.

**Fix:** Add an AbortController with a 3–5 second timeout:
```typescript
const controller = new AbortController()
const timer = setTimeout(() => controller.abort(), 3000)
const res = await fetch(url, { signal: controller.signal, cache: 'no-store' })
clearTimeout(timer)
```

**Fixed:** false

### bug-0167 :large_blue_circle: Minor — Resource server `GET /api/properties` requires `rs.properties.create` scope but README says `rs.properties.read`

**Files:**
- `apps/resource-server-fastapi/app/api/routes.py:11` — `require_scope("rs.properties.create")`
- `apps/resource-server-fastapi/app/templates/authorized.html:12` — also references `rs.properties.create`
- `README.md:612` — documents: "`/api/properties` — protected endpoint; requires Bearer token with `rs.properties.read` scope"

**Description:** The FastAPI demo resource server's protected endpoint uses `require_scope("rs.properties.create")`, requiring the `create` permission to read properties. The README documents it as requiring `rs.properties.read`. The seed data creates both `rs.properties.read` and `rs.properties.create` permissions, but the demo user `m@cpm.io` has the `Inspector` role which may not include `rs.properties.create`.

The `authorized.html` template also says "requires `rs.properties.create`", consistent with the code but inconsistent with the README.

**Impact:** Developers following the README expect the `rs.properties.read` scope to suffice. Users with only `rs.properties.read` receive a 403 on the demo endpoint. Confusing for anyone learning the PKCE flow.

**Fix:** Change `routes.py:11` to `require_scope("rs.properties.read")` and update `authorized.html:12` to match.

**Fixed:** false

### bug-0168 :large_blue_circle: Minor — `UpdateUserDto` allows empty strings for `firstName`, `lastName`, `username`, `phoneNumber` — no `@MinLength(1)` constraints

**Files:**
- `apps/auth-server/src/users/dto/update-user.dto.ts:4-7`
- `apps/auth-server/src/users/dto/create-user.dto.ts:4-5,8-9` (for comparison)

**Description:** `UpdateUserDto` defines all four string fields (`firstName`, `lastName`, `username`, `phoneNumber`) with only `@IsString() @IsOptional()` — no `@MinLength(1)`. This allows an admin to PATCH a user with `{ "firstName": "" }`, setting their first name to an empty string.

In contrast, `CreateUserDto` enforces `@MinLength(1)` on `firstName` and `lastName` (but also lacks it on `username` and `phoneNumber`). This creates a parity gap: create rejects empty names, but update accepts them.

**Impact:** Users can end up with empty-string names via the update endpoint, causing display issues in the admin console (empty table cells, broken avatar initials) and downstream JWT payloads. The `username` and `phoneNumber` fields also lack `@MinLength` on both create and update DTOs.

**Fix:** Add `@MinLength(1)` to all four fields in `UpdateUserDto`. Also add `@MinLength(1)` to `username` and `phoneNumber` in `CreateUserDto` for consistency.

**Fixed:** false

### bug-0169 :large_blue_circle: Minor — `CreateUserDto.email` has no `@MaxLength()` — arbitrarily long email strings accepted

**File:** `apps/auth-server/src/users/dto/create-user.dto.ts:6`

**Description:** The `email` field is decorated with `@IsEmail()` only. `class-validator`'s `@IsEmail()` does not enforce a maximum length. RFC 5321 limits the local part to 64 octets and the domain to 255 octets, for a total maximum of 254 characters (RFC 5321 §4.5.3.1). An attacker could submit a 10 KB+ syntactically-valid email string (e.g., `a{repeat 10000}@example.com` which `@IsEmail` may accept depending on the validator options).

**Impact:** Database bloat — the email is stored in the BetterAuth `User` table (globally `@unique`, indexed) and every email lookup becomes slower. Low probability in practice but a defense-in-depth gap.

**Fix:** Add `@MaxLength(254)` before `@IsEmail()`.

**Fixed:** false

### bug-0170 :large_blue_circle: Minor — `FormField` component auto-generates HTML IDs from label text — duplicate labels produce duplicate IDs

**File:** `packages/ui/src/components/form-field.tsx:14`

**Description:** `FormField` generates the `id` attribute as `id ?? label.toLowerCase().replace(/\s+/g, '-')`. If two `FormField` components in the same form have the same label (e.g., two "Name" fields in different sections), they get the same generated ID. This:
1. Breaks the `<Label htmlFor=...>` association — clicking either label focuses the first field.
2. Produces invalid HTML (duplicate IDs).
3. Breaks `aria-describedby` error associations — the wrong error message is announced.

**Impact:** Accessibility regression — screen readers and label clicks malfunction when labels collide. Currently mitigated because most forms use unique labels, but any future form with repeated labels will silently break.

**Fix:** Generate a unique ID using `React.useId()` as the fallback instead of deriving from label text.

**Fixed:** false

### bug-0171 :large_blue_circle: Minor — Copy-to-clipboard handlers silently swallow clipboard API failures — no error feedback to user

**Files:**
- All admin table components: `apps-table.tsx`, `orgs-table.tsx`, `roles-table.tsx`, `permissions-table.tsx`
- All admin view/edit drawers with copy buttons

**Description:** Every "copy to clipboard" button calls `navigator.clipboard.writeText(value)` (via the shared `copyToClipboard` helper) and, on success, sets a `copiedSqid` state to show a checkmark icon. If the clipboard API fails (not available in HTTP contexts, permission denied, or Firefox requiring user gesture), no error is shown. The user clicks "copy", nothing visually happens, and they have no idea the copy failed.

**Impact:** Silent failure UX — users in HTTP dev environments or restrictive browsers believe they copied a value when they didn't. Particularly confusing when sharing public IDs or invitation URLs.

**Fix:** Catch the clipboard error and show a toast:
```typescript
try {
  await navigator.clipboard.writeText(value)
  setCopied(id)
} catch {
  toast.error('Failed to copy to clipboard')
}
```

**Fixed:** false

### bug-0172 :white_circle: Info — `UsersTable` receives `initialOrgId` and `canPickOrg` props but immediately voids them — dead code

**File:** `apps/admin/components/users-table.tsx:24-31`

**Description:** The `UsersTableProps` interface declares `initialOrgId?: string` and `canPickOrg?: boolean`. The component destructures them from props (line 27) but immediately calls `void initialOrgId` and `void canPickOrg` (lines 30–31) to suppress unused-variable warnings. The props are never read or used anywhere in the component.

These props suggest a planned feature (org-scoped user filtering with a locked org picker for non-platform admins) that was never implemented. The `void` expressions are a code smell — they exist only to suppress lint, not to provide functionality.

**Impact:** No runtime impact. Increases interface surface area without utility. Callers (e.g., `users/page.tsx`) may pass these props expecting them to work.

**Fix:** Either implement the org-scoped filtering feature or remove the props from the interface and the `void` expressions. If deferring, add a `// TODO` comment explaining the intent.
