### bug-0278 🟠 High — auth-bucket rate limits silently ignore their new .env config

**Fixed:** true

**Files:**
- `apps/auth-server/src/app.module.ts`
- `apps/auth-server/src/token/token.controller.ts`
- `apps/auth-server/src/invitations/invitations.controller.ts`
- `apps/auth-server/src/common/config/rate-limit-config.ts` (new)

**Description:** Yesterday's `a259450` ("rate limits are now configurable
in .env") added `AUTH_RATE_LIMIT` / `AUTH_RATE_WINDOW_MS` env vars feeding
the `auth` NestJS-throttler bucket registered in `app.module.ts`. But every
route that actually carries the `auth` bucket —
`POST /api/token/direct/login`, `GET /api/token/oauth/authorize`, and all
of `InvitationsController` — decorates itself with
`@Throttle({ auth: { limit: 10, ttl: 60_000 } })`, hardcoding the
pre-`a259450` defaults as literal numbers.

Per `@nestjs/throttler` semantics, an explicit `{ limit, ttl }` passed to a
route's `@Throttle()` call *overrides* the named bucket's module-level
config for that specific route — it does not merely select which bucket to
use. So `AUTH_RATE_LIMIT` / `AUTH_RATE_WINDOW_MS` had **zero effect** on any
of these three route groups: the very endpoints the bucket exists to
protect (brute-forcing a credential, an invitation token, or repeatedly
minting authorization codes). Only routes with no `@Throttle()` override at
all (falling back to the bare `auth` bucket registration) would have picked
up the env vars — and there are none of those, since every `auth`-bucket
usage in the codebase carries this same hardcoded override. Directly
contradicts the commit's own stated purpose and its `.env.example`
documentation, which describes these exact three route groups as "opted
into" the configurable bucket.

**Impact:** An operator raising `AUTH_RATE_LIMIT` (loosen for legitimate
high-traffic) or lowering it (tighten after an incident) via `.env` would
see no behavior change on login, OAuth authorize, or invitation endpoints —
the most security-sensitive routes in the app — while believing the change
took effect. Not an open vulnerability by itself (the hardcoded 10/60s
values are a reasonable default), but a "config that silently does
nothing" trap, which is its own class of production risk.

**Fix:** PR #372. Extracted `DEFAULT_THROTTLE` / `AUTH_THROTTLE` into a new
`apps/auth-server/src/common/config/rate-limit-config.ts` (env-aware,
`NODE_ENV=test` override preserved), and pointed both `app.module.ts`'s
`ThrottlerModule.forRoot()` config and all three `@Throttle()` overrides at
the same constants, so they cannot drift again. **Verified:** new
`rate-limit-config.spec.ts` (defaults, configured env values, invalid/zero
overrides falling back, test-mode override) plus existing
`token.controller.spec.ts` / `invitations.*.spec.ts` — 76 tests pass;
`npx tsc --noEmit` clean.

### bug-0279 🟡 Medium — `GET /api/register/app` is an unrate-limited enumeration oracle

**Fixed:** true (on `feature/admin-signup`, not on `dev` — see note above)

**Files:**
- `apps/auth-server/src/registration/registration.controller.ts`
  (`feature/admin-signup` branch)

**Description:** The new `GET /api/register/app?appPublicId=<id>` endpoint
(added for the admin console's `/signup` page, to render "Register with
{app name}") returns `200 { name }` for a known `appPublicId` and
`404` for an unknown one. Its own docstring claims it "mirror[s]
SocialController's public `GET /api/social-providers`", but that sibling
endpoint is explicitly designed to *avoid* being an enumeration oracle — it
returns an empty provider list for both a known and an unknown
`client_id`, per its own comment: "returns an empty list for an unknown
client_id so it cannot be used to enumerate apps." `getAppName` does the
opposite: its 200-vs-404 split is exactly the enumeration signal the
sibling endpoint was designed to deny. On top of that, unlike
`POST /api/register` immediately above it in the same controller, it
carried no `RateLimitGuard` at all — fully unauthenticated, unrate-limited,
and distinguishable by design.

**Failure scenario:** An unauthenticated caller sweeps `appPublicId`
candidates against this endpoint at any rate to enumerate which apps exist
on the platform (a lower-severity but real disclosure — `appPublicId`
values aren't secret, but nothing currently limits bulk enumeration
attempts, unlike the sibling endpoint it claims parity with).

**Fix:** Reused the same `RateLimitGuard` already applied to
`POST /api/register` (`@UseGuards(RateLimitGuard)` on `getAppName`).
Full behavioral parity with `/social-providers` (a uniform response
regardless of validity) isn't possible without breaking the signup page's
actual UX requirement (showing the app name), so this is a bound on abuse
rate rather than closing the oracle outright — documented as such in the
updated controller comment. **Verified:** new
`registration.controller.spec.ts` guard-reflection test plus existing
suite — 27 tests pass in `apps/auth-server/src/registration`; `npx tsc
--noEmit` clean.

### bug-0280 🟠 High — self-serve signup regresses the password policy to 8 chars, no complexity

**Fixed:** true (on `feature/admin-signup`, not on `dev` — see note above)

**Files:**
- `apps/auth-server/src/registration/register.dto.ts` (`feature/admin-signup`
  branch)

**Description:** `bug-0007` (2026-05-27) tightened the password policy
project-wide from `@MinLength(8)` to 12+ characters with required upper,
lower, and digit character classes, applied to
`AcceptInvitationDto` and its matching admin-console client-side check.
`RegisterDto` — a brand-new DTO backing the self-serve `POST /api/register`
endpoint added on `feature/admin-signup` — only carried
`@IsString() @MinLength(8)`, i.e. exactly the pre-`bug-0007` policy, with
no character-class requirement at all.

The admin console's `SignupForm` (`apps/admin/app/signup/signup-form.tsx`)
does enforce the 12-char + complexity rule client-side before submitting —
so a user going through the actual `/signup` page is protected — but
nothing on the server enforces it. Anyone calling
`POST /api/register` directly (a script, a different frontend, a future
integration) can create an account with an 8-character, single-case,
digit-free password that the UI itself would have visibly rejected.

**Impact:** Weak passwords on newly self-registered accounts, bypassing a
policy this codebase already treats as a baseline security requirement
everywhere else account credentials are set.

**Fix:** Applied the identical `MinLength(12)` + `Matches(PASSWORD_PATTERN)`
combo `bug-0007` used on `AcceptInvitationDto`, verbatim, to
`RegisterDto.password`. **Verified:** new `register.dto.spec.ts` (mirrors
`accept-invitation.dto.spec.ts`'s cases, plus an explicit "8-char password
that satisfied the old policy is now rejected" case) — all pass; `npx tsc
--noEmit` clean.

## Verified — not filed

- **`feature/admin-signup`'s `RegisterDto.companyName`** is still required
  and still used as the new org's display name (not the user's identity —
  that regression was already the subject of this branch's `a7b272a` fix).
  Reasonable as-is; not a bug.
- **`getAppName`'s `appPublicId` query param** has no format validation
  (no DTO, no regex) before hitting Prisma. Checked: an unexpected shape
  (e.g. a repeated query param producing an array) is passed straight to
  `prisma.saApp.findUnique({ where: { publicId: appPublicId } })`, which
  would reject a non-string at the Prisma client boundary and surface as a
  generic 500 via Nest's default exception filter — no stack trace or
  query info leaks in a production build. Not worth a dedicated DTO for a
  single query param; noted in TODO as a nice-to-have.
- **`vibecast-permissions.ts`'s `findUnique({ where: { name } })`** looked
  suspicious at first (an old bug-0026 fixed "permission name unique per
  app" elsewhere in this codebase's history, which sounds like it implies a
  compound key) — checked `schema.prisma`: `SaPermission.name` is in fact
  `@unique` globally, not a compound `(appId, name)` key, so this is a
  valid Prisma call and the vibecast permission names are already
  self-namespaced (`vibecast.*`). Not a bug.
- **OIDC merge (`8db2fd7`) conflict resolution** — re-checked that
  `end_session_endpoint`/`OAUTH_LOGOUT_ROUTE` were re-added deliberately
  (this branch actually implements RP-Initiated Logout, unlike the
  situation bug-0277 fixed on 2026-09-02) rather than reintroducing that
  exact bug. `oauth-metadata.spec.ts` and the merge commit message both
  confirm this was intentional; not re-filed.
