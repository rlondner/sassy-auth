# bug-0288: `App` mock literals in 7 admin test files still missing password-policy fields

**Fixed:** false

## Summary

`apps/admin/lib/types.ts`'s `App` interface has required
`passwordPolicyOverride: PasswordPolicy | null` and
`effectivePasswordPolicy: PasswordPolicy` fields (added by the per-app
password-policy feature, commit `430f870`, 2026-09-05). bug-0283 fixed the one
production call site that builds an `App[]` by hand
(`app/(admin)/roles/page.tsx`, PR #380, still unmerged as of this review), but
that PR's scope did not extend to test fixtures. Seven test files still
construct `App`-typed literals without the two new fields, and all seven fail
`typecheck` on current `dev` (verified locally against `origin/dev` HEAD
`ccf2cea`):

## Impact

`typecheck` on `dev` fails regardless of which PR's diff triggers it — this is
the actual root cause behind every open PR (#378–#387, 9 PRs as of this
review) showing a red `typecheck` and `admin-e2e` check, even PRs that are
purely docs or an unrelated one-line fix. It's the same underlying condition
bug-0283 already documented for `roles/page.tsx`, just not fully closed: `dev`
has effectively had zero passing `typecheck` runs since the password-policy
feature merged on 2026-09-05, so the CI signal on this branch has been fully
uninformative for over a week. See `TODO_2026-09-14.md` for the fuller
backlog picture.

## Fix

Add `passwordPolicyOverride: null, effectivePasswordPolicy: FALLBACK_PASSWORD_POLICY`
to every `App` literal in the seven affected test files, importing
`FALLBACK_PASSWORD_POLICY` from `@/lib/types` where not already imported —
the same pattern bug-0283/PR #380 used for `roles/page.tsx`. Test behavior is
unaffected: these fields aren't asserted on by any of the seven suites, they
just need to satisfy the `App` type.

## Verification

- `grep`-audited every `App`-typed object literal across the seven files
  after the edit; all now carry both fields.
- Not run through `pnpm typecheck` in this worktree (no `node_modules`
  installed here — CI will confirm on the PR); the fix mirrors bug-0283's
  already-verified fix exactly, applied to the same field set.
