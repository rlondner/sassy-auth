## bug-0305: `/authorize` reports the wrong error for an unregistered custom-scheme redirect_uri

**Fixed:** true (fixed in this run's own PR, see below)

`TokenController.oauthAuthorize` computed `pkceRequired` from the raw,
unvalidated `redirect_uri` query parameter (via `isCustomSchemeRedirect`)
and checked it against the presented `code_challenge` **before** calling
`assertRedirectUriAllowed`. An unregistered custom-scheme `redirect_uri`
with no PKCE challenge therefore failed with the generic PKCE
`invalid_request` instead of `INVALID_REDIRECT_URI`, and — because
`redirectUriValidated` was still `false` at that point — skipped the
client-error-redirect path every other post-validation `/authorize`
failure uses (RFC 6749 §4.1.2.1).

Not an exploitable bypass (the request still fails closed either way),
but a real correctness bug with zero test coverage: every existing PKCE
test in `token.controller.spec.ts` used an origin-matching or
explicitly-registered `redirect_uri`, so the masked-error case was never
exercised.

**Fix (PR #479, `bug-0305` branch):** reordered `oauthAuthorize` so
`assertRedirectUriAllowed` runs before the PKCE-requirement check. Added
a regression test for the masked-error case, and updated the two
existing PKCE tests whose `redirect_uri` is valid to expect the (now
correct) 302 OAuth-error redirect instead of a bare 400 — a behavior
change those tests needed to reflect, since a PKCE failure on an
otherwise-valid request is now redirected to the client like every other
post-validation error. Verified: `token.controller.spec.ts` +
`redirect-uri.spec.ts` — 101/101 pass; `tsc --noEmit` on
`apps/auth-server` clean.

## Verification pass (no new bugs)

- Re-checked `assertPostLogoutRedirectUriAllowed` (no same-origin
  fallback, unlike login redirects) — correct per its own doc comment,
  no regression.
- Re-checked the PKCE-mandatory-for-custom-scheme logic itself
  (`isCustomSchemeRedirect` treats a custom scheme as public even for a
  confidential app) — correct; a client secret embedded in a
  distributed native-app binary can't be kept confidential, so the
  confidential-client PKCE exemption should not apply there.
- Confirmed `isExactMatch` in `redirect-uri.ts` compares protocol + host
  (port included) + pathname + search, which is the right granularity
  for RFC 6749 §3.1.2.3 exact-match redirect URI validation, including
  for a custom-scheme URI (e.g. `com.example.app://auth`), where `host`
  for a non-hierarchical-looking scheme is still parsed correctly by
  the WHATWG `URL` parser used here.
- Confirmed CI is green end-to-end on `dev` at `2215689` (`e2e`,
  `typecheck`, `unit tests`, Trivy) — no silent-red-CI repeat of the
  2026-07-15/2026-08-25 pattern this time.
