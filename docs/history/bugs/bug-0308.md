# bug-0308: `trust proxy` hop count is hardcoded, silently wrong for any topology other than Render's

**Fixed:** false

## Summary

`apps/auth-server/src/main.ts`'s `bootstrap()` hardcoded `expressApp.set('trust proxy', 1)`,
with an inline comment already flagging the risk: "if a second proxy is ever added in front
of Render's edge, this needs to become `2`." That one-hop assumption determines which
`X-Forwarded-For` entry Express treats as the real client — every per-client rate limiter
that keys on `req.ip` (`@nestjs/throttler`'s default tracker in `app.module.ts`, and
`auth-rate-limit.ts`'s `clientKey`) depends on it being correct for whatever actually fronts
the service.

This repo now deploys to two different platforms with two different edge topologies
(Render, and GCP per `docs/gcp-deployment.md`), and `gcp/setup-lb.sh` provisions an
*optional* external HTTPS Load Balancer (serverless NEG) that — unlike Cloud Run's default
domain-mapping path — adds a second hop in front of Cloud Run. If that LB is ever put in
front of the GCP deployment instead of using domain mappings directly, `req.ip` resolves to
the load balancer's own address for every caller, collapsing all distinct users' traffic
onto one shared rate-limit bucket. Symptom: 429s on routes like `GET
/api/token/oauth/authorize` with no correlation to any individual client's request rate —
the same symptom class as CR_2026-09-02.md's finding, which this hardcoded value was
originally written to fix for Render only.

Verified via `main-trust-proxy.spec.ts`: with the hop count fixed at `1` and two real hops
present (`X-Forwarded-For: <client>, <load-balancer>`), `req.ip` resolves to the load
balancer, not the client — reproducing the bug deterministically rather than just reasoning
about it.

As of today, neither `render.yaml` nor `gcp/env.auth-server.yaml` sets anything that would
trigger this — both deployments use a single hop — so there is no live impact right now.
This is a latent/configuration bug: a future infra change (adding the optional LB) would
silently reintroduce the exact 429 symptom this code was written to prevent, with no code
change required to trigger it and no test that would catch it before production.

## Fix

Made the hop count configurable via a new `TRUST_PROXY_HOPS` env var (default `1`, read with
the existing `envInt` helper from `common/config/rate-limit-config.ts` rather than adding a
duplicate parser), so a deployment's actual proxy topology decides the value instead of a
hardcoded assumption baked into source. `gcp/env.auth-server.yaml` and `.env.example` both
document why `1` stays correct today and when it would need to become `2`. Added two new
test cases to `main-trust-proxy.spec.ts` (misread-with-one-hop reproduction, resolved-with-
two-hops fix) alongside the existing Render-only coverage. Also documented in the README
("Trust proxy (`TRUST_PROXY_HOPS`)" section).

Verified: `main-trust-proxy.spec.ts` (5/5 passing, including the two new cases).
