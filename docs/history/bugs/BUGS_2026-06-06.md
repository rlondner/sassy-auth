## :red_circle: bug-0054 -- `oauthAuthorize` does not validate `redirect_uri` against app's registered URL

**Fixed:** false
**Severity:** Critical
**File:** `apps/auth-server/src/token/token.controller.ts` (lines 54-108)

**Description.** The OAuth authorize endpoint accepts an arbitrary `redirect_uri` query parameter and redirects to it with the authorization code appended, without checking that the URI matches the app's registered `url` field. At line 95, `const url = new URL(redirectUri)` constructs from the attacker-supplied value and the redirect fires at line 107.

The `assertRedirectUriMatchesApp()` helper exists and is used during token exchange (in the DTO), but the authorize endpoint -- where the redirect actually happens -- does not call it. An attacker who knows a valid `client_id` can craft an authorize URL with `redirect_uri=https://evil.com/callback`, and if a user clicks it while authenticated, the authorization code is sent to the attacker's server. The attacker can then exchange it for a JWT (the token exchange endpoint does validate `redirect_uri`, but the code has already leaked).

This is an authorization code interception vulnerability per RFC 6749 section 10.6.

**Fix sketch.** Before redirecting, validate that `redirect_uri` origin matches the app's registered URL:

```typescript
const app = await prisma.saApp.findUnique({ where: { id: numericId } });
if (!app) throw new NotFoundException(TokenErrorCode.APP_NOT_FOUND);

// Validate redirect_uri against app's registered URL
assertRedirectUriMatchesApp(redirectUri, app);
```

**Tests needed.** E2E test: authorize request with `redirect_uri` pointing to a different origin should return 400, not 302.

## :yellow_circle: bug-0055 -- `deleteUser` orphans BetterAuth `User`, `Session`, and `Account` rows

**Fixed:** false
**Severity:** Warning
**Files:**
- `apps/auth-server/src/users/users.service.ts` (line 285)
- `packages/db/schema.prisma` (line 98)

**Description.** `deleteUser` calls `prisma.saUser.delete(...)` which cascades to `SaInvitation`, `SaUserRole`, and `SaUserPermission`. However, the BetterAuth `User` row (and its child `Account` and `Session` rows) is NOT deleted. The `SaUser.betterAuthUserId` FK uses default RESTRICT, so:

1. The orphaned BetterAuth `User` retains its email -- the email cannot be reused for a new user (`P2002` on `user.email`).
2. Active sessions remain valid until natural expiry -- the user can still call BetterAuth endpoints.
3. The user could sign in again via BetterAuth and get a session, but JWT issuance would fail with `USER_NOT_FOUND`.

Additionally, if BetterAuth ever deletes a `User` record directly (e.g., GDPR), the FK RESTRICT from `SaUser` will block it with a P2003 error.

**Fix sketch.** Inside a transaction, also delete the BetterAuth `User` row:

```typescript
await prisma.$transaction(async (tx) => {
  const saUser = await tx.saUser.delete({ where: { publicId } });
  await tx.user.delete({ where: { id: saUser.betterAuthUserId } });
});
```

The schema's `onDelete: Cascade` on `Session` and `Account` will clean those up automatically.

**Tests needed.** Unit test verifying that after `deleteUser`, no `User`, `Session`, or `Account` rows remain for the deleted user's `betterAuthUserId`.

## :yellow_circle: bug-0056 -- `setLocaleAction` does not validate the `locale` parameter

**Fixed:** false
**Severity:** Warning
**File:** `apps/admin/app/(admin)/actions.ts` (line 8)

**Description.** The `setLocaleAction` server action accepts an arbitrary `locale` string from the client and writes it directly into the `NEXT_LOCALE` cookie. When `i18n/request.ts` later tries `import(\`../messages/${locale}.json\`)`, a crafted locale value (e.g., `../../package`) could trigger an import of an unintended module, or throw an unhandled error that crashes the RSC render. Sentry tags also receive the attacker-controlled value.

**Fix sketch.**

```typescript
import { getAvailableLocales } from '@/lib/locale'

export async function setLocaleAction(locale: string, pathname: string) {
  const available = getAvailableLocales()
  if (!available.includes(locale)) return
  // ... rest
}
```

**Tests needed.** Unit test: calling `setLocaleAction('../../package', '/')` should not set the cookie or throw.

## :yellow_circle: bug-0057 -- `setLocaleAction` open redirect via `pathname` parameter

**Fixed:** false
**Severity:** Warning
**File:** `apps/admin/app/(admin)/actions.ts` (line 21)

**Description.** The `pathname` parameter is received from the client and passed directly to `redirect(pathname)`. Next.js's `redirect()` supports absolute URLs, so a malicious client can call `setLocaleAction('en', 'https://evil.com')` to redirect the user to a phishing site.

**Fix sketch.**

```typescript
if (!pathname.startsWith('/') || pathname.startsWith('//')) {
  pathname = '/'
}
redirect(pathname)
```

**Tests needed.** Unit test: `setLocaleAction('en', 'https://evil.com')` should redirect to `/`, not to the external URL.

## :yellow_circle: bug-0058 -- Users page has no permission check; any authenticated user can view all users

**Fixed:** false
**Severity:** Warning
**File:** `apps/admin/app/(admin)/users/page.tsx` (lines 1-22)

**Description.** The apps, orgs, roles, and permissions pages all call `getMyPermissions()` and check for specific platform permissions (e.g., `platform.apps.manage`) before rendering, showing an `AccessDeniedPanel` if unauthorized. The users page skips this entirely -- it calls `getUsers()` and `getOrgs()` without any permission check and renders the full users table to any authenticated admin user.

This means any authenticated user can see all users across all orgs, including email addresses, phone numbers, and status.

**Fix sketch.**

```typescript
const perms = await getMyPermissions()
const canManage = perms.includes('platform.users.manage')
if (!canManage) return <AccessDeniedPanel />
```

**Tests needed.** E2E test: a user without `platform.users.manage` should see the access denied panel on `/users`.

## :yellow_circle: bug-0059 -- `SaUser.username` and `phoneNumber` lack unique constraints; `directLogin` may authenticate as wrong user

**Fixed:** false
**Severity:** Warning
**Files:**
- `packages/db/schema.prisma` (lines 94-113)
- `apps/auth-server/src/token/token.controller.ts` (lines 195-226)

**Description.** The schema defines `username` and `phoneNumber` as indexed but not unique (`@@index([username])`, `@@index([phoneNumber])`). The `directLogin` controller uses `prisma.saUser.findFirst` to look up users by username or phone. If two users share the same username or phone, `findFirst` returns an arbitrary one, and the login may authenticate as the wrong user.

In a multitenant system, two users in different orgs could legitimately have the same username (e.g., "admin"). The `saUser.org.appId !== app.id` check at line 229 catches cross-app collisions, but two users in different orgs within the same app will still collide.

**Fix sketch.** Add `@@unique([orgId, username])` and `@@unique([orgId, phoneNumber])` to the schema (if uniqueness is per-org), or change `findFirst` to `findMany` and throw if `results.length > 1` as an interim guard.

**Tests needed.** Integration test: create two users with the same username in different orgs of the same app; verify `directLogin` returns an error rather than silently picking one.

## :yellow_circle: bug-0060 -- `detectIdentifierType` phone regex misclassifies numeric usernames

**Fixed:** false
**Severity:** Warning
**File:** `packages/types/index.ts` (line 38)

**Description.** The regex `/^\+?[\d\s\-().]{7,}$/` matches strings that are not phone numbers: `"1234567"` (a 7-digit number, could be an employee ID used as username), `"(......)"` (8 dots in parens), `"1.2.3.4.5.6.7"`. Any username consisting of 7+ characters from `[0-9 \-().]` will be misclassified as a phone number, causing the token controller to query `phoneNumber` instead of `username` -- the login fails silently (user not found).

**Fix sketch.** Tighten the regex to require at least one digit and be more restrictive:

```typescript
if (/^\+?[1-9]\d{6,14}$/.test(identifier.replace(/[\s\-().]/g, ''))) return 'phone';
```

**Tests needed.** Unit tests: `"1234567"` should return `"username"` (or at least not `"phone"`); `"+15551234567"` should return `"phone"`.

## :yellow_circle: bug-0061 -- `updateUserAction` missing error handling; throws unhandled exceptions

**Fixed:** false
**Severity:** Warning
**File:** `apps/admin/app/(admin)/users/actions.ts` (lines 106-110)

**Description.** Unlike all other mutation actions (`createUserAction`, `deleteUserAction`, `setUserRolesAction`) which wrap API calls in try/catch and return structured `{ errorKey: string }` objects, `updateUserAction` calls `updateUser()` without error handling. If the API returns 403, 409, etc., the server action throws an unhandled exception that surfaces as a generic "Something went wrong" error with no i18n error key.

```typescript
// Current — no error handling:
export async function updateUserAction(id: string, patch: Partial<User>): Promise<User> {
  const result = await updateUser(id, patch)
  revalidatePath('/users')
  return result
}
```

**Fix sketch.** Follow the same pattern as `deleteUserAction`:

```typescript
export async function updateUserAction(
  id: string, patch: Partial<User>,
): Promise<{ user: User } | { errorKey: string }> {
  try {
    const user = await updateUser(id, patch)
    revalidatePath('/users')
    return { user }
  } catch {
    return { errorKey: 'users.errors.generic' }
  }
}
```

**Tests needed.** Unit test: `updateUserAction` returns `{ errorKey }` when the API returns an error, not an unhandled exception.

## :yellow_circle: bug-0067 -- Invitation endpoints lack token format validation

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/src/invitations/invitations.controller.ts` (lines 1-21)

**Description.** The invitation controller accepts any string as the `token` path parameter and passes it directly to `prisma.saInvitation.findUnique({ where: { token } })`. The token is a 64-character hex string (`crypto.randomBytes(32).toString('hex')`), but no format validation is applied. Additionally, the `GET :token` endpoint returns `{ firstName, email, expired }` -- user PII is disclosed to anyone with a valid or guessed token.

**Fix sketch.** Add `@Matches(/^[a-f0-9]{64}$/)` validation to the token parameter. Consider returning only `{ firstName, expired }` and not `email`.

**Tests needed.** Unit test: request with a malformed token (e.g., `<script>`) returns 400, not a DB query.

## :large_blue_circle: bug-0068 -- TOCTOU race in `updateOrg`, `updateApp`, `deleteOrg`, `deleteApp`

**Fixed:** false
**Severity:** Minor
**Files:**
- `apps/auth-server/src/orgs/orgs.service.ts` (lines 99-135)
- `apps/auth-server/src/apps/apps.service.ts` (lines 58-96)

**Description.** These methods first `findUnique` (to check existence and `isPlatform`), then perform the `update`/`delete` in a separate query. Between the two queries, a concurrent request could delete the entity or change `isPlatform`. An uncaught `P2025` will surface as a 500; more critically, if `isPlatform` changes between check and delete, the platform org/app could be deleted.

**Fix sketch.** Use `prisma.saOrg.update({ where: { publicId, isPlatform: false }, ... })` to make the check atomic. Catch `P2025` and return 404.

**Tests needed.** Concurrency test: simultaneous delete of the same org should not produce a 500.

**Fixed:** false
**Severity:** Minor
**File:** `apps/auth-server/src/token/oauth.service.ts` (lines 14-45)

**Description.** The `codes` Map only deletes entries when they are exchanged. Codes generated but never exchanged (abandoned flows, network failures) remain in the Map forever.
