## :yellow_circle: bug-0048 — Magic link URLs and OTP codes logged to `console.log` in production builds

**Fixed:** false
**Severity:** Warning
**File:** `apps/auth-server/src/auth/auth.config.ts` (lines 53-62)

**Description.** The BetterAuth magic-link and email-OTP plugins use `console.log` as their send handlers:

```typescript
sendMagicLink: async ({ email, url }) => {
  console.log(`[magic-link] ${email} → ${url}`);
},
sendVerificationOTP: async ({ email, otp }: { email: string; otp: string }) => {
  console.log(`[email-otp] ${email} → ${otp}`);
},
```

These are marked as development placeholders ("Wire to your email service in production"), but there is no environment guard. If the server runs in production with `NODE_ENV=production`, magic-link URLs and OTPs are written in plaintext to stdout, which typically flows to log aggregators (CloudWatch, Datadog, etc.). An attacker with log access could intercept magic-link URLs or OTP codes to authenticate as any user.

This is distinct from bug-0004 (email in Sentry/Winston) — this leaks **authentication secrets** (full magic-link URLs and OTP codes), not just PII.

**Fix sketch.** Guard with an environment check and throw if no real transport is configured:

```typescript
sendMagicLink: async ({ email, url }) => {
  if (process.env.NODE_ENV === 'production') {
    throw new Error('Magic link email transport not configured');
  }
  console.log(`[magic-link] ${email} → ${url}`);
},
```

Or better: inject an email service and fail fast at startup if `NODE_ENV=production` and no email transport is configured.

**Tests needed.** Unit test verifying that the magic-link handler throws in production mode when no real transport is registered.

## :large_blue_circle: bug-0049 — JWT token lifetime hardcoded to 3600 seconds with no configuration

**Fixed:** false
**Severity:** Minor
**File:** `apps/auth-server/src/token/token.service.ts` (line 74)

**Description.** The JWT expiration is hardcoded:

```typescript
exp: now + 3600,
```

There is no environment variable or configuration option to change the token lifetime without a code change and redeployment. Different deployment environments commonly need different lifetimes (shorter for high-security environments, longer for internal tools). The 3600-second (1-hour) default is reasonable but should be configurable.

**Fix sketch.** Read from an env var with a sensible default:

```typescript
const TOKEN_LIFETIME = parseInt(process.env.JWT_TOKEN_LIFETIME_SECONDS ?? '3600', 10);
// ...
exp: now + TOKEN_LIFETIME,
```

Add `JWT_TOKEN_LIFETIME_SECONDS` to `.env.example` with a comment.

**Tests needed.** Unit test verifying that the JWT `exp` claim uses the configured lifetime.
