# bug-0291 🟠 High — activation-email `message` branding is spliced into HTML unescaped, allowing stored HTML injection

**Files:**
- `apps/auth-server/src/email/templates/verify-email.template.ts`
- `apps/auth-server/src/email/templates/templates.spec.ts`

**Description:** PR #394 (`feat/branded-activation-emails`, merged today via
`64c8de6`) let any caller with the `platform.apps.manage` permission set a
per-app `activationEmailOverride.message` string that replaces the default
activation-email copy. `apps.service.ts`'s
`assertValidActivationEmailOverride` validates the field is a string and
rejects embedded `\r`/`\n` (to stop email-header injection via `subject`),
but does not — and, being a plain string field meant to hold admin prose,
should not — reject HTML-looking characters like `<`, `>`, `"`, `&`.

`verificationEmail()` in `verify-email.template.ts` then spliced that raw
string directly into the HTML part of the email:

```ts
html:
  `<p>Hi ${firstName},</p><p>${message}</p>${renderButton(verifyUrl)}` + ...
```

with no escaping. `message` had already been through `renderTemplate()` for
`{{firstName}}`/`{{appName}}`/`{{activationUrl}}` substitution, but
`renderTemplate` does no output-context escaping either (its own doc
comment says so explicitly: "a caller substituting a value into HTML... is
responsible for escaping it first" — nothing did).

**Failure scenario:** An admin (or any account holding
`platform.apps.manage` — not necessarily a fully trusted platform operator
in every deployment; it's an app-scoped console permission) sets, e.g.:

```json
{ "message": "<a href=\"https://evil.example/phish\">Verify now</a><div style=\"display:none\">" }
```

Every end user who signs up for that app from then on receives an
activation email whose body renders that attacker-supplied markup as live
HTML: a look-alike link that shadows or replaces the real "Confirm your
email address" button rendered just below it, a hidden `<div>` that can
carry further markup, or a remote-loaded `<img src="https://tracker.example/x">`
for open tracking/beaconing — all inside an email the recipient has good
reason to trust, since it otherwise carries this app's legitimate
activation link and branding. This is a stored-HTML-injection bug in a
transactional email, not a self-XSS: the injecting party (the app admin)
and the affected party (every user who signs up for that app) are
different people.

**Fix:** Added an `escapeHtml()` helper in `verify-email.template.ts` (the
five standard HTML-text-content entities: `& < > " '`) and applied it to
`message` only at the point it's spliced into the `html` output — `text`
stays an unescaped plain-text copy (nothing to inject into), and `subject`
is unaffected (already newline-guarded against header injection, never
rendered as HTML body content). Scoped narrowly to this one field/call
site rather than adding escaping inside `renderTemplate()` itself, since
`renderTemplate()` is also used for values already safe in their context
(e.g. `subject`, a mail header) where blanket escaping isn't appropriate to
decide from inside a generic helper — the caller owns that decision, and
this fix makes `verificationEmail()` make it correctly for the HTML output
it produces.

**Verification:** Added a regression test to `templates.spec.ts` asserting
a `message` containing `<a href="...">`, `&`, and `"` renders HTML-escaped
in `out.html` (and is NOT present as raw markup) while remaining literal,
unescaped text in `out.text`, and that the real activation URL/button are
unaffected. `pnpm --filter @sassy-auth/auth-server exec jest
templates.spec.ts` — 10/10 passing (including the new case).
`pnpm --filter @sassy-auth/auth-server exec tsc --noEmit` — clean. Not run
against a live email send/render in an actual mail client in this
environment; verified by asserting on the generated HTML string directly.

**Related, not fixed here:** `firstName` (the signing-up user's own name,
not app-admin-controlled) is spliced into the same `<p>Hi ${firstName},</p>`
unescaped, consistent with every other email template in this codebase
(`invitation.template.ts`, `password-reset.template.ts`,
`sign-in-code.template.ts` all do the same for their own interpolated
values). That's a user injecting markup into an email addressed to
themselves — self-XSS with no cross-user impact — and fixing it consistently
across all four templates is a larger, separate change than this
one-field, cross-user-impact fix. Worth a follow-up; flagged in today's
TODO.
