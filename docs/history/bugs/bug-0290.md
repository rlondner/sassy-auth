# bug-0290 🔴 Critical — auth-server crashes on boot outside production when dev TLS certs are absent

**Files:**
- `apps/auth-server/src/main.ts`
- `apps/auth-server/src/https-options.ts` (new)
- `apps/auth-server/src/https-options.spec.ts` (new)

**Description:** `0002a11` (`dev(sec): added certificates to run API with
https`, landed directly to `dev` on 2026-09-14) made `bootstrap()` read two
mkcert-generated dev TLS certificates —
`apps/auth-server/secrets/localhost-key.pem` and `localhost.pem` — via a
plain, unconditional `fs.readFileSync` whenever
`process.env.NODE_ENV !== 'production'`. Both files are gitignored
(`.gitignore` lines 63–64, added in the same commit) and generated
per-machine; nothing checks whether they exist before reading them, and
nothing in the repo — README, `DEPLOYMENT.md`, the Dockerfile, or CI —
generates or ships them.

**Failure scenario:** Any environment that reaches this code path with
`NODE_ENV` unset or `'test'` and no local `secrets/` directory now crashes
`auth-server`'s Node process with an uncaught `ENOENT` before it can bind a
port at all:

- **A fresh clone.** `pnpm install && pnpm dev` (README's own documented
  path, step 6 of "Getting Started") has no `secrets/` directory yet — there
  is no setup step anywhere that creates one.
- **`docker compose up`** — the README/`docker-compose.yml`-documented
  one-command Quick Start. The Dockerfile's own header comment says running
  with `NODE_ENV` unset is "load-bearing, not laziness" (needed so the
  session cookie's `Secure` flag matches plain-http `docker compose`
  access), and `docker-compose.yml` sets `BETTER_AUTH_URL:
  https://localhost:3010` with no `NODE_ENV` at all. The image build (`COPY
  . .`) also never generates or copies in mkcert certs. `docker compose up`
  now fails immediately.
- **CI e2e.** `.github/workflows/e2e.yml` sets `NODE_ENV: test` for the
  whole `admin-e2e` job and starts `auth-server` via `pnpm --filter
  @sassy-auth/auth-server dev` (`apps/admin-e2e/playwright.config.ts`'s
  `webServer` entry), which runs `main.ts`'s `bootstrap()` directly. No cert
  step exists in the workflow. (Verified via `gh run list`/`gh run view` that
  the two `dev`-branch e2e runs since `0002a11` landed both fail — currently
  at the pre-existing bug-0282 `Build admin console` step, which runs
  earlier in the job and would mask this crash until that unrelated blocker
  clears; confirmed the crash directly by reading the code path rather than
  by reproducing a green run that then hits it.)

**Fix:** PR #392. Extracted cert resolution out of `main.ts`'s inline block
into `resolveHttpsOptions(isDev, secretsDir)` in a new
`https-options.ts` module (kept separate from `main.ts` because importing
`main.ts` directly triggers its top-level `bootstrap().catch(...)` call,
which needs a live Postgres connection — same constraint documented in
`main-body-parser.spec.ts`). The function now checks `fs.existsSync` for
both files before reading; if either is missing it logs one
`console.warn` pointing at the new README section and returns `undefined`,
so Nest falls back to plain HTTP exactly as it did before `0002a11` instead
of crashing. Also documented the mkcert cert-generation step in `README.md`
→ "Local HTTPS certificates" (previously undocumented for `apps/auth-server`
entirely — `apps/admin`'s `--experimental-https` is a different,
self-generating mechanism and needed no such step).

**Verified:** `pnpm --filter @sassy-auth/auth-server exec jest
https-options` — 4/4 passing (missing-both-certs falls back with a warning
and does not throw, present-both-certs loads real buffers, not-dev returns
undefined even with certs present, missing-one-of-two falls back). `pnpm
--filter @sassy-auth/auth-server exec tsc --noEmit` — clean. Not run against
a live `docker compose up` or the full CI e2e job in this environment (no
Docker daemon / no ability to trigger a fresh Actions run from here); CI on
PR #392 will confirm the crash no longer reproduces once bug-0282 is fixed
and the job reaches this step.

**Fixed:** false
