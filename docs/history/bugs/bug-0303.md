# bug-0303 🟡 Medium — `shouldPromptTwoFactor`'s "always prompt" sentinel (`intervalDays = 0`) fails on a same-millisecond re-check

**Fixed:** true

**Files:**
- `apps/auth-server/src/auth/should-prompt-two-factor.ts:33-35`
- `apps/auth-server/src/auth/should-prompt-two-factor.spec.ts` (regression test added)

**Description:** The function's docstring states `intervalDays = 0`
means "always prompt if not enrolled" (documented as useful for
testing). The implementation computed this generically as
`elapsedMs > intervalMs`, where `intervalMs = intervalDays * 86_400_000`.
With `intervalDays = 0`, `intervalMs` is `0`, so the check reduces to
`elapsedMs > 0`. If `now` and `promptedAt` ever resolve to the exact
same millisecond — plausible when a prompt is recorded and immediately
re-evaluated within the same request, or in any test/fixture using a
fixed clock for both values — `elapsedMs === 0` and the function
returns `false`, contradicting the documented "always prompt" contract
for the `intervalDays = 0` sentinel.

**Failure scenario:** A caller that records `promptedAt = now()` and
then, in the same tick (or using a frozen test clock), re-evaluates
`shouldPromptTwoFactor` with `intervalDays: 0` gets `false` instead of
the guaranteed `true` the docstring promises — defeating the stated
"testing" use case intermittently and non-deterministically (it depends
on whether a millisecond boundary was crossed between the two calls).

**Fix:** Added an explicit `if (intervalDays === 0) return true;`
short-circuit (after the `promptEnabled`/`twoFactorEnabled`/`promptedAt
=== null` checks, before the generic elapsed-time math), so the
sentinel is unconditional rather than depending on wall-clock
granularity.

**Verification:** Added a regression test
(`should-prompt-two-factor.spec.ts`) asserting `promptedAt === now`
with `intervalDays: 0` returns `true`. `pnpm --filter
@sassy-auth/auth-server exec jest should-prompt-two-factor.spec.ts` —
10/10 passing (was 9/9 before the new test).
