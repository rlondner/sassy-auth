### 🟡 `c641152` — fix(social): repair DI/CORS/POST bugs found by the e2e gate

Four separate fixes in one commit: `@Optional() @Inject()` decorators on `SocialService` (interface-typed params were erased to `Object`); `social-buttons.tsx` switched from GET navigation to `fetch` POST + navigate to returned `url`; a scoped CORS middleware added to the raw-Express `/api/auth/*` route; a DB migration adding a global (`appId=NULL`) row for the `stub` provider.

**Findings**

- 🟡 **CORS runs before the auth rate limiter.** `expressApp.all('/api/auth/*', authCors, createDefaultAuthRateLimiter(), ...)` means OPTIONS preflights and cross-origin POSTs are answered / passed even if the rate limiter would otherwise throttle. Preflights themselves are cheap, but confirm the rate limiter is not the layer you rely on to absorb a preflight storm. Consider placing `authCors` *after* `createDefaultAuthRateLimiter()` for non-OPTIONS methods, keeping only OPTIONS short-circuited early.
- 🟡 **Reflected `Access-Control-Allow-Headers`.** `res.setHeader('Access-Control-Allow-Headers', req.headers['access-control-request-headers'] ?? 'content-type')`. Even though the browser makes this practically low-risk, an explicit allowlist (`'content-type, authorization'` — whatever `sign-in/social` actually needs) is clearer intent and easier to audit than reflection.
- 🟡 **`@Optional() @Inject('DB_CLIENT')` with no matching provider is pragmatic but obscure.** DI always injects `undefined`, and the constructor default parameters (`prisma`, `process.env`) always win. Anyone reading `SocialService` will wonder what those tokens resolve to. Either register real providers (`{ provide: 'DB_CLIENT', useValue: prisma }`) so the intent is grep-able, or drop the decorators and use module-scope `prisma`/`process.env` directly with a comment.
- 🟡 **`social-buttons.tsx` error path collapses all failures to `/oauth-error` with no `code=`.** The middleware and the rest of the flow classify outcomes (`social_email_unverified`, `social_signin_rejected`, …); a raw network / non-OK response here loses that classification. At minimum, pass `?code=social_start_failed` (or similar) so the error page can render something meaningful and the audit event has a distinct outcome.
- 🟢 Root-cause analysis in the commit body and inline comments is exceptional — every fix cites the exact file:line in `better-auth` / `nestjs` sources that proves the assumption. Keep this pattern.
- 🟢 The migration (global-seed for `stub`) is scoped, idempotent-friendly (`appId=NULL` row), and matches `resolveEnabledProviders`' documented contract.

**Recommendation:** Approve with follow-up for (a) middleware ordering, (b) explicit allow-headers, (c) `oauth-error` code on start-POST failure.
