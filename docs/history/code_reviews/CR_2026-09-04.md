### `6680e2a` — chore(db): bump prisma to v7 — Raphael Londner

- **Scope:** `@prisma/client` and `prisma` 6 → 7.0; added `@prisma/adapter-pg@^7.0.0`, `pg@^8.13.0`, `@types/pg@^8.11.0`.
- **Findings:**
  - 🟡 Prisma 7 makes the **driver adapter the default execution path**; the built-in binary engine is deprecated. Adopting `@prisma/adapter-pg` is correct (see `d7bc85c`), but transactional semantics under driver adapters differ from the binary engine — `$transaction([...])` batching and interactive transactions run through `pg` sessions. **Verify** any long-running or nested transaction paths (auth-server signup/2FA enrollment flows) still hold their expected isolation level and connection affinity.
  - 🟡 `pg` connection pool now lives inside the app process. No pool sizing config visible — `PrismaPg` will use `pg` defaults (max 10 connections). For production `auth-server`, set an explicit `max` per pod to avoid Postgres `too many connections` under horizontal scale.
  - 🟢 Peer graph resolves cleanly against `better-auth@1.6.11`.
  - **Recommendation:** Add a targeted integration test that exercises a multi-statement `$transaction` and asserts rollback on failure, to catch adapter-vs-engine behavioral drift before it hits prod.

### `d7bc85c` — feat(db): construct PrismaClient with `@prisma/adapter-pg` — Raphael Londner

- **Scope:** `packages/db/index.ts` now imports from local generated client and injects `PrismaPg` adapter. `two-factor-fields.spec.ts` updated to import `Prisma` from the local generated path.
- **Findings:**
  - 🔴 **Adapter is constructed at module-load time using `process.env.DATABASE_URL` — before** the fail-fast guard was in place at this commit. Guard was added in the next commit `bb888c2`, so bisecting between these two commits leaves a broken state (adapter constructs with `connectionString: undefined`, pg driver throws at first query with an opaque error). Not blocking now (fix landed within the same PR), but for future migrations, land env-guard **before** the code that consumes it.
  - 🟡 Dev-mode singleton (`globalForPrisma.prisma`) covers `PrismaClient` but **not the `adapter` / underlying `pg.Pool`**. Every HMR reload in Next dev creates a fresh `PrismaPg` → fresh pool → leaks connections until Postgres kicks them. Wrap the adapter in the same global:
    ```ts
    const globalForPrisma = globalThis as unknown as {
      prisma?: PrismaClient;
      adapter?: PrismaPg;
    };
    const adapter = globalForPrisma.adapter ?? new PrismaPg({ connectionString: process.env.DATABASE_URL });
    if (process.env.NODE_ENV !== 'production') globalForPrisma.adapter = adapter;
    ```
  - 🟡 `export * from './generated/prisma/client'` — verify no accidental re-export of `PrismaClient` symbol collision (works today but fragile if the generator emits a differently-named default export in future minor versions).
