## Review method

Given the size of the social-auth diff (51 files, ~2,900 lines across
`apps/auth-server/src/social/`, `apps/auth-server/src/token/`, the admin
login flow, and 6 new DB migrations), this review split into four parallel
specialist passes over `git diff fd98fab..HEAD`:

- **Security regression** (open redirect, token/state/nonce handling, secret
  handling, SSRF, PII-in-telemetry, the stub-IdP production-reachability
  question) — **0 findings.** The stub IdP's NODE_ENV allowlist, Apple
  client-secret handling, PKCE verification, and audit-sink PII separation
  were all independently verified sound.
- **Authorization** (per-app provider toggle, org/app scoping, invite-only
  enforcement, admin settings endpoints) — **0 findings**, across 9 reviewed
  entry points. Confirmed the per-app provider toggle is deliberately
  cosmetic (UI-only) and the real invite-only/org-scoping gates live
  elsewhere (`disableSignUp`, `evaluateSessionGate`,
  `saUser.org.appId !== app.id`) — exactly the kind of "toggle that looks
  like a security boundary but isn't" pattern worth a future reviewer
  double-checking before "tightening" it into one.
- **Data integrity** (6 new migrations, schema.prisma additions) — all six
  migrations are additive, none destructive; **1 Medium finding** (see
  bug-0269).
- **Concurrency** (OAuth code redemption, the e2e stub-IdP's in-memory
  state) — production OAuth code exchange is genuinely atomic (`@id`
  primary key + `delete`); **1 High finding**, scoped to test
  infrastructure only (bug-0270).

Plus manual review of the two new CI workflows (`trivy.yml`,
`ai-security-review.yml`) and a spot-check of README/`.env.example` against
what the feature actually implements, which surfaced three more findings
(bug-0265, 0266, 0267).

## Commit-by-commit notes worth keeping

- **`8d86e15` (CI workflows):** both new security workflows were
  non-functional as landed — see bug-0265/0266. Once fixed, `trivy.yml`'s
  CRITICAL-CVE gate and `ai-security-review.yml`'s PR-comment review should
  both actually run for the first time on the PRs from this review.
- **`0987b1c` (Sentry telemetry adapter):** excellent boundary discipline —
  one adapter file (`telemetry-sentry-adapter.ts`) is the sole `@sentry/*`
  import surface for the whole social feature, and its header comment cites
  exact file:line evidence for why the OTel-Logs route doesn't work on this
  stack. The PII-separation contract (`email`/`providerSub` never reach
  telemetry) is enforced at the call sites in `record-federation-event.ts`,
  not inside the adapter itself — not a bug (verified no current caller
  violates it) but worth an allowlist inside the adapter as defense-in-depth
  before a future caller adds one. See TODO.
- **`c641152` (DI/CORS/POST repair round):** the root-cause analysis in this
  commit body is unusually good — every fix cites the exact file:line in
  `better-auth`/`nestjs` source that proves the assumption. The scoped CORS
  middleware added here for `/api/auth/*` reflects
  `Access-Control-Allow-Headers` from the request rather than using an
  explicit allowlist, and runs before the auth rate limiter for all methods
  including OPTIONS — low risk (preflights are cheap, and the reviewed CORS
  origin-matching itself is a correct exact-match allowlist) but worth
  tightening. See TODO.
- **`47caeae` (e2e spec repair round 1):** `countAccountsForEmail`'s test
  helper uses `escapedEmail.replace(/'/g, "''")` string-interpolated SQL.
  Inputs are test constants today so this isn't exploitable, but it's a
  footgun for whoever parameterises the caller next. See TODO.
