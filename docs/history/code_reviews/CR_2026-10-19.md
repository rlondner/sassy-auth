#### 🟡 Warnings — Security & operations
1. **No traffic-splitting / canary.** `gcloud run deploy` without `--no-traffic` promotes a new revision to 100% immediately. For an **auth-server** this is risky — a bad JWT verification regression is instant tenant-wide impact. Pattern:
   ```
   gcloud run deploy ... --no-traffic --tag=next
   # smoke-test the tagged URL
   gcloud run services update-traffic ... --to-revisions=sassy-auth-server-<rev>=100
   ```
2. **Secret references pinned to `:latest`.** If `RSA_PRIVATE_KEY` or `BETTER_AUTH_SECRET` rotates mid-deploy (or between the auth-server step and the admin step), services can land on inconsistent versions. For an auth stack, pin versions by numeric id at deploy time (and bump deliberately on rotation).
3. **Seed jobs run on every deploy.** `sassy-auth-seed` and `sassy-auth-seed-vibecast` fire unconditionally in the loop. The runbook asserts idempotency against the shared DB, but if that assumption drifts (new seed script, test data mutations) you'll silently corrupt production. Add either (a) `if: ${{ github.event.inputs.run_seeds == 'true' }}` input, or (b) a seed-is-already-complete sentinel row the job checks.
4. **Migration job: `--max-retries 0` + `--task-timeout 10m`.** No retry on transient DB blips, no partial-state alerting. For a job that mutates schema, acceptable but opaque — pair with a Secret Manager-stored baseline backup confirmation, or at minimum fail-loud by reading `gcloud run jobs executions describe` after `--wait`.
5. **`--allow-unauthenticated` on both services.** Expected for public endpoints, but confirm the auth-server has WAF/rate-limit guard **in-app** (Cloud Run won't enforce it) — Turnstile covers signup; verify `/token`, `/oauth/authorize`, and `/.well-known/*` are rate-limited at the app layer.
6. **`timeout-minutes: 40`** is tight when a cold `pnpm` monorepo build + two image pushes + migrate + two seeds all run serially. One slow Artifact Registry push will trip it. Suggest 60.
