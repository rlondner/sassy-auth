**Findings:**

- 🟢 **Correct primitive.** Adding `COOKIE_PREFIX` (wired through BetterAuth's `advanced.cookiePrefix` server-side and through `getBetterAuthCookieName(cookie, isProduction, prefix?)` client-side) is the right fix. Two deployments forced onto the same `COOKIE_DOMAIN` can only be disambiguated in the browser's cookie jar by name or `Path`; name is the clean lever.
- 🟢 **Backwards-compatible rollout.** Production leaves `COOKIE_PREFIX` unset in `render.yaml`, so `getBetterAuthCookieName` defaults to `better-auth` and every currently-valid `__Secure-better-auth.session_token` cookie remains valid. Only staging users (small, internal population) get signed out at deploy — acceptable.
- 🟢 **Env group wiring is right.** `render.staging.yaml` places `COOKIE_PREFIX=sassy-staging` in the shared `sassy-auth-staging` env group, so `auth-server` and `admin` pull the same value — no drift possible from the Render side.
- 🟢 **Test coverage is proportional.** Two new test cases in `auth.config.spec.ts` (default and override paths for `advanced.cookiePrefix`); one new case in `better-auth-cookie-name.test.ts` covering custom prefix × production `__Secure-` combination. Existing default-behavior tests untouched.
- 🟢 **Comments name the bug.** Every touched call site carries a `bug-0293:` comment linking the change to the incident. Future readers debugging cookie-name resolution will land on the right context.

- 🟡 **DRY / correctness risk (medium): prefix resolution duplicated at 5 admin call sites.** The pattern `process.env.COOKIE_PREFIX || 'better-auth'` (and the BetterAuth default fallback string) is now hardcoded in `middleware.ts`, `login/page.tsx`, `login/actions.ts`, `account/security/actions.ts`, and `(admin)/actions.ts`. A future change (env var rename, default upstream change, adding a `two_factor_dev` cookie) requires every site to be updated in lockstep. **Recommend** either (a) overloading `getBetterAuthCookieName(cookie, isProduction)` to read `process.env.COOKIE_PREFIX` internally when `prefix` is omitted — simplest, one source of truth; or (b) exporting `resolveCookiePrefix(): string` from `@sassy-auth/types` and having every call site pass its return value. Option (a) is preferable because it preserves the existing 2-arg call signature and makes the 3-arg form redundant.

- 🟡 **Test gap (medium): no integration assertion that server and admin agree on the resolved name at runtime.** The unit tests validate each side independently. A regression where one of the five admin call sites is missed on a future edit (or where staging's env group somehow drops the var on only one service) passes CI. **Recommend** a lightweight cross-boundary test: either a shared constant test that imports the resolved cookie name from both `auth.config.ts` and `@sassy-auth/types` under the same `process.env.COOKIE_PREFIX`, or an e2e smoke that reads the `Set-Cookie` name from an actual sign-in response and diffs it against admin's `SESSION_COOKIE_NAME`. This would also catch a class of BetterAuth-internal renames.

- 🟡 **Rollout note missing (minor).** Not in the PR: mention in the merge/deploy notes that staging users with an existing session will be signed out at deploy because the cookie name changes. Not a bug — expected — but worth calling out so it isn't reported as an incident.

Still an outstanding hygiene item that CI or a pre-commit hook should verify `dist/` matches `src/` for workspace packages that commit build output — but not blocking here.

- 🟢 **Comment quality is high.** The `bug-0293` block in `auth.config.ts` reads as a self-contained explanation of why the option exists (identical Domain + identical name + identical Path → jar-slot collision), so a future maintainer removing `COOKIE_PREFIX` under the wrong assumption will see the reason inline.

### `5329d1e` fix(auth): scope session cookie to shared parent domain in production — Raphael Londner  (PR #435, merged)

**Scope:** `.env.example`, `DEPLOYMENT.md`, `apps/auth-server/src/auth/auth.config.ts`, `render.staging.yaml`, `render.yaml` (+63/−0).

**Findings:**
- 🟢 **Root-cause fix for a real production bug.** Federated (Google/Microsoft/Apple) sign-in was dropping the session because BetterAuth sets the session cookie mid-OAuth-callback on `auth-api.milissai.com`, and without a `Domain` attribute that cookie is host-only — the admin console at `auth.milissai.com` never sees it. Setting `COOKIE_DOMAIN=.milissai.com` and threading it into BetterAuth's `advanced.crossSubDomainCookies` is the correct minimal fix.
- 🟢 **Env-var-gated, defaults to unset.** Local dev (both services on `localhost`) and any deployment on a single host is unaffected.
- 🔴 **Regression: bug-0293 introduced in the same commit.** Setting `COOKIE_DOMAIN=.milissai.com` on `render.staging.yaml` *and* `render.yaml` forces staging onto the same cookie `Domain` as production, since `auth-staging.milissai.com`/`auth-api-staging.milissai.com` don't share a narrower suffix. Combined with the identical default cookie name (`better-auth.session_token`) and Path, this makes staging and production write to the same slot in a shared cookie jar — surprise sign-outs for anyone toggling between envs. The commit's own inline comment on `render.staging.yaml` diagnosed this exact mechanism and shipped it as an accepted "UX quirk." Fix is in PR #436 (`COOKIE_PREFIX` env var).
- 🟡 **Process gap:** self-diagnosed bug in an inline comment should have been either fixed in the same PR or filed as a tracked bug at merge time, not deferred to next-day review. (Called out in `TODO_2026-09-29.md`.)

**Recommendation:** Approve as merged (correct primary fix). Follow-up regression is being fixed in PR #436.
