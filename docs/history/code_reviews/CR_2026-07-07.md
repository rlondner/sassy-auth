### `14b0dbc` fix(search): escape LIKE wildcards — bug-0188
Branch: `worktree-agent-ad8a9a250dc8127da` · Files: 4 (`apps`, `orgs`, `permissions`, `roles` services) · +15/-5

**Findings**
- 🟡 **Escape may be a no-op in Prisma+Postgres.** Prisma's `contains` mode translates to `ILIKE '%' || $1 || '%'` without an `ESCAPE` clause. Postgres interprets `\` in `ILIKE` patterns as a literal backslash unless `ESCAPE '\'` is set explicitly. Confirm behavior with an integration test — e.g., search `q=%` should return exact-match rows only, not everything. If ineffective, the fix should switch to `startsWith`/`endsWith` (which internally handle escaping) or drop to raw SQL with `ESCAPE`.
- 🟡 **DRY violation.** The `q.q.replace(/%/g, '\\%').replace(/_/g, '\\_')` snippet is duplicated in 4 services. Extract to `packages/db/utils/likeEscape.ts` (or `apps/auth-server/src/common/like-escape.ts`) and import — reduces drift risk when the escape rules change (e.g., adding `\` itself, which is currently NOT escaped and would be interpreted).
- 🔴 **`\` is not escaped.** If a user supplies `q=foo\`, the resulting pattern contains a lone backslash that either escapes the next `%` from Prisma's `%$1%` wrapping (turning the trailing wildcard into a literal) or errors depending on collation. The escape function must also handle backslash: `.replace(/\\/g, '\\\\')` **before** the `%`/`_` replacements.
- 🟡 No test. Add unit tests for `search=%`, `search=_`, `search=\` on each list endpoint.
- **Recommendation:** Request Changes — add backslash escape, extract helper, verify Postgres actually respects `\` as escape (add `ESCAPE '\'` if not) with an integration test.
