### PR #378 — Activation webhook + pending-account signup
- **Author:** rlondner  &nbsp; **Base:** `dev` ← `feat/activation-webhook`
- **Files:** 21 &nbsp;|&nbsp; **+2475 / −12** &nbsp;|&nbsp; **Mergeable:** true, **Draft:** false
- **Scope:** Two coupled changes:
  1. Per-`SaApp` outbound activation webhook fired on every `SaUser` → `active` transition (email verification, invitation acceptance, admin re-activation). HMAC-SHA256 signed, 5 s timeout, 1 retry on network/5xx, `SaAuditEvent` outcome logging, non-throwing.
  2. Signup now mints an OAuth authorization code with `amr:['signup']` in `RegistrationService` and returns a `redirectUrl` so the new (still-pending) user is authenticated immediately, before email verification. `/api/token` accepts this code even when the user's `status !== 'active'`, provided the account is not `inactive`.

#### Findings

**🟡 Webhook — SSRF: private-IP hosts still allowed (Warning, actionable)**
- `apps/auth-server/src/apps/dto/update-app.dto.ts` gates `webhookUrl` with `@IsAppUrl()`, whose secure-mode policy (`app-url-policy.ts`) blocks non-HTTPS, `localhost`, and loopback hostnames — but **not** RFC1918 private ranges (`10/8`, `172.16/12`, `192.168/16`), link-local (`169.254/16`, incl. `169.254.169.254` cloud metadata), or `.internal` corporate hosts. All of those satisfy the current `host.includes('.')` check.
- `notify-activation.ts` correctly sets `redirect: 'error'` (blocks a signed re-POST to an internal target via 302), but the initial POST still lands wherever the DTO accepted.
- Impact: an admin (or anyone who compromises admin credentials) can point a signed webhook at internal services, using Sassy as a blind side-channel probe / exfil vector.
- Recommendation: extend `app-url-policy.ts` to reject private/link-local/loopback IP literals in secure mode, and resolve the hostname pre-flight (or in a scheduled revalidation) to catch DNS-rebinding. Ship this as a follow-up hardening PR — do not block this merge.

**🟡 Webhook — no replay/idempotency headers on the signed body (Warning)**
- Signed payload is `{event, userId, appPublicId, activatedAt}`. There is no timestamp header, no nonce, and no `X-Sassy-Event-Id` / `Idempotency-Key`. Receivers cannot distinguish the initial delivery from the automatic retry, and cannot enforce a signature freshness window.
- Recommendation: add `X-Sassy-Timestamp` (include it in the HMAC input) and a stable `X-Sassy-Event-Id` (random per event, identical on retry). Document the verification recipe in `SECURITY.md`.

**🟡 Signup redirect — `state`/`nonce` absent by design; document the constraint (Warning)**
- `RegistrationService.register()` mints the code without any `state` or `nonce` since there was no upstream `/authorize`. The response's `redirectUrl` therefore delivers `?code=…` alone. Any relying party enforcing `state` (correctly, per RFC 6749 §10.12) will reject it.
- The exception in `token.controller.ts` also relaxes the active-user check for `amr:['signup']` codes — narrow and correct, but this is the second place in the codebase where signup-flow codes get special handling. Consider a dedicated `CodeFlow` enum or a comment linking both sites so future refactors keep them in sync.
- Recommendation: (a) call this out explicitly in the PR body / API docs — clients embedding the admin signup redirect must not enforce `state` on that specific response; (b) add a test that a code minted with `amr:['signup']` cannot be replayed after the account is deactivated (present) *and* cannot be redeemed after email is verified + account moves to `active` a second time (edge).

**🟢 Webhook — good defensive posture**
- `redirect: 'error'` on fetch, 5 s `AbortController` timeout, single retry only on network/5xx (`isRetryable`), audit log wrapped in try/catch so it can never surface, `notifyActivation` never throws (caller in `users.service.ts` and `invitations.service.ts` `await`s it — safe because of the internal try/catch).
- Correct no-op guard in `users.service.ts`: only fires when `dto.status === 'active' && existing.status !== 'active'` — no re-fire on idempotent re-save.
- `webhookSecret` stored plaintext with the correct rationale in the schema comment (used to *sign* outgoing, not verify incoming — hashing would break signing).

**🟢 Signup code path — correctness controls in place**
- Only fires when `app.clientSecretHash` is set (public clients can't complete without PKCE — enforced in `/api/token`).
- Picks the oldest registered login redirect deterministically (`orderBy: { id: 'asc' }`) — avoids ambiguity when multiple URIs are registered.
- Exception in `token.controller.ts` distinguishes `pending` (allowed) vs `inactive` (rejected) — matches product intent.

**🟢 Tests**
- New: `notify-activation.spec.ts` (159 lines), `registration.service.spec.ts` (+79), `token.controller.spec.ts` (+176), `users.service.spec.ts` (+33), `invitations.service.spec.ts` (+33), `auth.config.spec.ts` (+33), `apps.service.spec.ts` (+89). Coverage of the new logic looks thorough.

**Recommendation:** **Approve with follow-ups.** No hard blocker. File follow-up issues for (1) private-IP SSRF hardening in `app-url-policy.ts`, and (2) `X-Sassy-Timestamp` + `X-Sassy-Event-Id` headers before external customers integrate.
