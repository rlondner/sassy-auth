### 3. Confirmed schema gaps (bugs 0026 / 0027)

`packages/db/schema.prisma`:

```prisma
model SaPermission {
  ...
  name     String  @unique          // ⚠️ globally unique — should be @@unique([appId, name])
  appId    Int
  ...
}

model SaRole {
  ...
  name     String                    // ⚠️ no uniqueness at all
  appId    Int
  ...
  // no @@unique([appId, name])
}
```

The `P2002` catch blocks in both services return user-friendly "name already exists" errors that **will never fire for roles** (no DB constraint) and **fire incorrectly for permissions** when the duplicate is in a different app. Two apps cannot have `users.read`, and two identically-named roles in the same app silently coexist.

**Recommendation.** Author the Prisma migration changing `SaPermission.name` from `@unique` to `@@unique([appId, name])` and adding `@@unique([appId, name])` on `SaRole`. Add a data-cleanup step if any existing rows would collide.

## 🟡 Warnings

### 4. `PermissionsService.createPermission` — double-write placeholder pattern

`createPermission` (and the mirrored `RolesService.createRole`) writes a row with `publicId: 'placeholder'`, then updates it with the encoded sqid:

```ts
const draft = await tx.saPermission.create({ data: { publicId: 'placeholder', ... } });
return tx.saPermission.update({ where: { id: draft.id }, data: { publicId: sqids.encode(draft.id) }, ... });
```

Two writes per create inside a transaction. Acceptable, but if `publicId` is `@unique`, concurrent creates may collide on `'placeholder'` and one will P2002. Verify the unique index allows this race-free, or use a deferrable constraint, or generate the sqid from a sequence value pre-insert.

**Recommendation.** Add a concurrency test (two parallel creates) and either pre-allocate the id (e.g., `prisma.$queryRaw` `SELECT nextval(...)`) or use a unique random placeholder per request.
