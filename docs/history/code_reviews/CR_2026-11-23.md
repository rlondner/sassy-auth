### PR #479 — `fix(auth-server): validate redirect_uri before the PKCE requirement check (bug-0305)` by rlondner

- **Files changed:** 3 | **+100 / -13**
- **Change:** Reorders `TokenController.oauthAuthorize` so `assertRedirectUriAllowed(redirectUri, app)` runs *before* the PKCE‑requirement check. Previously `pkceRequired = !isConfidential || isCustomSchemeRedirect(redirectUri)` was computed from the raw, attacker‑controlled `redirect_uri` *before* its registry check.

**Findings**

- 🟢 **Correctness (root cause):** The ordering fix is sound. `isCustomSchemeRedirect` reads raw input; deciding PKCE policy from it before registry validation meant an unregistered custom‑scheme URI with no `code_challenge` surfaced `INVALID_REQUEST` (generic PKCE error) instead of `INVALID_REDIRECT_URI`. Post‑fix, PKCE policy is decided only from a URI known to belong to the app.
- 🟢 **Security:** Not an exploitable bypass pre‑fix (fail‑closed either way; never redirects to an unvalidated URI). Post‑fix preserves that invariant — `redirectUriValidated` is still tracked correctly, and the two blocks that depend on it (prompt=none and post‑validation error redirects) remain downstream of `assertRedirectUriAllowed`. The warn log (`oauth.redirect_uri.rejected`) logs only `attemptedOrigin`, not the raw URI or credentials.
- 🟢 **Test coverage:** Adds a focused regression test for the previously uncovered case (unregistered custom‑scheme + missing PKCE → `INVALID_REDIRECT_URI`). Two pre‑existing PKCE tests are updated to expect a `302` OAuth error redirect (per RFC 6749 §4.1.2.1) instead of a bare `400` — this is a correct consequence of the reorder: a PKCE failure on an otherwise‑valid, registered URI should now be reported via client redirect, consistent with every other post‑validation failure.
- 🟡 **Behavioral change for callers:** The reorder means that for a *valid* redirect_uri, a missing PKCE challenge now returns `302` with `?error=invalid_request` instead of `400 JSON`. This is spec‑correct but is a public contract change for any client that distinguished the two shapes. Not expected to affect conforming clients, but worth a one‑line note in the CHANGELOG under "Changed" (currently only the "Fixed" bullet is present).
- 🔴 **CI red on this PR (mergeability blocker):**
  - `admin-e2e: failure` — step `Run e2e` failed. `dev`’s `admin-e2e` is green at the same base, so this is PR‑specific (real regression or flake — rerun once to disambiguate before merge). Note: the PR body / `BUGS_2026-11-23.md` state "101/101 pass"; that is the unit suite (`token.controller.spec.ts` + `redirect-uri.spec.ts`), not `admin-e2e`, so this CI failure is unacknowledged in the PR narrative.
  - `Trivy SCA & Vulnerability Scan: failure` — same failure present on **every open PR** (see §Repo‑wide notes). Pre‑existing CI issue, not caused by this change.
- 🟢 **Architecture / NestJS patterns:** Idiomatic — no new dependency, same `BadRequestException(TokenErrorCode.*)` pattern, same Winston logger context.

**Recommendation:** **Approve conditional on CI** — rerun `admin-e2e`; if it passes, merge. If it fails deterministically, investigate before merge (the diff does change observable `/authorize` response shape for one path, which could legitimately break an e2e assertion).
