### OIDC layer

**`a220f2b` — feat(oidc): serve /.well-known/openid-configuration** — by Raphael

- 🔴 **Discovery lies about supported client auth.** Advertises `client_secret_basic` and `client_secret_post` in `token_endpoint_auth_methods_supported`, but `TokenController.oauthToken` only validates PKCE — no client-credential parsing exists. Conformant clients may treat this as a downgrade signal, or fail hard. Either implement both auth methods or restrict to `['none']` until they land.
- 🟡 `claims_supported` advertises the non-standard, non-namespaced `org` claim. Spec-compliant clients may ignore. Use a URI-style key (`https://sassy-auth/org`) or document as SassyAuth-specific.
- 🟢 Placeholder-issuer fallback logs a warn but still serves; a mis-deployed instance will hand out `https://placeholder-issuer.example`. Fail hard in non-dev.
- **Recommendation:** Request Changes — fix the token_endpoint_auth_methods lie before this ships.

**`d08d88e` — feat(oidc): carry nonce, granted scope, auth_time on authorization codes** — by Raphael

- 🟡 `auth_time` is set to `session.session.createdAt`. That is the session-issue moment, not necessarily when credentials were last verified — if the session survives an MFA step-up, `auth_time` under-reports. Acceptable for MVP; document semantics or feed it from the actual auth event.
- 🟡 `codeVerifier: string | undefined` + `if (entry.codeChallenge) { ... }` — the comment claims "caller is responsible for confidential-client auth," but no such enforcement exists in `TokenController`. Today `oauthAuthorize` refuses to mint codes without a challenge (`!codeChallenge → throw`), so the branch is unreachable — but the trap is armed for the moment someone adds `client_secret_*` auth (see `a220f2b`). Add a controller-side assertion **and** an integration test proving a challenge-less code cannot be exchanged.
- 🟢 `parseScopes` silently drops unknown scopes — OAuth allows this, but consider `invalid_scope` for known-but-unsupported values like `offline_access`.
- **Recommendation:** Approve with a follow-up test.

**`b2af7a2` — fix(oidc): carry nonce/scope through login-redirect + restore timing-safe PKCE** — by Raphael

- 🟢 Restores `crypto.timingSafeEqual` — good catch. **Approve.**

**`d89d735` — feat(oidc): issue an id_token when openid scope is granted** — by Raphael

- 🟡 id_token omits `azp`. With single-string `aud` the claim is technically optional, but many verifiers still expect `azp = client_id`. Emit it defensively.
- 🟡 `at_hash` uses `crypto.createHash('sha256').update(token, 'ascii')`. Access tokens are already JWTs (ASCII-safe), so behavior is correct today; add a comment or refuse to hash non-ASCII tokens explicitly so the invariant survives future refactors.
- 🟢 1h id_token TTL matches access_token TTL — fine, but id_tokens should not be used as session credentials; add that guidance to docs.
- **Recommendation:** Approve, add `azp`.

**`b3d6c1c` — feat(oidc): add /userinfo endpoint** — by Raphael

- 🔴 **Missing `WWW-Authenticate: Bearer …` header on 401.** RFC 6750 §3 requires it; OIDC Core §5.3.3 mandates `WWW-Authenticate: error="invalid_token"` on unauthorized userinfo. Conformant SDKs (google-auth-library, openid-client) parse it. Set the header before throwing.
- 🟡 `verifyAccessToken` does not verify `aud`. Any access token this server issued can call /userinfo regardless of the target app. OIDC permits this, but you lose the ability to detect token substitution. At minimum log the `aud` on /userinfo hits.
- 🟡 Missing `Cache-Control: no-store` and `Pragma: no-cache` on the response — OIDC Core §5.3.4 recommends both.
- 🟡 GET only. OIDC Core §5.3.1 requires both GET and POST. Trivial to add.
- 🟢 401 with `USER_NOT_FOUND` for a deactivated user — strictly should be `invalid_token`.
- **Recommendation:** Request Changes — `WWW-Authenticate` + POST support before shipping.

**`7659359` — fix(oidc): stop advertising end_session_endpoint** — by Raphael Londner

- 🟢 Correct removal + regression test. `assertPostLogoutRedirectUriAllowed` and the `post_logout` redirect kind are pre-wired for the eventual endpoint; comment in `oauth-metadata.ts` flags the coupling well. **Approve.**

### Ops / config

**`a259450` — feat(config): rate limits configurable in .env** — by Raphael Londner

- 🔴 **Env-configurable buckets are silently overridden.** `@Throttle({ auth: { limit: 10, ttl: 60_000 } })` on `oauthAuthorize` (`token.controller.ts`) hard-codes values that shadow the `AUTH_RATE_LIMIT` module config. Result: operators set `AUTH_RATE_LIMIT` and see no effect on /authorize. Fix: `@Throttle({ auth: {} })` (empty override, uses the module bucket) or drop the per-route decorator and rely on the named bucket. Audit `direct-login` and any other route decorated the same way.
- 🟡 Per-IP keying via default `ThrottlerGuard` tracker — behind Render's proxy, ensure `trust proxy` / `X-Forwarded-For` handling is correct or all traffic will bucket to the proxy IP.
- 🟡 No shared store — in a multi-replica prod deploy, effective limit is `N × configured`. The `.env` comment acknowledges this; call it out in the runbook.
- 🟢 `envInt` coerces `0` → fallback, so operators can't set 0 to disable. Consider `-1` for "off".
- **Recommendation:** Request Changes — the shadowing bug guts the feature.
