### W1 — `setUserRolesAction` / `setUserDirectPermissionsAction` re-introduce string-matching error mapping

**Files:** `apps/admin/app/(admin)/users/actions.ts` (commit `1b45c19`)
**Severity:** Warning — same anti-pattern that **bug-0032** (`fix/bug-0032-error-mapping-brittle`) is supposed to eliminate.

```ts
const message = err instanceof Error ? err.message : ''
if (message.includes('403')) return { errorKey: 'users.errors.forbidden' }
if (message.includes('400')) return { errorKey: 'users.errors.rolesSetFailed' }
return { errorKey: 'users.errors.rolesSetFailed' }
```

Problems:

- A `403` substring will match `users.errors.40300` or any future log fragment. Brittle.
- `404` from `resolveRoleIdsForApp` ("Role(s) not found: …") collapses to a generic 400-bucket error. The user sees `rolesSetFailed` for both a stale role id and an empty cart.
- 5xx errors fall through to `rolesSetFailed`, so server-side failures look like input failures.

**Recommendation:** Block on (or co-merge with) `fix/bug-0032`. Replace `apiFetch` so it throws a typed `ApiError { status, code, message }`, then key off `err.status`.

### W2 — `getUserDirectPermissions` returns `appId: ''` (lossy)

**Files:** `apps/auth-server/src/users/users.service.ts` (commit `59ea2e2`), lines 360–390.

```ts
return (...).directPermissions.map((up) => ({
  id: up.permission.publicId,
  name: up.permission.name,
  appId: '',  // ← intentional, but lossy
}))
```

The comment notes this matches the `/effective-permissions` shape, but in `effective-permissions` the omission is acceptable because all rows share the *queried* app. Here, a direct-permission can theoretically be cross-app via legacy data, and the admin UI uses `appId` for filtering. Either:

- Include the real `appId` publicId (one extra `saApp.findUnique` or a join select), or
- Make the Permission row type explicitly carry an `appId | null` to flag the lossy case.

Right now the UI shows direct permissions with no app attribution; if you ever surface multi-app users this becomes a correctness bug.

### W3 — `setUserRoles` / `setUserDirectPermissions`: org → app derivation is racy under app reassignment

**Files:** `apps/auth-server/src/users/users.service.ts`, lines 322–358 (`setUserRoles`) and 392–435 (`setUserDirectPermissions`).

```ts
const user = await prisma.saUser.findUnique({ where: { publicId: userPublicId } });
// ... self-edit check, permission check ...
const org = await prisma.saOrg.findUnique({ where: { id: user.orgId } });
const numericIds = await resolveRoleIdsForApp(org.appId, roleIds);

await prisma.$transaction(async (tx) => {
  await tx.saUserRole.deleteMany({ where: { userId: user.id } });
  if (numericIds.length > 0) {
    await tx.saUserRole.createMany({ ... });
  }
});
```

The org → app lookup and the `resolveRoleIdsForApp` validation both happen **outside** the transaction. If a concurrent operation moves the user to a different org (or reassigns the org to a different app) between read and transaction-commit, the just-inserted role rows can end up scoped to a different app than the user's current org. Likelihood is low in practice, but enterprise multi-tenancy promises stronger guarantees.

**Recommendation:** Move the `saOrg.findUnique` + `resolveRoleIdsForApp` inside the same `$transaction` callback, or take a row-level lock on the user row via `saUser.findUnique({ where: { id: user.id } })` *inside* the transaction.

### W4 — `setUserRoles` / `setUserDirectPermissions`: delete-then-insert pattern is non-idempotent under partial failure

**File:** same as W3.

`deleteMany` then `createMany` inside `$transaction(async tx => ...)` is atomic in Postgres (good). But there's no `RepeatableRead` isolation set, so under default `READ COMMITTED` two concurrent set-replace calls for the same user can interleave:

```
T1: deleteMany → createMany(A,B)
T2:                                 deleteMany → createMany(C,D)
```

Final state is the last writer's set, which is the intended last-write-wins semantic — but each transaction may have run permission checks against a stale baseline. Acceptable for now; document the lack of optimistic concurrency. If you want stricter semantics, accept an `etag` / `version` on the user row and bump it inside the transaction.

### W6 — `af9f4ca` ships scrypt swap but doesn't migrate existing bcrypt hashes

**File:** `apps/auth-server/src/invitations/invitations.service.ts`.

```ts
- import * as bcrypt from 'bcryptjs';
+ import { hashPassword } from 'better-auth/crypto';
...
- const hashed = await bcrypt.hash(password, 10);
+ const hashed = await hashPassword(password);
```

This fixes the 500 on `/api/auth/sign-in/email` for **newly** accepted invitations. **Existing** account rows that were previously created with bcrypt are still in the DB with bcrypt hashes and will continue to 500 on sign-in. The fix is correct going forward; you need a one-time migration / forced-password-reset for any user who accepted an invite before this commit.

**Recommendation:** Add a one-off script (or migration) that flags `account` rows whose `password` column is in bcrypt format (`$2[ayb]$...`) and either (a) sends them a password-reset email, or (b) invalidates the account and re-issues an invitation. Document the cutover in `CHANGELOG.md`.

### W7 — Admin sidebar: `usePathname()` initial-render flicker

**File:** `apps/admin/components/sidebar-shell.tsx` (commit `a401cfd`).

```ts
const currentPath = usePathname() ?? ''
```

The previous server-side `x-pathname` header indirection was ugly but did highlight the active item on the **first** server-rendered HTML. After the switch, the initial paint will render the sidebar with no active item for one render tick before `usePathname()` resolves. For Next.js App Router this is fine in practice (the client renders almost immediately), but if you have Lighthouse / CLS budgets in CI this might shift visible content briefly.

**Recommendation:** Acceptable trade-off. Mention in the implementation plan that the e2e check (`9ab79bf`) now also implicitly guards against the active item being unset post-hydration.
