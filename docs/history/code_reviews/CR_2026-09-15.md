### `0002a11` — `dev(sec): added certificates to run API with https` (Raphael Londner)
Files: `.gitignore` (+2), `apps/auth-server/src/main.ts` (+12).

Introduces synchronous mkcert-based HTTPS for the auth-server in dev by reading `secrets/localhost{-key,}.pem` at boot when `NODE_ENV !== 'production'`.

- 🟡 **Correctness — env-gate is too wide.** `NODE_ENV !== 'production'` also matches `'test'`. E2E and unit test suites that spin up the auth-server (`test:e2e` script) will now `fs.readFileSync` cert files at boot and throw `ENOENT` if certs aren't present on the CI runner or a fresh dev clone. Recommend narrowing to `process.env.NODE_ENV === 'development'` **or** wrapping the read in a try/catch with a graceful log-and-fall-back-to-http path.
- 🟡 **Correctness — no clear onboarding error.** If a fresh clone runs `pnpm dev` without generating certs first, the error is a raw Node ENOENT rather than a pointer to a `docs/mkcert.md` runbook. Suggest either a `if (!existsSync(...))` pre-check with a friendly message, or documenting cert generation in `DEPLOYMENT.md` / a new `docs/dev-https.md`.
- 🟢 **Security:** cert paths are correctly added to `.gitignore` — no risk of committing private keys. Path resolved via `path.join(__dirname, '..', 'secrets', ...)` avoids `cwd`-dependent surprises. Prod is unaffected (`isDev` gates the whole block).
- 🟢 **Architecture:** wiring via NestFactory's `httpsOptions` is the documented Nest pattern.
- 🟡 **Style:** the `if (isDev) {` line has non-standard indentation (extra spaces) — cosmetic, but shows this wasn't run through the project's formatter/lint. Consider a pre-commit hook if not already active.
- 🔴 **Testing:** no tests added; no coverage for "certs missing" or "certs present but invalid" branches. Given this affects every dev boot, a one-line existence check with a covered error message would pay for itself.

### `953e42d` — `fix(auth): keep unprefixed session cookie name in dev under https` (Raphael Londner)
Files: `apps/auth-server/src/auth/auth.config.ts` (+16 comment/config).

Pins `useSecureCookies: process.env.NODE_ENV === 'production'` so BetterAuth doesn't rename `better-auth.session_token` → `__Secure-better-auth.session_token` in dev now that dev runs on https.

- 🟢 **Correctness:** the root-cause diagnosis in the commit message is accurate — BetterAuth derives `useSecureCookies` from `BETTER_AUTH_URL`'s protocol, not from `defaultCookieAttributes.secure`. Pinning to the same condition as `secure` is the right fix.
- 🟢 **Security:** in production, `useSecureCookies` remains on. Dev-only relaxation is bounded to `NODE_ENV !== 'production'` and does not weaken prod behavior.
- 🔴 **Tech debt — genuine finding.** The commit message says admin "hardcodes `'better-auth.session_token'` in a dozen places (Set-Cookie parsing, cookie forwarding, middleware session checks)." **This is the real defect** — the fix here treats the symptom. If Better-Auth ever changes cookie naming conventions again (or if a customer deployment configures `cookiePrefix`), admin breaks silently. Recommend:
  - Extract the cookie name to a single `SESSION_COOKIE_NAME` constant in a shared package (e.g. `packages/auth-config`), derived from the auth-server's actual configured value.
  - File as a tech-debt / refactor bug (e.g. `bug-0290` or a `refactor-` entry) so it doesn't get lost.
- 🔴 **Testing:** no regression test. A single unit test asserting that in dev-https mode `auth-server` still sets `better-auth.session_token` (not the `__Secure-` variant) would prevent this exact regression from reappearing on any future Better-Auth upgrade.
- 🟡 **Interaction with PR #386:** #386 was an earlier attempt at the same problem, reverting auth-server dev URLs from https back to http. That PR is likely now obsolete — verify and close/rebase.
