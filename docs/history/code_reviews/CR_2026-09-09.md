### PR #378 — Activation Webhook + Pending-Account Signup — by rlondner
- **Branch:** `feat/activation-webhook` → `dev`
- **Files:** 21, **Additions:** +2475, **Deletions:** -12
- **Recommendation:** 🔴 **Request Changes** — several security & operational gaps must be closed before merge.

**Findings:**

🔴 **Critical**
- **Replay attacks on webhook payload.** `notify-activation.ts` signs only the JSON body. There is no `X-Sassy-Timestamp` header + nonce/event-id bound into the signature, so a captured delivery can be replayed indefinitely. Adopt the Stripe pattern (`t=…, v1=hmac(t.body)`) with a documented max-skew.
- **SSRF at delivery time.** `IsAppUrl` (see PR #383) now blocks IP *literals*, but `notify-activation.ts` still performs no request-time DNS resolution or private-range re-check. Any admin able to PATCH `webhookUrl` can point at a hostname that resolves internally (DNS rebinding, private A records). Resolve DNS at delivery, reject RFC 1918 / link-local / metadata / ULA, and pin the resolved IP for the HTTPS request.
- **Unbounded response body.** `postOnce` awaits `fetch(...)` but never caps or drains the body — a hostile receiver can stream unbounded data. Cancel/close the body after reading `status` and enforce a max size.

🟡 **Warning**
- **`webhookSecret` stored in plaintext** on `SaApp` (migration `20260908124015_add_saapp_webhook_fields`). At-rest DB compromise leaks all tenants' signing keys. Wrap with a KMS/env-key envelope, or at minimum document in the threat model.
- **Weak secret floor** — `@MinLength(16)` in `update-app.dto.ts` allows low-entropy strings. Require ≥ 32 bytes or generate server-side (rotate-only), matching the `clientSecret` UX.
- **Retry has no backoff/jitter** — two back-to-back attempts hammer a struggling receiver. Add exponential delay + jitter, or move retries out-of-band.
- **`invitations.service.ts` awaits `notifyActivation` inline** after the DB transaction commits (~5 s timeout × 2 = up to 10 s added to the invite-accept HTTP response). Move to a background queue or explicit fire-and-forget.
- **Signup redirect-URI selection is silent** — `registration.service.ts` uses `orderBy: { id: 'asc' }` when multiple login callbacks exist. Signup code may be delivered to the wrong environment. Require an explicit `redirect_uri` or reject if >1 login URIs are registered.
- **Signup-AMR token for `unverified` users** — `token.controller.ts` allows a signup code to redeem for pending/unverified users. Ensure scope/claims strictly reflect `status: unverified` so relying parties cannot grant sensitive access; consider a shorter TTL for signup-AMR tokens.
- **`/userinfo` now returns `status` unconditionally** — appears outside the `openid`-scoped claims map. Verify `status` is gated on `openid` scope, otherwise per-user state leaks to any bearer token.
- **Test coverage gaps** in `notify-activation.spec.ts`: no explicit `AbortController` timeout test (fake timers), no real 3xx redirect assertion, no unicode-body signature-stability test.
- **RBAC** — no RBAC change is shown for `updateApp`. Confirm `platform.apps.manage` still gates `webhookUrl`/`webhookSecret` — a webhook is arguably more sensitive than renaming an app (data-exfiltration channel).

🟢 **Note**
- `apps.service.ts` in the diff is unreadable (binary). Regenerate the diff (`--text`) before merge review.
- `notify-activation.ts` uses `crypto.randomBytes(9).toString('base64url')` (72 bits) for audit-event `publicId` — inconsistent with sqids used elsewhere. Confirm intentional.
- `logOutcome` catch-all silently swallows errors; log a `warn` so ops notices repeated audit-log failures.
- `JSON.stringify(...)` body — pin HMAC encoding to `Buffer.from(body, 'utf8')` to guarantee byte-exact parity with what `fetch` sends when non-ASCII fields appear.
