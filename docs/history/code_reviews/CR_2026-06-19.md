### 🔴 `4e06f17` — `feat(auth-server): OAuth AS discovery doc + open orgs/perms reads to platform.users.manage`
**Two unrelated concerns in one commit. Strongly recommend splitting next time.**

**Part 1 — RFC 8414 discovery doc (low risk):**
- 🟢 Clean shared-constants pattern (`oauth-metadata.ts`) keeps `TokenController` route paths and `DiscoveryController` advertised endpoints in lockstep.
- 🟡 **Hard-coded issuer fallback:** `process.env.BETTER_AUTH_URL ?? 'https://auth.example.com'`. In a misconfigured prod, this will silently publish a wrong `issuer` claim that resource servers cache. Should `throw` on unset `BETTER_AUTH_URL` at boot, not at request time.
- 🟡 **No caching headers** on `/.well-known/oauth-authorization-server` — every RS-side discovery refresh hits the controller. Add `Cache-Control: public, max-age=3600` (or higher) per RFC 8414 best practice.
- 🟡 Metadata response does not include `revocation_endpoint`, `introspection_endpoint`, `scopes_supported`, `subject_types_supported`. If any of those exist, advertise them; if not, OK to omit (they're optional).

**Part 2 — Permission relaxation (medium risk, document the threat model):**
- `OrgsService.listOrgs`/`getOrg` and `PermissionsService.listPermissions`/`getPermission` now accept `platform.users.manage` in addition to the existing `platform.*.manage` gates.
- 🟡 **Permission concentration:** `platform.users.manage` is now sufficient to (a) enumerate all orgs across all apps, (b) read the full permissions catalog, and (c) per `2a1c972` below, bypass the system-perm escalation guard. That permission is now the single most powerful "shadow super-admin" capability. Make sure RBAC docs and audit trail reflect this.
- 🟡 **Org enumeration leak:** `listOrgs` returns names + counts cross-app. A holder of `platform.users.manage` for one app can see *all* orgs in the system. Confirm this matches the intended multi-tenancy boundary, especially if SassyAuth ever hosts mutually-distrusting tenants.
- 🟢 Mutation gates correctly untouched. Matrix + spec assertions updated alongside the runtime change — good test hygiene.

**Recommendation:** Add boot-time `BETTER_AUTH_URL` assertion; add cache headers on discovery; document `platform.users.manage` as a privileged tier in `code_reviews/` or the security spec.

### 🟢 `a4f6285` + `2a1c972` — Escalation guard (`assertCallerCanGrantSystemPerms`) and wire-in
- Strong design: load granted role/direct perms → filter `isSystem` → require caller holds each, with `platform.users.manage` bypass. Covers `createUser`, `assignRole`, `setUserRoles`, `setUserDirectPermissions`. Removal paths intentionally untouched.
- 🟡 **TOCTOU window:** the guard's read of role permissions and the actual assignment happen across separate transactions. A concurrent `setRolePermissions` adding a system perm to a target role between guard check and `tx.create` would slip a system perm through. Low practical likelihood; documenting the window in the guard's JSDoc is enough.
- 🟡 **Cost per call:** each guarded path triggers a deep `saUser` read (`roles → permissions → permission`, plus `directPermissions → permission`) twice in the worst case (once in the guard, once in the surrounding service). Consider hoisting caller-perm resolution into a request-scoped cache.
- 🟢 Spec coverage looks thorough — `+340` lines in `users.service.spec.ts`.

### 🟢 `b22f85f` — `checkPermissionForApp` helper
- Sibling to `checkPermission` for app-scoped (vs org-scoped) routes. Clean semantics: `platform.*` bypasses scope check; `org.*` requires `callerAppId === targetAppId`; `targetAppId: -1` sentinel forces platform-tier.
- 🟡 **Sentinel anti-pattern:** `targetAppId: -1` as a magic number. Replace with an explicit `requirePlatform: true` option or a discriminated union — sentinels invite caller bugs and silent type widening.
- 🟢 88-line spec — well-covered.
