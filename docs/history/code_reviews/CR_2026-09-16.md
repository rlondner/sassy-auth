### `3153f8b` fix(auth-server): stop BetterAuth's native length check rejecting per-app password overrides — Raphael Londner

**Scope:** `auth.config.ts`, `password-policy.ts`.

**Findings:**
- 🟢 Diagnosis is precise: BetterAuth's `minPasswordLength` is a single global option enforced natively regardless of which app's policy applies, so pinning it to the global default rejected any per-app override that legitimately relaxes the minimum. Introducing `MIN_PASSWORD_LENGTH_FLOOR = 8` as the belt-and-braces baseline is the right split of responsibilities: app-aware complexity/length is validated upstream by `validatePasswordOrThrow`, BetterAuth's native check is now just a hard absolute floor.
- 🟡 **`MIN_PASSWORD_LENGTH_FLOOR = 8` is a policy decision, not a technical constant.** Confirm this matches the platform's minimum acceptable floor (NIST SP 800-63B allows ≥8 with additional checks; some enterprise regimes require ≥10 or ≥12 absolute). Recommend documenting in `password-policy.ts` the *rationale* (e.g. "matches NIST 800-63B §5.1.1.2 minimum") and gating any future relaxation on a security review.
- 🟡 **Verification gap.** The commit doesn't add a test asserting `assertValidPasswordPolicyOverride` rejects `minLength < MIN_PASSWORD_LENGTH_FLOOR`. If that assertion already existed against a hardcoded `8` and the constant is now the source of truth, wire the test to import the constant so drift breaks the test. If it didn't exist, add one — this is the enforcement seam that prevents an admin from setting `minLength: 4` on an app.
- 🟢 Comment explaining the two-check architecture is thorough and will survive maintenance.

**Recommendation:** Approve as merged. Add: (1) explicit `MIN_PASSWORD_LENGTH_FLOOR` rationale doc-comment tying it to a standard, (2) assertion test importing the constant so the invariant is enforced in CI.
