## Follow-up work (found today, not filed as standalone bugs — lower confidence or larger scope than fits a single autonomous review pass)

- **`social.link.created`/`social.link.removed` still have no emitter**
  (bug-0268 only wired `social.signin.ok`). Detecting "this session-create
  was the first time this identity linked to this user" needs either a
  pre/post query around `Account` or hooking BetterAuth's own
  account-linking internals — the kind of deep source archaeology
  `classify-callback-outcome.ts`'s header comment already had to do for the
  rejection path. Worth a dedicated pass, not a bolt-on.
- **CORS middleware ordering on `/api/auth/*`**
  (`apps/auth-server/src/main.ts`, from commit `c641152`): `authCors` runs
  before `createDefaultAuthRateLimiter()` for all methods including
  OPTIONS, and `Access-Control-Allow-Headers` is reflected from the request
  (`req.headers['access-control-request-headers']`) rather than an explicit
  allowlist. Low risk as-is (preflights are cheap; the actual
  `Access-Control-Allow-Origin` matching is a correct exact-match
  allowlist, confirmed in today's security-regression pass) but worth
  tightening: move `authCors` after the rate limiter for non-OPTIONS
  methods, and replace the reflected header list with an explicit one.
- **`social-buttons.tsx` collapses all start-failures to `/oauth-error`
  with no `code=`** (from commit `c641152`). The rest of the flow
  classifies outcomes into specific codes
  (`social_email_unverified`, `social_signin_rejected`, ...); a raw
  network/non-OK response from the initial POST loses that classification
  and the resulting audit event has no distinct reason. Pass a
  `?code=social_start_failed` (or similar) so the error page and the audit
  trail both stay informative.
- **`countAccountsForEmail`'s string-escaped SQL**
  (e2e test helper, from commit `47caeae`): `escapedEmail.replace(/'/g,
  "''")` is a footgun for whoever parameterises the caller next, even
  though today's inputs are test constants. Swap for `psql -v` bindings.
- **PII allowlist inside `emitFederationEventToSentry`**
  (`apps/auth-server/src/social/telemetry-sentry-adapter.ts`): the "email/
  providerSub never reach telemetry" rule is currently enforced only at
  `record-federation-event.ts`'s call sites, not inside the adapter itself.
  No current caller violates it (verified in today's security-regression
  pass), but an allowlist inside the adapter (only pass `auth.*`/`app.*`
  keys through) would make a future violation impossible rather than just
  currently-absent.
- **`SaAuditEvent.type` has no enum/check constraint**
  (`packages/db/schema.prisma`): free-form `TEXT`, indexed and presumably
  queried by exact string match. A typo'd or renamed event-type string
  would silently fragment the audit trail rather than failing loudly.
  Low priority — recommend a Postgres `CHECK` constraint or Prisma enum
  once the full set of event-type strings stabilizes (today: 4 declared,
  2 actually emitted after bug-0268).
- **`.github/workflows/*.yml` both declare `branches: [main, master]`**
  when the repo's default (and only) branch is `master`. Harmless today;
  if `main` is ever created (e.g. a rename), both branches would fire
  duplicate runs on the same PR. Trim to `[master]` whenever someone is
  next in these files for another reason.
