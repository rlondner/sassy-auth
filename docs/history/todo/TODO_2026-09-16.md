## New follow-up: bound `activationEmailOverride.subject`/`.message` length

`assertValidActivationEmailOverride` (apps.service.ts) checks type and
rejects embedded newlines but places no upper bound on `subject` or
`message` length, unlike `passwordPolicyOverride`'s numeric fields (each
bounded 0–128) or the existing app-logo upload (`APP_LOGO_MAX_BYTES`).
Not filed as a bug this run — no concrete failure was reproduced (no mail
provider limit hit, no observed truncation) — but worth a small follow-up
bound (a few hundred/thousand chars is plenty for activation-email copy)
before this field sees real-world abuse from a compromised or careless
`platform.apps.manage` caller.

## New follow-up: escape interpolated `firstName` across all four email templates

bug-0291 (this run, PR #395) fixed HTML escaping for the one field with
cross-user impact (`activationEmailOverride.message`, admin-controlled,
seen by every user of that app). The same unescaped-interpolation pattern
exists for `firstName` in `verify-email.template.ts` and identically in
`invitation.template.ts`, `password-reset.template.ts`, and
`sign-in-code.template.ts` — each embeds the signing-up/invited user's own
name into their own email's HTML unescaped. That's self-XSS (no
cross-user impact, since the name and the recipient are the same person),
which is why it wasn't bundled into bug-0291's fix, but it's the same
underlying gap in `renderTemplate()`'s documented "caller must escape"
contract going unaddressed at every one of its call sites. Worth a single
follow-up pass across all four templates rather than four separate
one-line fixes.
