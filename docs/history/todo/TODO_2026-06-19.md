## Risky patterns observed

### Migration safety needs hardening
Three migration bugs (bug-0098, bug-0099, bug-0100) in a single migration file suggest the migration was developed against a clean database and not tested against a partially-migrated or production-like state. Migration testing should include:
1. Run against an empty database (fresh install)
2. Run against a fully-seeded database
3. Run after a partial application (interrupt at each step)
4. Run when non-platform apps have `org.*`-prefixed permissions

### Escalation guard coverage is incomplete
The new `assertCallerCanGrantSystemPerms` guard is applied to `assignRole` and `setUserRoles` but not to `removeRole`. The `checkPermissionForApp` helper has a silent bypass when `targetAppId` is undefined. The guard framework is well-designed but needs a systematic audit of all entry points that modify permission/role assignments.

### Admin UI permission gates are inconsistent across pages
- `/roles` page has `canRead`/`canWrite` checks via `allSettled` + `AccessDeniedPanel`
- `/users` page has no access check at all (bug-0058, still open)
- `/permissions` page has partial server-side gating but `PermissionsTable` has no `canWrite` prop
- The sidebar hides links based on permissions but there are no route-level guards

### Test infrastructure sharing pattern is fragile
The module-level singleton pattern in `factories.ts` (bug-0101) will cause failures as more scenario spec files are added. The shared `sharedApp` / `sharedHttpServer` pattern needs a reference-counting teardown or per-file isolation.

### ADMIN_URL fallback pattern
Both `createUser` and `resendInvitation` in `users.service.ts` fall back to `http://localhost:3001` when `ADMIN_URL` is not set. This is fine for development but means a production deployment without `ADMIN_URL` will send invitation emails with `localhost:3001` URLs. There is no startup assertion that `ADMIN_URL` is set. (Already noted in the review but not tracked as a separate bug since bug-0062 covers the seed-password variant of the same "no production guard" pattern.)

## Positive observations

### Test coverage is strong for the new features
The org-scoped admin feature shipped with comprehensive test coverage:
- Multi-tenant scenario tests (visibility isolation, grant-ceiling)
- Migration verification spec
- Unit tests for sidebar permission logic
- Matrix test rotation for the new permission split
- E2E tenant-admin spec

### Escalation guard design is sound
`assertCallerCanGrantSystemPerms` correctly checks both direct and role-derived permissions. The separation of `checkPermission` (general RBAC) and `checkPermissionForApp` (app-scoped) is a good architectural pattern. The issues found are coverage gaps, not design flaws.

### Flox environment is a significant DX improvement
Auto-provisioning Postgres, generating `.env.local` with RSA keys, and running migrations + seed on first activation eliminates the multi-step manual setup.
