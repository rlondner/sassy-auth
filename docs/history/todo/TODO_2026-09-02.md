## Follow-ups from today's OIDC review

- **RP-Initiated Logout is speced but not implemented.** The original
  design doc (`docs/superpowers/plans/2026-08-21-oidc-compatibility.md`)
  includes a full `GET /api/token/oauth/logout` controller task, and two
  of its three pieces shipped (`assertPostLogoutRedirectUriAllowed` in
  `redirect-uri.ts`, the `'post_logout'` `SaAppRedirectUri` kind) — but
  the controller itself never did, and the discovery doc was advertising
  the resulting `end_session_endpoint` anyway until today's bug-0277 fix
  (PR #370) removed it. If OIDC logout is still wanted, the remaining
  work is: a `TokenController` route at `OAUTH_LOGOUT_ROUTE` that
  validates `id_token_hint`/`post_logout_redirect_uri` against
  `assertPostLogoutRedirectUriAllowed`, revokes the BetterAuth session,
  and redirects; then re-add `end_session_endpoint` to the discovery doc
  in the same change. Until then, leave it removed rather than
  re-advertising a 404.
- **Nonce validation is (correctly) the relying party's job, but it's
  undocumented.** This server carries `nonce` through the whole flow
  (query param → `SaOauthCode` → `id_token`) but doesn't validate it
  itself, which is correct per the OIDC Core spec. Nothing in the new
  README OIDC section says the RP must compare the returned `nonce`
  against the one it generated. Worth a one-line callout next time
  someone's in that section — a consumer skipping this check reopens the
  replay-protection nonce exists for.
- **Two similarly-named rate-limit knobs, two different "0" behaviors.**
  `REGISTER_RATE_LIMIT=0` means "unlimited" (pre-existing, unrelated
  guard in `rate-limit.guard.ts`); the new `DEFAULT_RATE_LIMIT`/
  `AUTH_RATE_LIMIT` treat `0` (and negative, and non-numeric) as
  "invalid, use the built-in default" — i.e. still rate-limited. Both are
  reasonable choices for what each guards (self-service registration vs.
  the global NestJS throttler covering login/authorize), and both fail in
  a safe direction, but an operator skimming `.env.example` could
  reasonably expect `0` to mean the same thing in both places. A short
  cross-reference comment in `.env.example` (already partially in place —
  the throttler section documents its own `0` behavior, just not that it
  differs from `REGISTER_RATE_LIMIT`'s) would close the gap. Not filed as
  a bug since neither behavior is wrong on its own.
- **`redirectUris` is now a real, queryable per-app registration set** —
  worth checking whether the admin console's app-management UI has any
  way to add/remove `SaAppRedirectUri` rows yet, or whether it's
  currently DB-only. Not checked in this run (out of scope: no admin-app
  commits landed in this window), but the OAuth-hardening value of
  registered-set matching (`da5498e`) is limited until there's a UI path
  to actually register non-default URIs.
