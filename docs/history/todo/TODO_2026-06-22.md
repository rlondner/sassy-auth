## Positive observations

### Toast integration is consistent and well-structured
The `onSuccess` callback pattern is applied uniformly across all 5 entity types and their create/edit/delete paths. Each table implements a `refresh` callback (either via server action re-fetch or `router.refresh()`) that is threaded through to the drawer's `onSuccess` prop. The pattern:
1. Server action succeeds → show success toast → call `onSuccess()` → close drawer
2. Server action fails → show inline error in drawer → keep drawer open

This is a clean, predictable UX pattern. The Toaster component correctly forwards `next-themes`' resolved theme to Sonner, so toasts respect the user's light/dark mode preference.

### E2E page object fix is well-targeted
The `raceSuccessOrError` scoping fix correctly identifies the root cause (Next.js Dev Tools phantom alert element) and applies a precise selector that only matches real error indicators. The OAuth route mock narrowing is also well-reasoned — the comment explains the exact failure mode.

### Error handling in drawers uses early return
The refactored error handling pattern (`if ('errorKey' in result) { setErrorKey(...); return; }`) is cleaner than the previous ternary (`if (...) setError() else close()`). The explicit `return` prevents accidental fall-through to the success path.

## Risky patterns observed

### No error toasts for failed mutations
All drawers show `toast.success()` on success but rely on inline drawer error messages for failures. This is consistent but means:
- If the user closes the drawer before reading the error, the feedback is lost
- There is no global error feedback mechanism for mutations

Consider adding `toast.error()` calls as a complement (not replacement) to inline errors, at least for the most critical mutations.

### Refresh mechanism diverges across entity types
- **Apps, Orgs, Permissions, Roles:** Client-side re-fetch via server action (`listXxxAction(...)`)
- **Users:** `router.refresh()` triggers a full Server Component re-render

This divergence means the Users page gets a full re-render (including potential layout shifts) while the other pages do a seamless client-side data swap. The user experience is slightly different across entity types. This isn't a bug but makes the codebase harder to reason about.

### Test coverage gap
No unit tests or E2E tests have been added for the toast notification behavior. The i18n toast keys are tested implicitly by the E2E page objects (which now use `raceSuccessOrError(page, t('apps.toast.created'))` etc.), but there are no tests verifying:
- Toast appears after successful create/edit/delete
- Toast does NOT appear after failed mutations
- Toast theme matches the user's preference
