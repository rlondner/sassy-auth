## bug-0292 (medium, GDPR geo-detection) filed without an accompanying fix PR

for the full writeup. Unlike every other numbered bug in this catalog,
this run deliberately did not open a code-fix PR for it: the correct fix
(moving `trust proxy` from a hop-count to an explicit trusted-address
list) requires knowing production's actual proxy topology — Render's edge
IP ranges, whether the admin app and auth-server share a private network —
which isn't visible from the repository. A guessed fix risks landing a
`trust proxy` config that trusts an untrustworthy hop (spoofable IP,
silently *worse* than today's fail-closed "always require GDPR consent"
default) instead of a real fix. **Needs a human decision on the trusted-
address list before this is implemented in code.** The current mitigation
(leave `GEOIP_DB_PATH` unset) already ships in `DEPLOYMENT.md` — this item
is purely to make sure the underlying gap doesn't get lost if someone
sets that env var later without reading the history.

## Follow-ups from this run's review (not filed as bugs — no failure scenario, just gaps)

- **`apps/admin-e2e/tests/two-factor.spec.ptes`** (from PR #428): the
  per-app `twoFactorPromptEnabled: false` override has unit-level coverage
  (`resolve-trust-days.spec.ts`, `actions.signin.test.ts`) but its e2e
  test is `.skip`'d pending a seeded `PROMPT_DISABLED_APP_CLIENT_ID` fixture
  app in the e2e database. No end-to-end path currently exercises the
  per-app override actually suppressing the prompt in a live login flow.
  Worth unskipping once the e2e seed data exists.
- **`apps/auth-server/src/auth/auth.config.ts`** social-sign-in consent
  gate reads `client_id` off the post-login redirect URL's query string
  (`new URL(currentLocation).searchParams.get('client_id')`) to know which
  app's consent requirements apply. Confirmed correct for the current
  social providers wired up; worth re-checking this assumption holds for
  the redirect shape of any new social provider added later.
- **`2eacef1` (`chore(types): rebuild dist to include consent document type exports`)** commits regenerated `packages/types/dist/{index.d.ts,index.js}` directly. Checked-in `dist/` for workspace packages makes the source of truth ambiguous — a future edit to `packages/types/src` that forgets to rerun the build ships a stale runtime, silently, since nothing currently verifies `dist` matches `src`. The three CI workflows already build `@sassy-auth/db`/`@sassy-auth/types`/`@sassy-auth/telemetry` from source (see `cf68542` above), so the committed `dist/` is really only load-bearing for local dev consumers. Consider either gitignoring `packages/*/dist` and relying on that existing CI build step, or adding a pre-commit/CI check that fails when `dist` is stale relative to `src`. Also, three separate CI workflows (`e2e.yml`, `typecheck.yml`, `unit-tests.yml`) now each hand-list the same `--filter @sassy-auth/db --filter @sassy-auth/types --filter @sassy-auth/telemetry` — worth extracting into a composite action or a glob (`pnpm -r --filter "./packages/*" build`) before a fourth shared package makes it four places to keep in sync.
- **`process.env.ADMIN_URL ?? 'http://localhost:3001'`** is duplicated
  across several auth-server call sites (flagged inline by the PR #425
  author as low-priority cleanup, not addressed in that PR). Candidate for
  a small follow-up extracting a single shared constant/config accessor.
