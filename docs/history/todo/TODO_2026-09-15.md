## Follow-up: extract a shared session-cookie-name constant

`953e42d`'s fix (pinning `useSecureCookies`) treats the symptom; the
underlying fragility is that `apps/admin` hardcodes the literal string
`'better-auth.session_token'` in ~10 files (`app/login/actions.ts`,
`app/login/page.tsx`, `app/account/security/actions.ts`,
`app/(admin)/actions.ts`, `lib/api.ts`, and their tests) instead of
sharing `BETTER_AUTH_SESSION_COOKIE` from
`apps/auth-server/src/common/constants.ts`. Not filed as a bug this run
because it isn't a currently-reproducible failure — the strings still
match on `dev` today — but the next time BetterAuth's cookie-naming
behavior changes (a version bump, or a deployment that sets
`cookiePrefix`), this breaks silently again the exact same way. Worth a
small follow-up: move the constant to a package both apps already share
(e.g. `packages/types` or a new `packages/auth-config`), or have admin
import it directly from the auth-server workspace package.

## Follow-up: confirm `apps/admin` and `apps/auth-server` mkcert certs share a CA

`apps/admin` serves dev over `next dev --experimental-https` (Next's own
self-generated, self-signed certificate); `apps/auth-server` now serves
dev over a certificate generated manually with `mkcert` (see today's
README addition). These are two different certificate-issuance
mechanisms. If they don't share a trusted local CA, a developer running
both dev servers could see TLS warnings crossing between
`localhost:3001` and `localhost:3010` despite both being individually
"trusted." Not verified this run — this environment has no dev servers
running and no certs generated to inspect. Whoever next runs both
servers locally should check `openssl x509 -in <cert> -noout -issuer`
for both and confirm they match (or note that it doesn't matter because
they're never compared by the browser in the same security context).
