## Fix before `custom-scheme-redirect-uris` is opened as a PR

Local branch `worktree-custom-scheme-redirect-uris` (not pushed, no PR
yet; lives in `.claude/worktrees/custom-scheme-redirect-uris`) adds
mandatory PKCE for custom-scheme (`com.example.app://...`) redirect
URIs. In `apps/auth-server/src/token/token.controller.ts`'s
`oauthAuthorize`, the new `pkceRequired` check
(`!isConfidential || isCustomSchemeRedirect(redirectUri)`) runs
**before** `assertRedirectUriAllowed(redirectUri, app)` validates that
`redirectUri` is one of the app's registered URIs — so
`isCustomSchemeRedirect` is evaluated on the raw, attacker-controlled
query param, not a confirmed-registered one.

This doesn't look exploitable as a PKCE bypass: `assertRedirectUriAllowed`
still runs right after and rejects any URI that isn't actually
registered to the app, so a confidential app that has only
http(s) redirect URIs registered can't be tricked into skipping PKCE
by sending an unregistered custom-scheme `redirect_uri` (fails closed,
400). But it's the wrong order on principle — "is PKCE required"
should be decided from the URI *after* it's confirmed to belong to the
app, not from unvalidated user input — and it means a legitimate
custom-scheme app gets a generic `invalid_request` instead of the
proper `invalid redirect_uri` error when the client sends a redirect
URI that doesn't match any registered one. Move the
`assertRedirectUriAllowed` call (or at least capture its result) ahead
of the `pkceRequired` computation. The same pattern should be checked
in `registration.service.ts`'s social-signup code-issuance path, which
has an equivalent `pkceRequired` check.

No test currently exercises "confidential app, unregistered
custom-scheme-shaped `redirect_uri`, no PKCE" — worth adding alongside
the fix.
