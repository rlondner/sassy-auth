# Signup redirect: PKCE support for public clients + state/nonce passthrough — design

**Date:** 2026-09-23
**Status:** approved design, no implementation plan yet
**Scope:** (a) let the immediate-signup-redirect feature (from
`2026-09-08-activation-webhook-design.md`) work for public (PKCE) OAuth
clients, not just confidential ones; (b) carry `state` and `nonce` from the
original `/authorize` request through to the signup-flow redirect for both
client types. Honoring a requested `scope` (e.g. `offline_access`) from the
signup-time redirect is explicitly out of scope.

---

## 1. Problem and stance

`RegistrationService.register()` (`registration.service.ts:148-180`) already
mints a signup-flow OAuth code and redirects the freshly-registered (still
`pending`/`unverified`) user straight into the relying-party app, skipping the
"check your email" wait — but only when `app.clientSecretHash` is set. The
code comment explains why: the code is minted with no PKCE challenge (there
was no `/authorize` request for this registration to negotiate one against),
and `/api/token` rightly refuses a challenge-less code from a public client,
since PKCE is that client type's only defense against code interception.

In practice, most browser-based SaApps (SPAs) are public clients using PKCE —
confirmed against a real app (`vibecast`, public, no client secret) — so
today's implementation only benefits the minority of confidential-client
integrations. Meanwhile the admin `/signup` page already receives a `next`
query param carrying the *original* `/authorize` URL the user was on before
being bounced to sign up, which includes the app's own `code_challenge`,
`code_challenge_method`, `state`, and `nonce`. That challenge was generated by
the relying party itself and travels with a `code_verifier` it still holds —
exactly the same trust relationship PKCE already relies on at `/authorize`
today. There's no new trust extended by reusing it here.

Separately: today's confidential-client redirect sets `code` on the redirect
URL but never `state`, and mints the code with `nonce: null` regardless of
what the original request asked for. Any conformant OAuth/OIDC client library
validates `state` against what it sent and (when `openid` scope was
requested) validates `nonce` inside the returned ID token — so the existing
confidential-client redirect likely fails client-side validation today. This
was not caught because the only local test app is public. Fixing this touches
the same few lines, so it's included here rather than filed separately.

This design:

- Lets `RegistrationService.register()` parse the `next` URL (when the admin
  passes one through) to recover the original `redirect_uri`,
  `code_challenge`, `code_challenge_method`, `state`, and `nonce`.
- Validates those fields exactly the way `/authorize` already does —
  reusing `assertRedirectUriAllowed` and the `OAUTH_AUTHORIZE_PATH` /
  `resolveIssuer` constants — rather than introducing parallel validation
  logic.
- Mints the signup-flow code bound to that challenge for public clients
  (making the feature work for them for the first time), and passes
  `state`/`nonce` through for both client types (fixing the existing gap).
- Never fails registration itself over a malformed, mismatched, or absent
  `next` — every validation failure degrades silently to today's fallback
  (challenge-less code for confidential apps with a registered login
  redirect URI, or "check your email" otherwise).

## 2. Data flow

`apps/admin/app/signup/page.tsx` already resolves `next` and passes it to
`SignupForm`. Threading it further:

```
SignupForm (has `next` prop)
  → registerAction({ ..., next })          // apps/admin/app/signup/actions.ts
  → POST /api/register body: { ..., next }
  → RegisterDto.next?: string              // apps/auth-server/src/registration/register.dto.ts
  → RegistrationService.register(dto)      // parses + validates dto.next
```

No new admin-side redirect logic is needed — `SignupForm` already does
`window.location.href = result.redirectUrl` when present (added for the
confidential-only version of this feature); it doesn't care why a
`redirectUrl` did or didn't come back.

## 3. Backend validation and code minting

Inside `RegistrationService.register()`, replace the current
`if (app.clientSecretHash) { ... }` block with logic that first tries to
recover a validated `{ redirectUri, codeChallenge, codeChallengeMethod,
state, nonce }` from `dto.next`, then decides whether a redirect is possible:

1. **Parse `next`.** `new URL(dto.next)`; on throw, treat as absent.
2. **Confirm it's really an `/authorize` URL for this app.** Its path must
   equal `OAUTH_AUTHORIZE_PATH` (matching `resolveIssuer()`'s origin is not
   required — the admin app and auth-server may differ only by port in dev),
   and its `client_id` query param must equal `app.publicId`. Mismatch →
   treat as absent.
3. **Validate `redirect_uri`.** Extract it from `next`'s query string and run
   it through `assertRedirectUriAllowed(redirectUri, app)` (imported from
   `../token/redirect-uri`), catching its `BadRequestException` and treating
   a rejection as "no `next`" rather than propagating the error.
4. **Resolve the challenge.**
   - Public client (`!app.clientSecretHash`): both `code_challenge` and
     `code_challenge_method === 'S256'` are required. If either is missing,
     no redirect is possible for this app — fall through to the "no
     redirectUrl" outcome (registration still succeeds).
   - Confidential client: `code_challenge`/`code_challenge_method` are used
     if present and valid (`S256`), else `null`/`null` (today's behavior).
5. **Resolve `redirect_uri` to use for the code.** The validated one from
   `next`, replacing today's "oldest registered login URI" lookup. This also
   fixes apps with more than one registered login redirect URI (e.g. web +
   mobile deep link) being sent to the wrong one.
6. **If no valid `next` was recoverable at all** (steps 1-2 failed): fall
   back exactly to today's behavior — confidential + has a registered login
   redirect URI → challenge-less code against the oldest one; everything else
   → no `redirectUrl`.
7. **Mint the code** via the existing `OauthService.generateCode`, passing
   the resolved challenge/method, and now also the extracted `state` and
   `nonce` (previously hardcoded `null` for nonce, and state was never part
   of this call's inputs at all — `generateCode` already accepts `nonce` as
   its 7th parameter).
8. **Build the redirect URL** with `code` and, when present, `state` — fixing
   today's confidential-client gap where `state` was silently dropped.

`scope` is **not** read from `next`. The signup-flow code keeps the existing
fixed `'openid profile email'` regardless of what `next` requested — in
particular, `offline_access` (which would grant a refresh token to a
not-yet-verified user) is never granted this way, even for apps that have
`allowOfflineAccess` set. This mirrors `/authorize`'s scope filtering intent
but pins the outcome rather than deriving it from an unauthenticated
`next` value.

## 4. Error handling

Every validation step above fails *closed but silent*: a bad, tampered, or
absent `next` never throws out of `register()` and never affects the rest of
registration (org/user creation, verification email). Worst case, the user
lands on `/signup/check-email` exactly as they do today. This matches the
existing posture of the `app.clientSecretHash` check it's replacing.

## 5. Testing

Extend `registration.service.spec.ts`:

- Public app + valid `next` with `code_challenge`/`S256` → `redirectUrl`
  contains `code` and the `state` from `next`; the minted code (verified via
  `oauthService.generateCode` call args) carries the challenge and nonce.
- Public app + no `next` → no `redirectUrl` (unchanged from today).
- Public app + `next` present but missing `code_challenge` → no
  `redirectUrl`.
- Public app + `next` with a `redirect_uri` that isn't a registered login URI
  → no `redirectUrl`, registration still succeeds.
- Public app + `next` with a mismatched `client_id` → treated as absent,
  falls back to no `redirectUrl`.
- Confidential app + `next` with a challenge → challenge honored, `state`
  passed through (currently un-covered gap).
- Confidential app + no `next` → today's challenge-less-code behavior,
  unchanged, now also with no `state` param (since there's nothing to carry).
- App with two registered login redirect URIs + `next` naming the second one
  → code and redirect target both use the one from `next`, not the oldest.

Admin-side: extend `actions.test.ts`/`signup-form.test.tsx` (already touched
for the confidential-only version) only if `next` needs explicit assertion in
the request body — likely a one-line addition confirming `next` is forwarded
in `registerAction`'s fetch call, since `signup-form.tsx`'s redirect handling
itself needs no changes.

## 6. Out of scope

- Deriving `scope` (including `offline_access`) from `next` — see §3.
- Changing `/authorize`'s own behavior — it is only read from, never
  modified.
- Any change to how `next` is used elsewhere on `/signup` (the "back to
  login" link) or on `/login`.
