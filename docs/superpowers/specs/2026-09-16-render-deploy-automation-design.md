# Render deployment automation — design

## Problem

Deploying SassyAuth to Render currently requires two kinds of manual work beyond
`render.yaml` itself:

1. **Manual secret generation and entry.** RSA keypair, `BETTER_AUTH_SECRET`,
   `SEED_ADMIN_PASSWORD`, and `DATABASE_URL` (from Neon) must be generated by hand
   and typed into the Render dashboard when the Blueprint prompts for every
   `sync: false` variable (DEPLOYMENT.md §2–3.1).
2. **Manual post-deploy bootstrap.** The platform seed (`db:seed`) must be run from
   a Render Shell session by hand after every fresh deploy (DEPLOYMENT.md §3.4).

Goal: eliminate both, so a push to `master` results in a fully configured,
seeded deployment with zero dashboard clicks beyond the one-time setup of a
Render API key and a Neon API key as GitHub secrets.

## Scope

**In scope:**
- `sassy-auth-server` and `sassy-auth-admin` — the two services that make up the
  production deployment.
- Secret generation/storage, Neon database provisioning, Render env var sync,
  and post-deploy seed automation.

**Out of scope:**
- `sassy-resource-server` (the FastAPI sample app). It's a developer-facing demo
  bundled in the public repo, not part of production. It stays in `render.yaml`
  for anyone who wants to deploy it manually, but the automated pipeline does
  not touch it, and `SASSY_CLIENT_ID` automation is dropped entirely.
- DNS record creation. Render still shows CNAME targets for custom domains;
  pointing DNS at them remains a manual (one-time, rarely-repeated) step.
- Replacing `render.yaml` or Render's Blueprint sync. Service topology,
  build/start commands, and domains remain declared there; Render's native
  GitHub integration keeps applying it on push, unchanged.

## Architecture

A new `tools/deploy-render/` TypeScript package with a single entrypoint script,
run via `tsx`, invoked by a new GitHub Actions workflow
(`.github/workflows/deploy-render.yml`) on push to `master`. The script has four
staged, idempotent functions run in order on every invocation:

### 1. `ensureSecrets()`

Checks the GitHub `production` Environment for `RSA_PRIVATE_KEY`,
`RSA_PUBLIC_KEY`, `BETTER_AUTH_SECRET`, and `SEED_ADMIN_PASSWORD` (via the
GitHub REST API). Generates any that are missing, using the same logic already
documented in DEPLOYMENT.md §2 (Node's `crypto` for the RSA pair and the
BetterAuth secret; a random strong password generator for the seed admin
password). Writes new values back as GitHub secrets (libsodium-sealed, per
GitHub's secrets API).

Because GitHub secrets are write-only after creation, the **first time** a
value is generated, the script prints it once to the GitHub Actions job
summary (not the step log) with a clear "save this now, it cannot be retrieved
again" banner. On all subsequent runs, the secret already exists and this step
is a no-op read-check.

### 2. `ensureNeonDatabase()`

Calls the Neon API to find-or-create the project and database (by a fixed,
configured name), and fetches the pooled connection string
(`?sslmode=require` form). If `DATABASE_URL` isn't already stored as a GitHub
secret, stores it. If it is, leaves it untouched (rotating the DB is a
deliberate, separate action, not something a routine deploy should do).

### 3. `syncRenderEnvVars()`

Reads the current values of every variable listed in `render.yaml`'s
`sassy-auth-production` env var group plus the per-service `sync: false`
entries for `sassy-auth-server` and `sassy-auth-admin`, and pushes them via
Render's REST API (`PATCH /v1/services/{serviceId}/env-vars`). This replaces
the Blueprint's interactive "Render prompts for every sync: false variable"
step entirely — by the time Render's own Blueprint sync builds the service,
the env vars are already correct.

### 4. `triggerSeedJob()`

Polls `GET /v1/services/{id}/deploys` until the latest deploy for
`sassy-auth-server` reaches `live`, then starts a Render one-off Job
(`POST /v1/services/{id}/jobs`) running `pnpm --filter @sassy-auth/db db:seed`.
Polls the job to completion and surfaces its logs in the Action's output.
`db:seed` is already idempotent (documented behavior), so re-running it on
every deploy is safe and just confirms the platform admin/org/permissions
still exist.

## Data flow

```
push to master
   → GH Actions workflow starts
   → ensureSecrets()        → GitHub Environment secrets (production)
   → ensureNeonDatabase()   → Neon API → DATABASE_URL secret
   → syncRenderEnvVars()    → Render API → env vars on sassy-auth-server + sassy-auth-admin
   → (Render's own Blueprint sync fires on the same push, independently, and deploys)
   → poll deploy status     → Render API
   → triggerSeedJob()       → Render API job → runs db:seed → logs result
```

Two independent triggers land on the same push: Render's native GitHub
integration (already auto-applying `render.yaml`) and this workflow. The
workflow doesn't cause the deploy — it ensures env vars are correct *before*
Render's build uses them, then finishes the loop afterward with the seed.

**Ordering risk:** if Render's Blueprint sync deploys before the workflow
finishes updating env vars, that first deploy could run with stale/missing
secrets. Mitigation: `syncRenderEnvVars()` runs as early as possible in the
workflow, and Render automatically restarts a service whenever its env vars
change — so a lost race self-corrects with one extra restart rather than
failing outright.

## Error handling

- **Missing prerequisite secrets** (`RENDER_API_KEY`, `NEON_API_KEY`, a GitHub
  token scoped to write Environment secrets): the script fails fast with a
  clear message at startup. These three are the only values a human ever sets
  by hand, once, in GitHub's UI.
- **Render/Neon API errors:** transient failures (rate limits, 5xx) retry with
  bounded backoff; anything else surfaces the raw API error and exits
  non-zero so the Action goes red rather than silently doing nothing.
- **Seed job failure:** exits non-zero with the job's logs printed inline. No
  automatic retry — a failed seed likely indicates a real schema/data problem
  that deserves a human look, not a flaky call worth masking.
- **Partial secret generation:** after writing a newly generated secret to
  GitHub, the script reads it back to confirm the write is durable before
  proceeding to touch Render. If the write didn't stick, it aborts before any
  Render API calls, so Render is never configured with a secret that only
  exists in memory.

## Testing

- **Dry-run mode** (`--dry-run`): runs all four stages against the real
  Neon/Render/GitHub *read* APIs but logs intended writes instead of
  performing them, so the pipeline can be validated against real account
  state without side effects.
- **Local execution:** since this is one script, it can be run from a
  developer machine with the same environment variables the Action uses —
  needed for the very first bootstrap (before the workflow file exists) and
  useful for debugging a failed run.
- **Unit tests:** thin wrapper functions around each external API call, so a
  small Vitest suite can mock them and cover the idempotency branches
  (skip-if-exists logic) and the deploy/job polling logic without hitting real
  APIs.

## One-time manual setup (irreducible)

- Create a Render API key, store as the `RENDER_API_KEY` GitHub secret.
- Create a Neon API key, store as the `NEON_API_KEY` GitHub secret.
- Create a GitHub PAT (or use `GITHUB_TOKEN` with the right permissions) able
  to write Environment secrets, if the default workflow token can't.
- The very first time this repo is connected to Render as a Blueprint (`New →
  Blueprint`) — Render doesn't currently expose a public API to create that
  initial connection; it's a one-time action, not a per-deploy one.
- Point DNS at the CNAME targets Render shows for each custom domain, once.
