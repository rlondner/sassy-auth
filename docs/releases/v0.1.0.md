# SassyAuth v0.1.0

Draft release notes for the first public release. Not yet tagged or published —
the repository is still private, and the decision to publish is a manual one.

---

A multitenant authentication and authorization server with an admin console.
Resource servers delegate login, session and token concerns to SassyAuth and
verify the resulting RS256 JWTs independently.

## ⚠️ Experimental

Not security-audited, and not recommended for production without your own
review. There is no stability guarantee between commits, and no upgrade path is
promised yet.

SassyAuth handles authentication, sessions and token issuance — the parts of a
system where defects have the widest blast radius. Please read
[Known Limitations](../../README.md#known-limitations) before evaluating it. That
section is deliberately kept current and lists the gaps we already know about,
with the reasoning for each.

## What's here

- **OAuth2 Authorization Code with PKCE (S256)**, plus direct login and an
  invite/accept flow
- **RS256 JWTs** with a published JWKS endpoint and RFC 8414 authorization
  server metadata
- **Two-factor authentication** — TOTP enrolment and challenge, backup codes,
  per-app device-trust intervals, and optional per-app enforcement
- **Email OTP sign-in** and password reset
- **Multitenancy** with organisation-scoped RBAC
- **Admin console** (Next.js) for apps, orgs, users, roles and permissions, in
  English and French
- **A sample FastAPI resource server** showing token verification, audience
  validation and scope checks end to end

## Verification

123 end-to-end tests covering the auth flows, the admin console, the permission
matrix and the resource-server round-trip, alongside 114 unit and integration
spec files. Both the e2e and typecheck workflows are green.

The e2e suite runs against a freshly seeded database on every run, which is how
several defects in this release were found — including a seed that could not
complete on a clean database at all.

## Known limitations

Seven documented gaps, including:

- Rate limiting uses an in-process store, so it is per-replica rather than
  cluster-wide
- The JWT `scope` claim lists every permission the user holds, not only those
  belonging to the audience app
- `%` and `_` are not escaped in `LIKE` search queries
- `deleteUser` leaves the underlying BetterAuth identity in place

The full list, with reasoning and bug numbers, is in the
[README](../../README.md#known-limitations).

## Getting started

`flox activate` provisions Node, pnpm and PostgreSQL, generates `.env.local`
with an RSA key pair, migrates and seeds. Otherwise bring your own PostgreSQL —
see [Getting Started](../../README.md#getting-started).

The seed's default password only applies when `NODE_ENV` is `development` or
`test`; seeding anything else requires `SEED_ADMIN_PASSWORD`.
