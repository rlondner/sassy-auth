## Risky patterns / missing tests called out

### 1. 2FA rate limiting is per-process, not global
`auth.config.ts` sets explicit `customRules` for `/two-factor/verify-totp` and
`/verify-backup-code` (window 10s / max 3) and the comment correctly notes that BetterAuth's
default rate-limit storage is **in-memory** — so the cap is per-replica, not cluster-wide. A
multi-replica deployment multiplies the effective attempt budget by the replica count. Wire
`secondaryStorage` (Redis) before scaling horizontally, or the 2FA brute-force cap is softer
than it reads.

### 2. Direct-login TOTP throttle ≠ interactive-endpoint parity
`token.controller.ts` protects `direct/login` with `@Throttle({ auth: { limit: 10, ttl:
60_000 } })` (10/min/IP), while the interactive BetterAuth endpoints are capped at 3 per 10s.
`verifyUserTotp` bypasses BetterAuth's own attempt accounting entirely (raw
`createOTP(...).verify`). TOTP rotation makes brute-force impractical either way, but the two
2FA verification surfaces have **different** limits and no shared per-account lockout.
Consider an account-scoped failure counter so a distributed (multi-IP) attacker can't sidestep
the per-IP throttle.

### 3. `shouldPromptTwoFactor` is duplicated (server + client) with a "keep in sync" comment
The canonical, unit-tested version lives in `apps/auth-server/src/auth/should-prompt-two-factor.ts`;
a hand-copied twin lives in `apps/admin/lib/two-factor-prompt.ts` (untested, and the helper
is misnamed `getSystemTrustDaysClient` even though it reads a **server-only** env var and is
only ever called from server actions / server components). The copies are equivalent today
but will drift. Extract to a shared package, or add a test asserting parity.

### 4. Email-OTP delivery is fire-and-forget with an empty `.catch`
`otp-sender.ts` does `void emailer.send(...).catch(() => {})`. A misconfigured emailer logs
`outcome: 'sent'` with no local signal. Confirm the EmailService-side Sentry capture actually
fires in production, otherwise dropped sign-in codes are invisible. (Carried from
TODO_2026-07-15 #2 — still open.)

### 5. `parseSessionCookie` comma-splitting regex remains a known fragile spot
`apps/admin/app/login/actions.ts` still hand-parses `Set-Cookie`. Safe while BetterAuth
returns a single cookie; any change that emits a second Set-Cookie silently breaks session
forwarding. Swap in `set-cookie-parser` before that happens. (Carried from TODO_2026-07-15
#3.)
